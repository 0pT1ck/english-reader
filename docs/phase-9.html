§1

触发它的那个症状，和查出来的病根

用户的原话：「为什么复习页经常要转圈圈？……我复习完了温故知新， 返回主界面后刷新，又成了 0/13，刷新几次后才能回到 13/13。」

0/13 的完整链条

1 答 13 张，会话里数字是对的 每次 advance()（ReviewModel.swift:298）写一条事件进发件箱、 本地把 done 置上、dueDone += 1。
2 下拉刷新 → 先读缓存包 → 当场变 0/13 apply() 里 states.removeAll()（:152）， 然后 todayDone／dueDone 从包里的 progress.buckets_done 重新读（:168）。 而那个包是上一次成功取包时存的盘，里面是 0。
3 再取一次包 → 服务端回 304 → 还是 0/13 那 13 条答案还在手机上没发出去，所以服务端那份包一个字节没变。 ETag 算的是整包（backend/modules/today/module.py:55），进度当然也在里面—— 进度没变，是因为事件没到。
4 复习会话结束之后，没有任何东西去发发件箱 drain() 的调用点只有五处：启动、回前台、读完一篇文章、 拼写做完、设置页。产生事件最多的那一屏，恰恰没有。
5 所以「刷新几次」本身救不了 真正起作用的是这期间你碰巧把 App 切到后台再回来、或者去读了篇文章。 那一下发件箱空了，服务端 done_at 落了 （backend/modules/review/session.py:293 才数得到）， ETag 变了，下一次刷新才拿回新的包。

转圈的四个来源

症状原因
每次刷新都要等load() 串行两个请求： /today 然后 /reviews/calendar。 实测隧道往返 0.82–0.95 秒（2026-09-17 三次，无认证请求）， 所以一次刷新起步 1.8 秒
什么都没变也慢304 只省流量不省时间：服务端照样把整包拼出来、 序列化、算 sha256 才知道没变，还顺手往 decisions 写一条
有时一直转不出来请求被取消时 phase = .loading（:125）， 而这个状态没有重试——.offline 有个 5 秒循环，它没有
日历经常空calendar() 故意没有离线退路
病根一句话：屏幕上「我做了多少」这个数，和改变它的那些事件， 有两个来源——服务端的快照和本地的发件箱。而每次刷新，旧的那个赢。

这不是「过度依赖网络」，是依赖错了地方。内容依赖网络是对的（一天一次，有缓存有 304）； 「我刚才做完了」依赖网络是错的，而它恰好是每天要看几十次的那个数。
§2

那条线

已定

用户的原话：「每个端都必须专干他该干的事。服务端该干的事就是生文， 客户端该干的事就是拿到生的文、学习、学习完把进度汇报给服务器， 服务器根据进度继续生文。」

工厂 服务端：生文、造例句、建义项集、标注、判词组、算难度 要钱、要 API key、要 24 小时醒着。这是服务端存在的全部原因—— 手机不可能夜里 04:00 自己起来花钱写文章。
邮局 服务端：发内容（增量），收事件 而且邮局自带存档：多设备必须有一个会合点，所以事件日志本来就得存在它这儿。
学习者 客户端：拥有全部学习状态，屏幕上每个数都自己算 选文、抽题、排期、进度、日历、拼写，全在这儿。 上报事件 + 上报词池快照。
判断一件事该在哪，只问一句：它是供给还是记账？ 供给是异步的——夜里发生，不需要人在场。记账是跟着拇指同步发生的。 把记账放到 0.9 秒的隧道那一头，就是 §1 那个症状的来源。

服务端对学习记录只有两种关系：要么是生文需要的那一小撮信号（它解释，见 §7）， 要么是它不解释的存档（§5）。出现第三种关系，就是这条线破了。

§4

新的铁律

拟定

每条都附「它替掉了什么」和「怎么验」。 一条规矩没有验法，就只是一句愿望——这是 P8 §8 动铁律 4 那次学到的。

1 · 服务端不许有任何学习逻辑

替掉旧铁律 1「客户端零业务逻辑」。验法：读源码断言服务端没有排期、 没有队列组成、没有选文、没有进度聚合。

旧铁律 1 的理由现在不成立。它写的是「破了这条，将来要在三种语言里各实现一遍同样的算法」—— 而现在只有一种语言：Core 是 Swift，iOS App 和 ercli 共用同一份。 更要紧的是，搬下去之后调度只有一份实现：查过 backend/modules/generation/daily.py:66，夜间备稿从学习记录里 只要一个「正在学的词」的集合，不读排期、不读到期日、不读队列。 模块注释自己写着「The only thing this module reads from the learner's record is which words to avoid teaching again」。所以服务端根本不需要 FSRS。

2 · 客户端不许产出内容，服务端不许解释记录

替掉旧铁律 3「服务端是唯一事实来源」的措辞。两个方向都要说： 前半句防「顺手在手机上拼个句子」，后半句防「管理台顺手算一下他学得怎么样」。 唯一的记名例外在 §7，而那一条是靠「客户端上报快照」避开的，不是靠破例。

3 · 屏幕上没有一个数字等网络

新增。这是 §1 那个症状的可执行版本。验法：每一个显示出来的数都有本地来源。 这一条要配一套新的验收项，是这个 Phase 该产出的东西之一。

4 · 内容 id 一旦发出去就不许变

这一条现在不成立，而新架构必须有它。 现在文章可以被重新分析，reading_tokens 删了重建、id 全变—— 「踩过的坑」§6.5 就是这么来的：标注任务举着旧 id 报成功、 文章永远停在 annotating、点开是空的、全程零日志。

以前这个坑只伤服务端自己。记录搬到设备之后，标记指着的是内容 id， id 一变就是设备上的记录静默失效，而且是在别人的手机上失效。 所以「内容 id 不可变」从实现细节升成契约。

推论：重新分析必须变成加一个新版本，不是原地重建。

＝可扩展性优先 模块自包含、一处登记自动挂载、订阅事件而非改原流程、版本化迁移。这套东西正是让这次搬家做得动的原因。

为什么决策日志是第五种，而不是第六类派生物

因为它不可重算。抽卡用的是 Double.random，当时货架上有哪几篇、 配置是多少，过后都复原不出来。丢了就真的答不上「为什么」—— 而这一类日志的设计目的原话就是「用户说『不对劲』时，AI 能查出来到底怎么了」。

现在全项目只有两个地方写它，一共 118 行： article.prepared（备稿，15 行）与 today.assembled（选文，103 行）。 前者是工厂决定、留服务端；后者是选文，按 §2 归客户端。 重构之后客户端还会多出几个同类的判断：抽了哪张卡、排期给了什么评级和间隔、拼写词表怎么挑的。

定的是存在服务端（客户端把它当一种事件上报），三个理由： 诊断工具在服务端（管理台是诊断通道）；存着不看不算解释，和存档是同一种关系； 走发件箱那条现成的管子，不用造新机制。量也不值一提—— 选文一天一条、抽卡一天三十条左右，一年一万来行。

顺带两个小修，都在这个 Phase 里做掉：
① 现在 today.assembled 是每次 /today 请求都写一条 （所以 103 行里绝大多数是下拉刷新写出来的）。它该在真的做了一次选文时写。
② 抽卡要记种子，或者整天用一个带种子的 PRNG。 现在 Double.random(in: 0..<1) 抽完就没了，记了也重放不出来—— 改成有种子的，「为什么抽到这张」才真的答得上，顺带验收脚本也能复现。
§6

多设备：事件日志成为主干

已定 ③，三条细则拟定

状态是事件日志的纯函数。两台设备各自重放，得出同一个状态—— 所以不需要合并算法。Anki 撞到真冲突时要弹窗让人选「上传还是下载」，我们不用。

我们已经走了一半而没说出口：发件箱本来就是追加式的、带幂等键、带 occurred_at； OutboxVerdict 是逐条的（Core 的注释写着「silence is not consent」）； 铁律 2 本来就说事件先落本地。缺的只是承认它是主干，而不是一条上报管道。

三条细则

① 服务端收到即分配单调序号，排序用序号 两台手机的时钟不一样，而重放要全序。设备时钟（occurred_at）原样保留， 只用来判「当天」。两个用途分开，别用同一个数。
② 同步变双向 现在只有发件箱（上报）。要加「拉取序号 N 之后的事件」。
③ 唯一一种真冲突：同一张卡，两台设备在同一天各答一次 按现有规则累加——规则本来就是「一天算一轮，asks 累计， 失误次数定评级」（P3 决定 11）。重放天然就对，不用特殊处理。 这条要写进不变量，否则以后有人会「修」它。
多设备把备份这件事顺手解决了。上一轮我说服务端要当个「保险柜」， 存一坨它不解释的字节——不对：它存的是结构化的事件日志（多设备要按序号合并）， 但它仍然不解释。备份不是另一件事，是同步的副产品。 三个角色因此缩成两个：工厂 + 邮局，邮局自带存档。

§8

义项换稳定键，和那次数据大清洗的关系

拟定

讨论里一度以为「先清洗、后重构」更安全。 数完真实数据之后这个理由站不住，但顺着它查出了一件更该做的事。

先说清楚现在「方便替换」是个陷阱

backend/modules/senses/repository.py:37-48 自己写着：

This path is for topping up one word. It is the wrong path for replacing
the whole inventory … Called in a loop over every headword, the subscriber

所以「按一下按钮就能全量替换」这件事本身是成立的，代价是静默作废九万多条标注。 跨 Phase 不变量那一段就是为了拦住这个按钮而写的， 它推荐的正确做法（保留旧表 + 义项级映射，约 7,200 次调用） 就是「费很大力」的来源，而它是现在这个架构的价格，不是重构的价格。

但「为什么费力」有一半是架构造成的

躲不掉 新义项集对词的切分本来就和现在不一样 要从真词典源重建，「旧义项 3 对应新义项 2」是个判断题。 7,200 次调用就是这个判断的价格，重构不能让它变便宜。
可避免 义项 id 是自增代理键，store_senses 是删了重插 于是任何一次重建——补一个词的义项、重跑一次生成器、做一次迁移—— 都会让 id 全变，而这跟语义变没变毫无关系。 九万条标注每次都被推到悬崖边上，靠一段注释和一条不变量拦着。

所以 P9 做三件，清洗本身不在 P9

① 义项换成稳定的自然键 headword + 内容指纹。标注和学习记录都指它，不指自增 id。 替换整个库变成「按键 upsert」，语义没变的义项键不变、标注自动存活。
② 映射表永不删除 13,741 行，留着不费什么。有了它，离线设备揣着旧 id 回来也翻译得出来—— 这是多设备逼出来的要求，不是可选项。
③ store_senses 那个「删了重插」的行为本身改掉 不再靠注释警告。

数据大清洗不属于 P9——它是数据操作，不是重构，按「只规划当前 Phase」留在主文档 §M。 P9 做完之后它从「7,200 次调用 + 悬崖」变成「7,200 次调用，而且掉不下去」； 稳定键做得好的话，只需要给真正合并／拆分／消失的那部分调用。

② 两个上限本来是两条规则，代码把它们混成了一条 — 2026-09-17 定并改完

用户的决定：「太简单了」是学习者的判断，提示不否决它—— 它藏在右上角的二级菜单里，点它的人知道自己在干什么，不存在误触； 但看了提示就降一档。

· 当天刚标——P7 §3 原话「当天这一次封顶为 Hard」＝封顶，不是降档
对 Good 两者结果相同（都得 Hard），所以混着也看不出来； 对 Easy 就分家了：降一档是 Good，封顶是 Hard。 两处注释也各写了一半——session.py:50 写的是 "caps the grade at Hard"， scheduler.py 写的是 "costs a grade"，两句话说的是两回事。

④ 事件日志 — 做完。U2 那个决定改了

client/Sources/ERCore/EventLog.swift（251 行）＋ 6 项测试。 一个追加式文件,一行一条 JSON——不是 SQLite,也不是发件箱那套「一条一个文件」。

U2 原本定的是「系统 SQLite ＋ 薄封装」,2026-09-17 改掉。三条依据:

① 量太小,数据库没活可干。 实测全部历史 375 条事件, 增速约 70 条/天 ＝ 2.5 万条/年,一年约 5 MB。重放两万五千条是毫秒级的, 投影整个放内存里、启动时重放一次就有——比任何查询都快。 我当初主张 SQLite 的理由是「客户端现在真需要查询了」,而 U3 量完之后那个理由不成立。

② Linux 那一课刚上过。 从 Swift 用 SQLite 在 Linux 上要 systemLibrary ＋ modulemap ＋ 容器里装 libsqlite3-dev。 和 import JavaScriptCore 同一个形状的风险,而且这次是自找的。

③ 有数据库会把人引回旧错误。 一张 study_states 表摆在那儿, 下一个人就会把它当事实来源直接改——而 P9 存在的全部理由就是那件事。 「只有日志能写,投影只能算」这条规矩,靠「没有别的东西可以写」来保证最结实。

发件箱那条「一条一个文件」的理由不适用。 它的原话是 「a log only grows, so it has to be compacted, and compaction rewrites the whole file」——而这份日志永不压缩(它是事实,只增不减,5 MB/年没必要), 所以那个失败模式不存在。反过来,两万五千个文件会让每次追加都去列一遍目录, 而那正是发件箱越用越慢的原因(P8 §18 修过一次同形状的)。

唯一的崩溃损伤是断尾:最后一行写了一半。而那一行按定义是「还没告诉用户 已经保存」的那条——和发件箱依赖的是同一个性质。丢掉它,但报出来, 而且和「中间坏了一行」分开报:前者是崩在写的那一刻,后者要查。

「报到哪儿了」存在日志之外的小文件里,绝不回头改日志。 改日志就意味着重写它,而重写是这份文件唯一没有的危险操作。

⑨ 一条事件只有一个家 — 做完

在这之前一条标记写两处：先进日志，再进发件箱。 那中间有一个窄口子——崩在两次写之间，事件在日志里而发件箱里没有， 于是它永远发不出去，而屏幕上什么都不会说（本机重放算得出它，服务端永远不知道）。 现在 drain() 直接从日志取那五种（SyncEngine.drainLog）， 发件箱只剩遥测——打开文章、读到哪、点了哪个词，那三样不改变任何状态， 所以它们本来就不在日志里。

映射搬进了 Core（OutboxEntry.loggedKind），App 与 ercli 共用一份：两份判断早晚会在某一种事件上分家， 而那时一台设备把它记进历史、另一台没有，两边都不会报错。 ercli 那 17 处 outbox.append 全部改走同一个 record()。

一个水位线不够用，这一条是想清楚才写的，不是撞出来的。 服务端的回应是**逐条**的（Core 里那句注释：「silence is not consent」）， 所以一批里可能第 5 条落了、第 6 条被拒、第 7 条又落了。 只有水位线的话，被拒的那一条会把它后面全部挡住——那比重发一条糟得多。 所以水位线之上单独记一个集合，追上了就清空。 平时那个集合是空的:事件按顺序发、按顺序落。

决策事件从「待发」里过滤掉。 §5 定了它存服务端， 但那个端点还没做（§6 的活）——不过滤的话它会永远堆在那儿， 把待发数变成一个永远非零的噪音。而待发数现在要算上日志， 否则标了一个词、待发显示 0，而它其实还没送出去。

⑮ §10 数据库重切：查清楚了，但没有执行，而且是有理由的

两件事先查明白了，一件是好消息，一件不是。

好消息:168 处调用不用改。 实测 SQLite 的**未限定表名会在 attach 的库里解析**， 读和写都是（写也真的落进那个文件）。而 learning 这条连接本来就 attach 着 dictionary 与 content。所以把表挪到别的文件之后， SELECT … FROM reading_articles 照旧解析得到—— 物理重切不必动那 168 处 get_connection("learning")。

不是好消息的那件:迁移记录也在 learning.db 里，21 条、10 个模块。

schema_migrations 是**每个库一张**，而每条迁移自己声明 database="learning"。所以搬表要同时做三件事:把表挪过去、 把那个模块的迁移记录也挪过去、把所有 database= 改成新家。 漏一条，那个模块的全部迁移会在新库上重跑一遍—— 而 CREATE TABLE IF NOT EXISTS 重跑无害， ALTER TABLE ADD COLUMN 和那几个可调用的迁移 （比如 _merge_study_tables）重跑会失败或者把数据弄坏。

也就是说 §10 是一次「20 张表、21 条迁移、3 个文件，每一处都要对」的手术， 而它动的是 93,063 条标注和全部学习记录。

所以这个 Phase 的顺序要改一下:§11、§12 先做，§10 放到它们之后。 理由是 §12 那条纪律本身——「先搬网，再搬代码」。而现在**网是不全的**: 中转站 402、gemini 的 key 只在阿里云，所以标注这一路调不通， verify_phase2 与 verify_phase4 有几项因此报红 （CLAUDE.md 早就写着那几条「不是回归，别去查代码」）。 在一个知道自己不全的网底下搬 20 张表，正是那条纪律要拦的事。

改完之后这个 Phase 的收尾顺序是: §11 模块劈开 → §12 验收网搬家 → §10 数据库重切 → 删 Web 学习页。 §10 从「中间那一步」挪到「倒数第二步」，而它要的前提正是 §12 给的。
