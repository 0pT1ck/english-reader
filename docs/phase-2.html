§1

交付什么

一句话：电脑上打开一个列表，挑一篇文章读完，点过的词、标过的词、读到哪儿，全部回到服务端。

P2 之前，文章是不存在的。generation_drafts 里那 34 篇是 P1 的实验产物——一整坨文本，没有拆开，没有句子，没有词。 真题 452 篇躺在磁盘上，只被句法统计脚本按文件读过。库里没有任何一样东西可以被「读」。

所以 P2 的主体工作有三块：把文章拆开存进库、把客户端接口定下来、把 Web 阅读页搭起来。 P1 顺延过来的两项（语境释义标注、真题难度画像）都在这三块里各归其位。

与主文档 §K 的一处出入

§K 给 P2 写的是「今日包与事件上报接口」。经讨论决定 P2 不做 /today，客户端就是一个文章列表，你自己挑。

理由是 /today 需要「服务端决定今天读什么」，而选文算法在 P3、水平估计在 P3、提前生成在 P6。 P2 要么手动排、要么写一个占位规则——占位规则一旦写得像算法就跨了 Phase，写得够笨又没验证到什么。 而 §K 本来就把「真题直读（列表选读）」放在 P2，列表这条路是必须做的。

代价要记住：铁律 2 的「服务端决定 + 多篇一次全量下发」这个行为，到 P6 才第一次真跑。 损失有限——单篇下发时全文与全部标注一次给全，读的过程零请求；事件先入本地队列再批量上报。离线形状的一半仍被验证。 而且 /today 是新增接口，不违反只增不减。

补记（同日稍后）：这个代价比写下时更小。讨论中确认了内容供给的目标形态是 「每天生成若干篇不同主题的文章，你挑感兴趣的读」——那本身就是一个列表加一次挑选。 列表自选不是 P2 的临时妥协，是最终形态的一部分；/today 将来要做的也更接近 「今天备了这几篇」而不是「今天只准读这三篇」。详见 §5 末尾。

Web 阅读页跟手机没有关系

§K 给 P2 写的完成定义是「手机上真读完一篇」，这句跟铁律 8 冲突，以本文为准： Web 阅读页只在电脑上跑，是开发期的测试工具，用完即弃。手机上要用的是 P7 的 iOS 原生端，那才是要好看、要顺手的那个。

所以这一阶段不做移动端适配：不做响应式布局、不做触摸手势、不考虑小屏排版，也不测手机浏览器。 连字号滑块都不做——浏览器的 Ctrl+滚轮 已经是这个功能，而每天要待二十分钟的那个界面在 P7。

这不是省事，是不把 UI 力气投在一个注定要扔掉的东西上。P2 要验证的是接口形状、入库管线和数据落库， 这三件事在电脑上验证得同样彻底——断网测试甚至更彻底：直接把后端停掉即可。

§3

文章怎么存

决定 1

拆成三层，全部在 learning.db。拆开存的目的只有一个：运行时不做任何语言分析。

文章  《Why cities get hotter》  300 词，来源=生成 / cet4-2019-06
 └ 句子  #3  "The city council addressed the problem last year."
     └ 词  addressed → 词条 address，动词，字符 27-36
              语境义项 = #2 着手解决
              类别 = 目标词

点一个 addressed，服务端不能现场跑 spaCy——查表即可。 这是主文档 C5 的原话：「这项分析在文章入库时一次性完成并存好，运行时只是查表，低配硬件也毫无压力。」 NanoPi R5S 是最终部署目标，这条不是优化是前提。

为什么不进 content.db

生成的文章是花钱产物，按「丢了会怎样」的分类该进 content.db。但决定是进 learning.db，理由是恢复备份的一致性。

设想：用上周的备份恢复 learning.db，而 content.db 是今天的。如果文章在 content 里，两个文件的文章编号对不对得上要看运气； 在同一个文件里就没这个问题。这是唯一一个会真正伤到数据的风险，其余（备份从几 MB 涨到几十 MB、多用户时真题被复制 N 份）都是洁癖问题或尚不存在的场景。

跨库查询不是这次的考虑因素。P0 已经把它解决了：get_connection("learning") 上已经挂载了 content 与 dict， SQL 里直接 JOIN content.senses。三个月前那个设计现在正好收租。

不另建「遇见记录」表

主文档 F2 要求记录到最小单位：某个词的某个义项、在某篇文章的某一句里出现，以及当时的反应。这两半已经分别有地方了—— 「出现」就是 tokens 表的每一行，「反应」就是 word_marks。再建一张 encounters 表是把 tokens 抄一遍。

日志规范写着「业务记录本身就在业务表里，不重复记」。同一条原则。

前提是文章入库后不可变：改了文章，历史遇见记录就跟着变了。所以要重新生成就是新建一篇，不是改旧的。

但要另建一张「现在什么状态」的表

上面两半回答的是「发生过什么」。还缺第三样：这个词现在到底怎么样了——学过没有、第一次是在哪篇学的、总共遇见几次、当前标成了哪一档。

没有这张表，两件事做不了：复习不知道该复习谁，生成不知道哪些词还没教过。 它对应主文档 F3「义项级掌握状态」，一直是设计里有、表里没有的东西。

这不是未来的活儿，P2 就得有。「读完一篇，这篇的目标词自动记为学过」这个动作从第一天读文章起就在发生； 表不建，数据从今天起就在丢，将来补不回来。P2 只写状态，不做调度——什么时候安排复现是 P5 的事， 记忆强度、难度、下次到期这些列 P2 不建。

建行的范围有限：只给已引入的目标词和你手动标记过的词建行。 附带词按主文档 C6 是「只给释义，读完即止，不产生任何任务」，不进这张表。

§4

点一个词，框里显示什么

决定 2 · 7

主界面上唯一高频的交互。你点的是什么词，该显示的东西不一样——这是 P2 最需要想清楚的一处。

普通生词：三层释义

Lin asked each student to write one short account of a recent conflict.

① 这句里的意思    报告 / 描述 / 叙述
                  a written or spoken description of something that happened
② 常见释义        n. 报告, 解释, 估价, 理由, 利润, 算账, 帐目 / vi. 报帐…
③ 四六级常考      义项② 在真题中出现 N 次 · 熟词僻义

第一层是 P1 顺延过来的「语境释义标注」。做法是文章入库时让模型从我们自己的义项表里选一个编号， 不是自由写一句中文——选编号可以校验（编号必须存在、必须属于该词条），错了能重试，还能直接接上 P5 的义项级记忆状态。

第一层同时给出英文概念定义（senses.concept_en，已有）。主文档 C1 的原话：这样查词本身也是阅读输入，而不是在中英之间来回切换。

覆盖全篇实词，不只覆盖生词

实测三篇 gpt-5.5 生成文：去重实词 176–205 个，其中 98% 在义项表里，80% 以上是多义词。

这个 80% 就是理由。不标注的话，点开任何一个「你以为你认识」的常见词——account、measure、subject—— 看到的都是词典那一坨逗号堆，还得自己判断哪条对。而主文档说得很清楚：熟词僻义正是 CET 阅读最爱考的地方。

已知风险：一次让快模型输出 180 条会在后半段漂移或偷懒——这是 P1c 已经吃过的亏 （「读 25 条清单做语义聚类」超出了快模型的能力）。缓解办法是按段落分批，每批 30–40 个词、输出短， 并且校验每个返回的义项编号确实属于那个词条。

四种特殊分支

派生显示构词分解，不当新词 点 nationality 显示 nation + -ity 而非一条新释义。词族表 10,471 条现成。 主文档的理由：考场上靠词缀猜出大意，比多背几个词值钱。
专名可点，但不计生词率 点 Camulodunum 明说「这是地名，跳过就行」。生成时故意保留适量—— 「看见陌生专有名词直接跳过」本身就是要练的阅读技能。
超纲明说「暂时不用学会」 给中文意思让句子读得通，同时标明它不在你的范围内。判断靠词典的考纲标签，数据现成。 真题里的超纲词不加这个标记——C10 明说，在真题直读这条线上，遇到不认识的词本来就是要练的内容。
功能词可点，给词典释义 C1 说「点击任意词」，所以 the / of 也要能点，不做特殊处理。

两处依赖还不存在——留位置，不留空

这两项原设计都需要 P2 还没有的东西。处理办法不是砍掉，是把契约里的位置留好、值先给空， 并由 §6 的能力声明说明「这不是没数据，是还没实现」。做法与理由见 §6。

P3派生词是否已掌握词根。 原设计是词根已掌握时才显示构词分解。「你认识哪些词」要到 P3 才有—— 契约里 root_known 现在就在，值为 null，能力声明里 level_estimate: false。 P2 的客户端一律显示构词分解，那句「你已经认识 nation」的位置显示为待开发。
待生成专有名词的一句话说明。 原设计要说明「这地方是干嘛的」，那要再花一次模型调用去写。 契约里 note 现在就在，值为 null，能力声明里 proper_noun_notes: false。 P2 的客户端显示「这是个名字，跳过就行」，说明位显示为待生成。
§5

词的状态

两个维度

一个词有两件事要记：你怎么看它（标记档位，你手动给的），和它在学习流程里走到哪儿了（词池位置，系统自动给的）。原设计这两件都不完整。

维度一：你的标记 —— 三档

原设计只有两档：标记生词，和什么都不标。讨论中发现中间缺一档。

看到 nation + -ity 当场「哦」一声，跟三个月后在考场上还认得，是两回事。 熟词僻义同理：点开 account 发现这句里是「叙述」不是「账户」，当下懂了，下次未必。

档含义去向
不认识标记生词进复习队列，安排复现（P5）
模糊现在懂了，但未必记得住存着，将来某次复习捎带出现（P5 决定时机）
（不标）我认识隐式信号，系统默认你会

任何词都能标，不限于派生词

这个念头起于派生词，但本质是「现在认识了、未来不一定」，跟是不是派生词无关。 限定在派生词反而要多一套判断，而且遇到熟词僻义时你只能二选一——要么标成生词进完整复习队列，要么什么都不标。

手动按钮，不自动

弹层底部两个按钮：[不认识] 和 [模糊]，你觉得会忘才按第二个。

不做成「点开就自动进模糊表」的理由：你点了哪些词本来就已经在记录了（word.tapped 事件）。 如果「模糊」等于「点过」，它就是冗余的，白建一张表。模糊的价值恰恰在于它是一次主观判断。

P2 做到哪一步

做弹层入口、事件类型、一张薄表（哪个义项、什么时候、在哪篇哪句标的、标过几次）
不做什么时候复现、间隔多长、怎么评分——那是 P5 的遗忘曲线。这张表里不出现「下次到期时间」「记忆强度」「难度」这类列，等 P5 来加

这正是铁律允许的「留位置，不提前开发」。

状态挂在义项上而不是词条上，与主文档 E1 一致——语境标注已经给出了义项编号，所以标记时它是现成的。 这也是「认识 address 是地址 ≠ 掌握了它在本文里的义项」这条设计的兑现处。

标记跨文章互通，粒度是义项

状态挂在义项上而不是挂在文章上，所以标记跟着词走：A 篇里标了，B 篇里出现同一个词的同一个义项，点开就是已标记状态。 词形变化不影响——addressed 与 addresses 都归到词条 address，靠 P0 的词形还原。

account 有四条义项：① 账户  ② 叙述  ③ 认为  ④ 占

A 篇  account = ②叙述，你标了不认识
B 篇  account = ②叙述  → 已标记  ✓
C 篇  account = ①账户  → 未标记（有意如此）

第三种情况是设计使然，不是缺陷。按单词记的话，你标过一次 address 系统就永远以为你会了， 而考试恰恰考你没见过的那个义项——主文档 D2 的原话：「按词条追踪，认错义项这种错误永远抓不出来。」

但界面上必须说破，否则会显得系统失忆。 在 C 篇点开 account 时，弹层要提示「你在另一篇文章里标记过它的另一个义项『叙述』」。 这行提示本身就在教熟词僻义——让你意识到「这词我见过，但这次意思不一样」。所以 GET /articles/{id} 除了返回本义项的状态，还要带上同词条其他义项的已有标记。

两个连带问题

1没有义项集的词，退回词条级 真题里约 10% 的词不在义项表里（超纲词、生僻派生词），没有义项编号可挂。 这类词的状态把义项编号留空、按词条记。它们本来就是「不用学会」的，粒度粗一点没有损失。
2客户端要合并本地未上报的标记 读 A 篇标了几个词、还没联网，接着读 B 篇——B 篇的数据是早先拉的，带的是旧状态。 客户端必须把本地队列里未上报的标记合并到新打开的文章上，不能只信服务端下发的那份。 不做这一步会出现很难查的现象：断网时标的记号换一篇就「看不见」，联网后又冒出来。

维度二：词池位置 —— 三格，系统自动给

手动标记不够。读完一篇，这篇的 25 个目标词应该自动记为「学过了」，不需要你一个个去点。 这个状态有两个用处：安排复习，以及让生成器知道哪些词还没教过。

词池什么意思生成文章时怎么用
没学过还没被任何文章引入过从这里抽新目标词
复习中引入过了，还没稳固到期就安排它在新文章里再露一面，但不占新词名额、不再讲解
毕业遇见够多次、抽查也过了彻底不再管

为什么「学过就永久退出」不行

讨论中最初的想法是「学过的词以后别再拿来生成文章」。这条如果照字面做，会跟复习打架。

主文档写着一个词要稳固掌握需要遇见 8–12 次，而复习的主渠道（E2 双通道）是把到期的词塞进当天的新文章里—— 在真实句子里再碰一次效果最好，卡片只是塞不下时的泄压阀。学过一次就永久退出的话， 每个词一辈子只在文章里见过一面，剩下 7–11 次全靠卡片，那就退回成背单词软件了。

所以真正的诉求是「别老拿同样的词当新词讲一遍」，对应的是不再占新词名额，不是不再出现。 「彻底不再出现」是第三格「毕业」的事。结论：还该出现，但不再讲解。

顺带确认了内容供给的目标形态

讨论中提出的另一半想法：每天生成若干篇不同主题的文章（各用各的词，不是同一批词的多种写法），你挑感兴趣的读，读完就记账。 没被读的那几篇，词留在池子里，以后还会出现。

没读的不删，留着，分「新备的」与「往期」两个列表：新备的只放最近三天（配置项 reading_fresh_days，控制台可改）， 保证打开就能一眼挑完；过期自动转往期，随时能翻出来读，读了照样记账。

没读的文章用掉的词不算已学。这条落到实现上是一句很硬的约束——记账只发生在读完那一刻，生成时不写任何状态。 所以那些词仍在「没学过」池里，以后还会被抽去写新文章。

这套供给机制不属于 P2，属于 P6 日常运转（提前生成、每日流程）与 P3 自适应（按兴趣主题挑词）。记进待办，本阶段不动手。 但它确认了三件与 P2 有关的事：

1列表自选是最终形态，不是妥协。「生成几篇你挑」本身就是列表加一次挑选，见 §1 补记。
2sense_states 必须在 P2 建，且只在读完时写。「读完记账」从第一天读文章起就在发生，表不建数据就在丢； 而「生成时不写」这条约束要从一开始就守住，否则未读文章的词会被误记为已学。
3articles 表要有状态与备稿日期，列表接口要能筛。 未读 / 已读、哪天备的——「新备的」与「往期」两个列表靠它分。P2 就要有这两个字段，不然 P6 没法在不改契约的前提下接上。

一笔要留到 P6 去算的账：备五读一的话，要读满 289 篇就得生成约 1445 篇。 实测每篇约 4300 输入 / 680 输出 token，而写文章必须用贵的那个模型——gpt-5.5 超纲率 0.32%， 同一套提示词换 deepseek-v4-flash 是 3.64%，差十倍。 不过保留未读大幅削减了这笔浪费：没读的不是废品，只是还没轮到，真正白花的只有你这辈子都没点开的那些篇。 生成成本在主文档 §M 里已经是一条待定项。

顺带一个好处：积压会自己变成复习材料。某个词在没读的 A 篇里用过，后来又被抽去写了 B 篇。 你先读 B，这词记为学过；再回头读 A 时，它在 A 里自动变成「复习中的词露一面、不再讲解」——旧文章越积越像混合了新词与复习词的正常读物。

§6

客户端契约

铁律 4 · 5

P2 之前 /v1/client/ 下一个端点都没有。这是第一笔，也是要陪着侧载客户端跑很多年的那一笔。

POST /v1/client/devices/register   设备注册换令牌（P0 的 devices 表已有）
GET  /v1/client/library            文章清单 + 各项难度指标
GET  /v1/client/articles/{id}      单篇：全文、句子、每个词的标注、你已有的标记
                                   （含同词条其他义项的标记，供弹层提示，见 §5）
POST /v1/client/events             批量上报，每条带幂等键

单篇一次给全，读的过程零请求——这是离线形状在 P2 能兑现的那一半。 没有「阅读偏好」这类接口：字号交给浏览器缩放，而真正的阅读偏好属于 P7 的原生端，那时是设备本地的事，不进服务端——它不是学习记录，多设备之间也不需要一致。

「这是谁的数据」这个口子

主文档 §M 记着这条过期不候：P2 正是定义客户端接口的那一刻，焊死了将来加多用户就只剩开 /v2/ 重写客户端、或者用别扭的追加字段打补丁两条路。

做法是身份由令牌推导，不由客户端自报：

Authorization: Bearer <设备令牌>
   ↓ 服务端：令牌 → devices 表 → 这台设备属于谁
GET /v1/client/library
   { learner: { id: 1, name: "…" }, articles: [ … ] }

接口路径里不出现人的编号；将来加多用户，在 devices 表上加一列写明归属即可，手机上的旧客户端一行不用改。 响应里回显 learner 是为了让客户端能发现「换人了，本地缓存该清了」。

不实现注册登录。这是协议层面说得通，即铁律明确允许的「留位置」。

未来资产在契约里怎么占位

P2 定的接口要陪着侧载客户端跑很多年。凡是将来某个 Phase 会填上的东西， 字段现在就在、值先为空，客户端照常渲染一个「待开发」的位置。 P3／P4／P5 上线时服务端把值填上，客户端一行不用改。这是铁律 6 的「留位置」，不是提前开发——不实现任何产生这些值的逻辑。

光留 null 不够。root_known: null 到底是「这个词没有词根」还是「水平估计还没做」？ 两种情况客户端该显示的东西不一样——前者什么都不显示，后者显示「功能待开发」。所以每个响应顶层带一个能力声明：

只留形状显而易见的位置。一个布尔、一句话、一个数、一个可以整体为 null 的对象——这些猜错的余地很小。 结构复杂的不猜：复习卡片长什么样、抽查题长什么样、今日包里装几类东西，都等它们各自的 Phase 自己来， 以新增端点的方式接入（/today、/reviews、/quiz），而不是现在往 article 响应里塞一个猜的字段。

一个差点写进代码的度量错误

本方案初稿把这两项写成「不在 cet4 表里的比例」。按那个算法量出来是这样：

超四级词比例   58.2%   57.1%   56.9%   ← 四级最高，完全反了

原因是 ECDICT 的 tags 记的是「这个词出现在哪几张表上」，而表是分级的：

the      tags='zk gk'                 ← 中考、高考，但没有 cet4
make     tags='zk gk ielts'
people   tags='zk gk'
dwindle  tags='toefl ielts gre'       ← 真的超出四六级
moisturizer  tags=None                ← 什么表都不在

「不在 cet4 表里」把 the、make、people 全算成了超纲词。 正确算法是累积：在四级水平之内 = 带有 zk / gk / cet4 任意一个。

这是第二次栽在同一类错误上。第一次是「形式主语几乎为零」——改了三轮提示词， 最后发现是校验器在数 there be。主文档记的教训原话：一个错误的度量比没有度量更危险，改代码前先验证指标本身在数什么。 这次的区别只是在写进代码之前先跑了一遍数。任何新指标上线前，都要先找一个已知答案的样本验证它数得对。 真题的三个等级就是现成的已知答案。

2analyzer.py 修了一个断句缺陷，见下。生成工作台加了一个「入库」按钮。

六个写完才发现的缺陷

其中三个的共同特征是不报错——功能看上去完全正常，只是数据悄悄不对。 这也是为什么验收清单里要有「入库但没读的文章，其目标词仍在没学过」这种反过来查的条目。

1句子会跨段落焊在一起 spaCy 的 senter 只看标点、不看排版，于是不以句号结尾的段落被焊到下一段上。 一篇真题里 17 句其实该是 20 句，而那个「巨型句」正是喂给标注模型的上下文、阅读页高亮的单位、进度恢复的粒度。 修法是在句法分析后按换行强制断句——只有排除了依存句法分析器才允许这么做，而本项目正是排除的。 这是 P0 的分析器缺陷，P2 是第一个真正用到句子边界的消费方。
2重复事件把数据库锁住了 幂等去重靠唯一索引报 IntegrityError，而捕获之后没有回滚。 失败的 INSERT 会把隐式事务挂在那儿，写锁一直不放。症状是几步之后一个毫不相干的请求报 「database is locked」——我为此追了六轮才定位到。凡是吞掉数据库异常的地方，都要问一句事务归谁收。
3目标词解析错了，而且不报错 generation_drafts.target_words 存的是 JSON 数组，按逗号空格切会切出 ["assignment" 这种永远匹配不上的东西。后果是文章照样能读、照样能标记，只是读完什么都不记—— 没有报错、没有日志。验收清单里那条「生成文章的目标词被标出来」就是抓这个的，它当场抓到了。
4被判成专有名词的目标词漏记了 记账那一步只统计「实词」，而生成器要求用目标词 latin、模型写成 Latin， spaCy 判成专有名词，于是二十五个目标词里静默少记一个。 被指定为目标词是比词性标注更强的信号，所以记账的条件改成「实词，或本篇的目标词」。 验收清单查的是「25 个目标词，25 个已在复习中」，差一个就红。

标注：四分之一的词不用花钱

调模型之前先settle两类词——没有义项集的（记为 0）和只有一个义项的（直接选它）。实测一篇 344 词的真题：

164 个实词
  11 个没有义项集   → 直接记 0，退回词条级
  34 个只有一个义项 → 直接选它
 119 个真正有歧义   → 3 批调用，7 秒，10007 输入 / 717 输出 token

按这个比例，452 篇真题全量标注约 450 万输入 token，用 deepseek-v4-flash—— 模型选择没有另外配置，默认提供商正好就是它，与 P1 的实测结论一致：标注是数据整理，不是写作。

一个我自己写错的提示词

标注提示词最初有这么一句：「如果候选义项里没有一个贴合，选最接近的那个。」 跑完全部真题之后回头抽查，它把诚实的「答不上来」变成了悄悄标错：

around 3:30 a.m.            → 标成「到处／四处」   ✗ 该是「大约」
a heavy note of hypocrisy   → 标成「注意／留意」   ✗ 该是「口气、意味」

而这两个词的义项集里真的没有那一条。所以模型第一轮干脆跳过反而是对的判断， 是那句话逼它硬选。改法不是调措辞，是给它一个正当的「都不贴合」选项——填 0， 并说明白填 0 是正当答案、不是失败。这正是主文档记着的那条经验： 说清楚什么时候该用，比施加数量约束有效。

改完之后仍然不够好，所以没有继续调。逃生口用起来了，但既有真阳性也有假阳性： get up、known as、at least 跳过是对的（那些是词组， 而主文档 §J 明确不做词组）；ocean 在 span the ocean 里跳过是错的（义项①明明贴合）； around 和 note 则还是被硬标了。 再往下调每轮都要花钱跑真题，而取舍该你看过再定——见文末待定。

「没有贴合的义项」成了一份免费报告

被跳过的词连同它的句子存了下来（sense_id = -1，与「这个词没有义项集」的 0 和「还没标注」的 NULL 各不相同），控制台上有一页漏义项报告。 这正是 p1c §3 设计过、但没有实现路径的那件事：一个词的义项集覆盖不了真题里实际出现的用法， 就是一条该补的缺口，而标注器顺手就把它们找出来了。

补完义项之后点「重跑标注」，这些词会被放回队列重新判断。

一个词不能把整篇文章卡住

第一轮跑完，77 篇里有 3 篇永远停在「标注中」——各自只差一个词。 现在模型答不上来的词会被结掉（退回词典释义），文章照常可读，缺口进报告。 一个词扣住一整篇是不可接受的失败模式，而它只在跑到第七十七篇时才暴露。

补一个词的义项，会静默打断所有已有标注

决定「先补义项再全量跑」之后，第一件事是检查这条路本身通不通。不通。

store_senses 是先 DELETE 再重新插入，新 id 是自增的。而 P2 是第一个记录义项 id 的阶段—— 每个词的每次出现、每条标记、每条掌握状态都指着它。所以补一个词的义项，会让这些引用全部指向已删除的行， 没有报错、没有日志，只是释义面板从明天起显示得比昨天少。实测：补 around 和 note 两个词，就打断 14 处已标注的位置。

修法按铁律 6：义项模块公告自己的数据变了，阅读模块订阅并自修。义项模块不需要知道有人引用它。

senses.store_senses()  →  emit senses.replaced
                              ↓
                       reading 订阅，分三类处理：
                         标注   → 置回待标注，重新判断
                         标记   → 落到词条级（0），保住「你标过这个词」
                         掌握状态 → 同上，合并遇见次数与最早引入时间

标记和状态不猜新旧义项的对应关系——猜就是编数据。丢掉的只是「哪一条义项」， 保住的是「这个词你标过、你遇见过」，那才是不能丢的部分。验收 7.6 查全库悬空引用必须为 0。

闭环合上了：报告 → 补义项 → 自动失效 → 重标

用漏义项报告当输入，手工补了两条确实缺失的义项，然后重跑受影响的文章：

around 3:30 a.m.          到处／四处 → 大约          ✓
around 1 p.m. / 3-4%      到处／四处 → 大约          ✓
have people ... around    到处／四处（不变）           ✓ 本来就对，没被带跑
a heavy note of hypocrisy 注意／留意 → 口气／意味     ✓
hand over notes and coins  → 没有贴合的义项        ← 当场又抓到一条：note = 纸币

补两条义项修正了四处错标，并且立刻暴露出第三条缺口。 这条路是通的，而且每跑一轮都会自己产出下一轮的输入。

词族分级：设计早就规定，但一直没实现

第一版把每个派生词的拆解都显示出来，于是出现了 University ← universe—— 拼写像、来源无关，作为构词提示是误导的。但翻回 P1b 建表时的注释，判断标准早就写好了：

A  透明、纯语法（carefully ← careful）。根本不是新词。
B  可推导但有专门含义（nationality ← nation）。以拆解形式显示。
C  语义已漂移（depart ← part）。显示拆解会误导。

过滤掉 C 是第一步。但第一版的过滤规则我判断错了一次，值得记下来。

当时的想法是「A 级直接采信——纯语法后缀正是规则可靠的地方」。 准备验收清单时随机抽了 25 条规则生成的 A 级条目，约五分之一是错的：

forster  ← forst + -er     词根根本不是个词
brunner  ← brunn + -er     同上
renoir   ← noir  + re-     一个画家的名字，被劈成两半
remove   ← move  + re-     前缀碰巧对上，语义无关
repair   ← pair  + re-     同上
banner   ← ban   + -er     同上
retreat  ← treat + re-     同上

而这一档有 3741 条，占 A 级的 65%。词频筛不掉后四个——move、pair、 ban 都是常用词。要区分 remove ← move 和 revisit ← visit 需要语义判断，那正是 P1b 那次模型复核干的事，也正是为什么 10471 条里只有 4997 条有复核。

所以规则改成：只采信模型复核过的条目，C 级不显示，模型自己标了「需确认」的也不显示 （有 21 条，army ← arm + -y 是其中之一）。

文章 #79 里显示构词分解的词，从 13 个降到 6 个，全部正确：
  Archaeologists←archaeology   Naval←navy   Ninth←nine
  assignment←assign   historians←history   likelihood←likely
被滤掉的错条目：banner←ban   repair←pair   retreat←treat   army←arm

代价是 builder ← build、careful ← care 这些正确但未复核的也不显示了。 这个代价很小——这类词透明到根本不需要提示，构词提示真正值钱的地方是 likelihood、 archaeologist 这种，而它们恰好都复核过。

P0 验收清单改了一条

P0 的 3.2「两套接口分离」原本断言的是「/v1/client 下没有任何接口」， 那是一句阶段边界标记，P2 写下第一套客户端契约之后它到期了。 改成断言铁律 4 真正主张的性质：两套接口在各自前缀下，没有越界路径。 「客户端令牌碰不到管理接口」挪到 verify_phase2.py 去查——那里才有令牌。

改完重跑：P0 29 项全过，P1b 28 项全过，P1c 16 项全过。

人工验收当场抓出的两个记账错误

症状是「读了好几篇，复习中却只有 55 条」。查下去发现 55 这个数本身就是错的：

colony   义项0（未标注）×25  |  义项1 殖民地 ×30

colony 在一篇 430 词的文章里当然没出现 55 次。25 个目标词每个都记了两条。两个原因：

5标注完成前「读完」，产生幽灵行 那时 sense_id 还是 NULL，被 COALESCE 当成了 0—— 而 0 的含义是「这个词没有义项集」，两件事混淆了。修法是文章不到 ready 就拒绝记账， 也不标记为已读：只排除 NULL 不够，那样会把文章标成已读却什么都没记， 之后再读就被「只记一次」挡住，目标词永远丢失。
6重复「读完」反复累加遇见次数 点两次按钮、离线队列重放、脚本重跑，每次都把整篇的遇见次数再加一遍。 事件本身是幂等的（幂等键去重），但幂等的是事件，不是它的效果。 改成只在第一次记账——read_at 和 finished_at 本来就是一次性的， 账目跟它们对齐。真正的重读是 E6 旧文重读，属于 P8，到时会带自己的事件。

修完重建账目：colony 一条、5 次遇见，roman 两条 （文中确实用了「罗马人」和「罗马的」两个义项——那是义项级追踪该有的样子，不是重复）。

读真题几乎不产生复习条目，这是设计，但看不出来

「读了好几篇却只有几十条」的另一半原因跟 bug 无关：真题没有目标词。

C6 规定目标词是「每篇 25 个，全部来自 CET 词表」，那是生成文章时指定的。 真题是现成语料，没人指定过——所以读真题只会记下你手动标记的词， 附带词按 C6「只给释义，读完即止，不产生任何任务」。

这是对的：一篇 400 词的真题里大概有四十个你还没学的 CET 词，全部自动算作目标词就会冲垮队列， 而那正是 C6 设上限要防的事。但它读之前完全看不出来，所以文章列表和管理页都加了一列 目标词：生成文章显示 25，真题显示 0。读之前就知道这篇会不会记账。

什么东西有资格进账本 —— 试了两版，都推翻了

人工验收暴露出「读真题什么都不记」之后，做过两版自动记账，都被推翻，而推翻的理由一次比一次根本。

1真题自动挑 25 个词 按「在四六级词表内 + 还没学过 + 词频最高」挑。排序判据还写反了——按词频升序等于挑 say · as · go · get · up · day，那些早就会了。改成必须带 cet4／cet6 标签之后挑的是 political · president · nation · military，看起来对了。 但整条还是错的：那是在替你判断哪些词你需要学，也就是水平估计（P3），装在了 P2 里。
2生成文章的目标词自动入账 这版看起来站得住——文章确实是为教这 25 个词写的。但它仍然在替你断言 「读过 = 需要复习」。用户的话：不管真题还是生成文章，都不该在点击读完后自动加入待复习。

立下的规则：进复习队列只有两条路，都是你自己的信号。
你标记了（「我不会」），或者读后抽查答错了（D3，「你以为你会」）。两者都没有就不进。 读完一篇只增加遇见次数，不改变词池位置。

这跟 D1 原本的设计正好合上：抽查「专门针对未被标记的词，因为被标记的系统已经知道了」。 未标记的词由抽查兜底，而不是由系统假定你学会了或没学会。

代价要认，而且不小。主文档的覆盖率算法——「每篇 25 个目标词 × 289 篇 ≈ 3.2 个月覆盖 7226 词」—— 前提是读完一篇就算学了这 25 个。现在覆盖速度取决于你的标记率，不再是可预测的数。 换来的是账本里每一行都追得到你做过的一件事。验收 7.4 查的就是这条： 复习队列里的每一条都必须对应一次标记。

保留下来的是文章列表上的「目标词」一列，含义相应地窄了：它说的是 这篇为教哪些词而写（生成文 25、真题 0），不是「读完会记几个」。

问题：语境标注跑完真题后，漏义项报告里冒出 get up、known as、 at least——模型遇到它们时单词义项没一条贴得上，只能跳过。每篇约 7 处。 点 account 却不知道这句里是 account for，是点词查词的缺陷。

已达成的结论：

1不建「哪些词组值得学」的清单。 原打算对标义项集建一份，那是花了两个阶段、中间还推倒重来过一次的活儿。 一句话砍掉了它：「不认识词组的话，也没必要管他是不是考纲里的吧？」—— 这正是同一天立的规则：进复习队列只由你的标记决定。 「31.8 万条词组里只有 6 条带考纲标签」是策展的难题，而我们不策展。
2释义是现成的。ECDICT 源文件里有 36 万条多词条目， get up、account for 全带中文。P0 导入时一句 " " in headword 主动滤掉了。
3识别分两步，实测有效。 结构性（动词 + 小品词，且词典里有这个组合，不花钱，挡掉 to be the world 这类噪音，每篇从 43 处降到 6.8 处） + 逐处封闭判断（「在这句里是不是一个整体」，判据是透明度不是价值： 整体意思能不能从组成词看出来）。三组对照实测：真词组 10/10、字面 8–9/10、 噪音 8–9/10，而那几个「错」里有两个是测试标错了。
4标记词组之后要追问组成词。 「account for 肯定得认识 account……不能因为这个词组影响了对 account 的判断。」 不认识词组不代表不认识 account——让词组的标记替这个词背锅， 会把一个完全掌握的词塞进复习队列。

还没谈的（下次动手前必须先定）：数据怎么存（词组在标记表里怎么跟单词区分）、 已有的 95058 条标注要不要动、词典怎么导入（单独一张表还是并进 words）、 阅读页怎么显示（词组标记会不会盖掉目标词／派生词／超纲词的标记）。
