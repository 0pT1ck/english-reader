设置与验收

设置屏把前两个 Phase 欠下的出口一次给齐；然后三个 Phase 的验收一起还， 在 TestFlight 的真机上。

这个 Phase 的重心不在设置本身——设置是一屏 Form，画法上没有一件新东西。 重心是还债：P6 与 P7 一次验收都没跑过，两条验收断言已经到期，Swift 契约没重新生成， 两处菜单里写着「选项还没做」，还有一套 P3 做好、P5 实现、至今没人用过的拼写。 设置屏的作用是把这些欠账的出口安在同一个地方，然后一起上真机。 外加一条动了架构铁律 4 的决定：开发者选项里直接控制后台（§8）。

功能设计 English Reader ｜ 上一阶段 Phase 7

这是讨论稿。标「已定」的是用户 2026-09-15 当场拍板的， 标「拟定」的是我提的、等确认，标「不做」的是明确划出去的边界。

用户已拍板的：
① 这个 Phase 是设置 + 验收，把三个 Phase 欠的债一起验收掉；
② 设置里建一个「开发者选项」二级菜单，放日志、跳天、管理台的东西， 直接控制后台、不纠结分层（§8）；
③ 账号先做 UI 不做功能，将来是几个朋友各自登录、各拿各的数据； 登录用账号 + 密码，这个 Phase 只画不接（§3）；
④ 日志加等级、本地存 3 天自动清、可复制／分享／导出（§9）；
⑤ 三样不做：扫码配置、XCUITest 截图、verify_phase8.py；
⑥ 其余照清单做，等成品出来再决定删改。

讨论期间不写任何实现代码，包括脚手架和示例。本文档里出现的字段名、 函数名、端点都是已经存在的东西——要新写的只有 §11 那一处半。
§1

这个 Phase 装两件事

一件是画一屏，一件是把欠了两个 Phase 的账结掉。后者才是难的那件。

原本的顺序不是这样。主文档 §M 和 P6 §13 都写着 「设置那个 Phase 排在这次验收之后」——先验 P6 与 P7，通过了再做设置。 2026-09-15 改成三个一起验。

改动的代价要先认下来，因为它是同一笔账的第三次记名。 P5 没有人工验收（理由见 P5 §17），P6 与 P7 压到同一次真机验收， 现在 P8 也压进来。真机上第一次跑起来时，如果阅读那条链有结构性问题 （点词命中不准、面板高度不对、正文排版读着累），要改的就是三个 Phase， 而设置与复习已经架在阅读上面了。

为什么还是这么定：验收要动用别人的开发者账号，约人一次不容易； 设置屏又正好是「验收时你会想要的那些东西」的容器—— 看日志、跳天、清缓存、看待发条数，没有它，真机上出了问题只能干瞪眼。 先做设置再验收，比先验收再做设置更省一次约人。

缓解仍然只有那一条，必须守住：CI 上的四样——编得过、装得上、起得来、不闪退。

这个 Phase 一条学习逻辑都不新增。和 P7 一样，画的是已有的东西的样子； 不一样的是 P7 画的是 Core 里的规则，这一份画的大多是运维状态—— 缓存占了多少、有几条事件没发出去、上一次同步是什么结果。 这些东西在别的客户端上叫「设置」，在这个项目里其实是诊断通道： 管理控制台开在公网上、带着管理密码，不该为了查一条发不出去的标记去开它。

1拟定八个区的顺序照上图：账号、连接、阅读、今天的安排、存储、日志、开发者选项、关于。
排序的依据是用的频率倒过来——连接是装完第一次要填、之后再也不碰的东西，但它出问题时最要紧，所以靠上；朗读和字号是天天可能动的，反而不该占第一屏的位置（它们的主入口在阅读屏，见 §6）。

3拟定不做搜索、不做分组折叠、不做「恢复默认」。七个区，十几行，没有一样需要找。
§3

账号：只做壳，但要照将来真会用的样子画

2026-09-15 用户说了它将来是什么：「未来先给我的几个朋友拉过来测试， 他们登陆自己的账号拿自己的数据」。所以这不是装饰，是一个确定要做的功能的第一版外壳。

先看清楚：多用户离得有多远

比想象的近。数据层基本已经就绪，这不是巧合—— devices.learner_id 那一列是 P2 写契约那天专门加的， 迁移的注释原话是：「Adding real users later means giving this column real values and nothing else — no sideloaded client needs updating」。

那一块现在
属于人的表全都带 learner_id 了：study_marks、study_states、reading_progress、review_sessions、review_history、spelling_attempts、client_events。review_queue 靠 session_id 挂在 review_sessions 上，也是分得开的。
内容表文章、句子、义项、词族不带人——本来就该共享，一篇文章不属于谁。
身份由设备令牌推导，learner_for_device() 一个函数管着，路径里不出现人的编号。契约顶层回显 learner，客户端据此认出「这是别人的缓存」。
缺什么三样：① 没有 learners 表——learner_profile() 现在硬编码返回 name: "本人"；② 没有登录这回事（凭证只有设备令牌）；③ 每天备稿是按一个人算的，几个人各要各的今日包，生成成本按人数乘，或者改成共享文章池、各自记各自的进度。
第三样才是真问题，而且它不是界面问题。前两样是两天的活， 第三样要定的是「朋友们读的是同一批文章还是各读各的」—— 前者便宜、但目标词是按你的词池选的，对别人不一定合适； 后者对每个人都对，但每天的生成开销乘以人数。

这个 Phase 不碰它（铁律：当前 Phase 中发现的未来需求记进待办，不动手）。 但要记进主文档 §M，而且要记成上面这句话的样子—— 记成「以后做多用户」等于没记。

那么这个 Phase 画什么

比原先想的少。2026-09-15 改过一次：原本要做一张个人页， 上面放连续打卡天数——而那个数 P7 已经显示在复习主界面上了 （决定 6，ReviewScreen.swift 那句「你已经连续打卡了 N 天！」）。 再放一遍就是同一个数显示两处。

剩下的东西撑不起一张页：一个名字、一行「功能待开发」、一个点了说「还没做」的按钮—— 那是一张空页，而它还要占一次点击。所以账号不做二级页。

#状态决定
4已定账号就是设置顶上那一行，点不进去：头像占位、名字、下面一行小字「词汇量估计 · 功能待开发」。右边不带箭头——带箭头而点不动，比没有箭头更让人以为坏了。
5已定登录用账号 + 密码，这个 Phase 只画不接（2026-09-15 用户定）。位置在「连接」区，和「用设备令牌连接」并排——它们本来就是一件事的两种做法。
不画成邀请码：邀请码本质上还是手工发凭证，是现在这套令牌换个名字，将来要再改一次界面。账号密码是这件事最后的样子，一次画到位。点它说「还没做」（P6 决定 30 的办法）。
6拟定「用设备令牌连接」照旧留着，就在登录下面。这是目前唯一真能用的路——不留它，App 装上就是废的。
将来登录接上之后，这一条退进开发者选项（它那时才真正变成一个开发用的东西）。
7拟定「词汇量估计」显示「功能待开发」，而不是空着或者 0。这是 capabilities 头一次真的被客户端读——learner.level 恒为 null、capabilities.level_estimate 为 false，契约当初留这个标志位要区分的正是「没数据」和「没实现」，而至今没有任何客户端读过它。
8已定账号这一行不放任何统计数。连续天数在复习主界面上（P7 决定 6）；已读篇数与已标词数客户端自己数得出来，但会和服务端漂移（架构铁律 3：客户端存的一切都只是缓存）。
宁可这一行只有名字——一个会漂的数比没有数更坏，因为你会信它。
9不做注册、改密码、换头像、改昵称——不画。登录画一个就够撑起这个壳了；剩下那些每画一个，将来都是一个要对齐的空承诺。
名字这一行要说实话。服务端现在对谁都回 name: "本人"（写死在 learner_profile() 里）。所以它显示的确实是服务端给的值， 但它不是「你的名字」——它是「这台设备连着的那份学习记录」的名字。 等 learners 表建起来，这一行自己就对了，界面不用改。
§4

连接：补完那三件

现在这一区只有两个输入框和一个保存。填完对不对，要去别的屏撞一次才知道。 这一区将来会被 §3 的登录取代，所以这里补的是在那之前必须能用的那三件。

#状态决定
10拟定「测试连接」按钮。点了打一次 /v1/client/today（或更轻的 /reviews/calendar），当场回三种结果之一：通了并显示 learner.name、连不上、令牌不对（401）。
这三种必须分得开——现在的唯一校验是「URL 拼不拼得出来」，而令牌错和网络断在屏幕上长得一模一样，这正是坑 §6.7 那个形状。
11拟定「清除令牌」。Connection.clearToken() 早就写好了，没有出口。放在令牌那一行的二级页里，带一次确认——清掉之后要重新去管理台签发，那是个不便宜的动作。
清令牌不清缓存也不清发件箱：发件箱是客户端唯一独有的数据（P5 决定 8），换令牌不该把没发出去的标记一起扔了。
12不做扫码配置暂时不做（2026-09-15 用户定）。原本是：管理台签发时出一张二维码（地址 + 令牌），App 扫一下自动填好。
省下的是：后端一个二维码依赖，App 一个相机权限——这个 App 至今一个权限都不要，加第一个是有分量的事。
代价：令牌是只显示一次的随机长串，每次配置都得把它从电脑挪到手机上（自己发给自己，再粘贴）。验收当天反复清装会烦几次。
等真正的登录做出来，这件事自己就没了——那时要输的是账号密码，本来就是手打的东西。
§5

存储、缓存与发件箱

Core 里全写好了、测过了，界面一个出口都没有。这一节是给它们装出口。

三类本地数据（P5 决定 8）：发件箱是客户端唯一独有的， 元信息几百字节，正文缓存约 300 KB 一篇。 Cache.swift 的模块注释写着「缓存永不自动清理，读过没读过都留着， 直到学习者说否」——而「说否」这件事现在没有地方说。

#状态决定
13拟定缓存二级页：按篇列出来，显示每篇占多少，可以单篇清、也可以全清。bodySizes() / clearBodies() / clearAllBodies() 三个都是现成的。
清掉的是正文，元信息留着——所以清过的文章仍然显示标题和读到哪，点开重新拉。这是 Core 已经定好的语义，界面照搬，不要自己发明「删除文章」。
14拟定发件箱那一行升级成三样：待发条数、上一次同步的结果（SyncReport 的 landed／duplicates／rejected／offline，Core 早就返回了，至今没人显示过）、「立刻上报」按钮。
幂等键重复上报算正常而不是错误（契约里手写的那几条语义之一），所以「立刻上报」可以随便点，点十次和点一次一个结果——这一点要在界面上说出来，否则没人敢点第二次。
15拟定损坏的事件文件要有出口。Outbox.pending() 会把读不出来的文件名单独返回，discardDamaged() 负责扔掉它们——现在没有任何界面调它。
不给出口的后果是安静的：一条写坏的事件永远发不出去，待发数永远减不到零，而你不知道为什么。界面上要说清楚「扔掉它意味着那次标记没了」，然后让人自己决定。
16不做「全部下载」不做。P6 决定 31 当初把它列进了这个 Phase，现在看它是个误会：今日包本来就把当天三篇全文内联下来了（P4 决定 8，约 1 MB），离线形状已经成立。真正没下载的是往期文章和 452 篇真题的正文——那是几百 MB 的循环拉取，为一个「万一」。
代替它的是一行状态：「今天的内容已在本地」。这句话才是「全部下载」真正想回答的问题。
§6

阅读与朗读

这一区只有三个开关，而且其中最重要的那个不放在设置里。

#状态决定
17拟定正文字号的入口在阅读屏的 ··· 菜单里，不在设置页。调字号要看着正文调——在设置页上拖一个滑块，然后退出去看效果、不对再进来，这是把一个两秒的动作做成一分钟。
顺带把 P6 决定 17 那个空菜单填上了（见 §10）。值本身存在一处，设置页不重复放。
18拟定朗读口音可选：美音／英音。Speech.swift 现在写死 en-US。四六级听力两种口音都考，而改这一行的成本是零。
19拟定朗读语速可调。现在写死 DefaultSpeechRate × 0.9，注释说的理由是「单词单独念时默认语速偏快、听不清词尾」——那是针对单个词定的，整句朗读时它就偏慢了。给一个滑块，比在代码里猜一个数强。
20拟定「点词自动朗读」开关，默认关。点词面板弹出时直接念出来。默认关是因为在安静的地方它会把人吓一跳，而这个 App 大概率在图书馆和地铁上用。
21不做深色模式手动切换、字体选择、行距、页边距，全不做。深色跟随系统；后三样是阅读器的军备竞赛，而这个 App 的正文样式在 P6 定过一次、真机上还没验过——先让一种样子被真的读过，再谈可调。
§7

今天的安排：只读

每天几篇、新备的算几天、拼写开不开——显示，但不给改。

这三个值今日包里已经在发了（TodaySettings 的 fresh_days、 weight_decay、spelling_enabled，加上 today_article_count 决定的篇数）。接进界面是零成本的——数据已经在手机上。

为什么不给改，理由有两层。
第一层是铁律 4：改配置是管理接口的事，客户端令牌碰不到它。 要在 App 里改，就得新开一个 /v1/client/settings 的 PATCH， 带一份白名单——那是后端的真改动，不是接一根线。
第二层是值不值：「每天几篇」是你半年改一次的东西。 为它写一个客户端写接口，再为那个接口写一份验收，不如在管理台点一下。

而「想在手机上改」这个需求，§8 已经从另一条路满足了： 开发者选项里的「配置热改」能改任何一项运行参数，包括每天几篇。
于是这两节合起来的口径是：正常路径上只读，要改就进开发者选项—— 这正好也是这些参数该有的分量，它们不是偏好，是运行配置。
#状态决定
22拟定四个值只读显示，旁边一句「在管理控制台改」。不给改，但要让人看得见现在是多少——「今天怎么只有三篇」这个问题，不该靠翻文档回答。
23不做不新增 /v1/client/settings。写在这里是为了让下一次想做它的会话知道：不是没想到，是想过之后没做——而且 §8 之后更没必要了，见下。
§8

开发者选项：直接控制后台

2026-09-15 用户定：「无视铁律 4。直接做，可以控制后台。因为我们这是开发者选项」。 不再讨论分层，这一节只写放什么、怎么放最整洁。

后端一行都不用改。core/auth.py 的 require_admin 本来就接受 X-Admin-Secret 请求头，注释写的是 「命令行，以及 AI 直接查诊断时用」。
所以「非浏览器的客户端拿着 secret 直接调管理接口」这条路一直存在、一直被支持， 以前那个客户端是命令行，现在多一个手机。
#状态决定
24已定开发者选项是设置里的一个二级菜单，里面有日志、跳天、以及管理台的东西。
25已定原生控件，直接调管理接口，凭证是 X-Admin-Secret。不做内嵌网页——管理台的页面是给鼠标设计的（表格宽、按钮小），手机上点不动。
26拟定原生做五样，其余留一个「打开管理台」的网页入口兜底。
五样是验收和开发期天天要用的：① 跳天 +1／归零，并显示现在停在第几天；② 定时任务：状态与「立刻跑一次」；③ 配置热改：读全部、改单项；④ 服务端日志：按级别与 trace_id 查；⑤ 服务状态概览。
全是现成的 JSON 端点（/v1/admin/review/clock、/tasks、/config、/logs、/status），客户端只是画它们。
判据写死在这里，免得以后无限膨胀：只放验收与开发期天天要用的，别的一律去管理台。
27拟定管理密码进钥匙串，和设备令牌分开存、分开显示、分开清除。照 Connection 现在的规矩：永不回显，只给够认出「是哪一个」的那几位。

手机连哪台机器

2026-09-15 用户定：连阿里云那台开发期实例，数据的事不用纠结—— 「我们现在的两个备份的数据到正式上线都要清除的」。 所以验收期间在它上面产生的标记、读完、复习记录作废也无所谓， 部署文档那条「开发期实例上的记录全部作废」照旧成立，只是它不再是个需要绕开的麻烦。
