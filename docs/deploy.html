§2

镜像长什么样

两段式。构建段有 uv、编译链和轮子缓存，运行段只有解释器、虚拟环境和应用代码。 这个划分不是为了好看，是为了公网上那台机器里不该带着一套编译工具链。

1 依赖层与代码层分开 改一个 .py 不会重新下载 spaCy 那一堆轮子。
2 spaCy 模型在构建时装进去 它是从 GitHub releases 拉的 12 MB，是整条链上最容易在国内失败的一步—— 所以让它发生在有出网能力的那台机器上，绝不留到运行时。 用 URL 装而不是 spacy download：后者在构建时现解析版本，两次构建可能不一样。
3 非 root 运行 在家里的局域网上这是迂腐，在开着公网端口的机器上这是「处理函数里的 bug」 和「以 root 身份运行的处理函数里的 bug」之间的差别。
4 数据库只在挂载卷上，绝不进镜像 重建或升级容器不许碰到学习记录。
5 uvicorn 直接起，不走 run.py 那个启动器的存在意义是给双击 .bat 的人开浏览器、打印中文提示， 这里一条都不适用。加 --proxy-headers，让应用看见真实客户端地址和协议。
§3

第一次真的构建它，撞出三个静默失败

每一个都不报错

P0 写下这份 Dockerfile 时，部署验证被明确推迟了。所以这是它第一次被执行。 三个问题的共同形状是：没有任何东西出错，只是事情被做错了。

1 容器默认 UTC，而这个项目读的是本地时钟 core/tasks.py:204 把 "04:00" 当成机器所在地的凌晨四点， 复习的「当天」也按本地零点切。容器留在 UTC 的话，夜间备稿会在中午跑，日界提前八小时—— 全程零报错、零日志。镜像里写死 TZ=Asia/Shanghai。
2 绑定挂载按 uid 数字比对，不按用户名 容器用户的 uid 和宿主机目录的属主对不上，启动即 PermissionError， 报错里没有一个字提到权限模型。做成 ER_UID/ER_GID 可覆盖， 并把 HOME 设到可写位置——被覆盖成一个 /etc/passwd 里没有的 uid 时， HOME 会是空的，然后某个要缓存目录的库以很难看懂的方式失败。
3 不设管理密码，容器直接崩，而报错跟密码无关 应用会生成一个密码并追加进 /app/.env——那个文件在镜像里不存在， 目录属于 root，于是进程带着一段 PermissionError 栈死掉。 compose 里用 ${VAR:?一句人话} 提前拦住。
这三个都是「跑一次」才看得见的。读代码看不出来， 因为代码在它自己的假设下是对的——错的是假设，而假设不写在代码里。
§4

三个容器怎么摆

按用户的惯例：/opt/appdata 下一个服务一个文件夹， compose 文件在里面，数据目录并排放。

/opt/appdata/
├── cloudflared/          出站隧道，当前的入口
│   ├── docker-compose.yml
│   └── .env                 TUNNEL_TOKEN
├── caddy/                宿主机公共反代，等备案
│   ├── docker-compose.yml
│   ├── Dockerfile.caddy     自编，带 alidns 插件
│   ├── Caddyfile            一个站点一段
│   ├── .env                 域名、ACME 邮箱、DNS 密钥
│   └── data/ config/        证书

三者靠一个共享的 Docker 网络 proxy 连起来， docker network create proxy 每台机器建一次， 各 stack 都声明 external: true——谁先起谁后起都无所谓。

手机 ──HTTPS──▶ Cloudflare ──隧道(出站)──▶ [cloudflared]
                                              │ proxy 网络
                                              ▼
                                        [english-reader:8000]
                                              ▲
                      [caddy] ────────────────┘   （8443，等备案）

app 容器一个端口都不发布（expose 而不是 ports）， 实测 NetworkSettings.Ports 是 {"8000/tcp":null}。 这条要守住：publish 出去就等于把整个 API、连同管理接口，用明文挂在公网 IP 上。

Caddy 为什么要自己编

官方镜像没有 DNS 插件，而未备案时证书只能走 DNS-01 （HTTP-01 要 80、TLS-ALPN-01 要 443，两个都不可达）。 所以拿官方的 caddy:2.10-builder 编一个带 alidns 的二进制， 再塞进官方的 caddy:2.10-alpine。两段都是官方镜像，只是多编译了一个插件。

它为什么不在仓库里

Caddy 现在是宿主机的公共入口，将来别的服务也挂它。 放进这个仓库就等于让本项目拥有整台机器的入口，下一个服务要加站点得来改这个仓库。 代价说清楚：那三十来行不在版本控制里，重装服务器要重写。

§5

在那台机器上构建，三条取包的路都要换

73 KB/s → 496 秒

第一次构建跑了五十分钟只拉到 220 MB。问题不在镜像源，在守护进程。

1别给那台的 Docker 守护进程配代理。 BuildKit 会把守护进程的代理注入每一个构建步骤， 而那台的 mihomo 只有 73 KB/s。装依赖要几个小时。 去掉代理、改用国内源之后，同一层 496 秒装完。
2docker.io 要配镜像源，而且要能用的那种。 机器上原有的 docker.xuanyuan.me 会 403 限流， 而且不回落到官方源——整个构建当场失败，错误信息是那家的广告。 换成别的之后 python:3.12-slim 17.5 秒拉完。
3宿主机连得上，不等于容器里连得上。 github.com 在宿主机上有 484 KB/s，在容器里是 000（完全不通）。 我先在宿主机上量了速度、判断「直连就行」，然后构建在那一步失败。 判断某条路行不行，要在 docker run 里判。
要什么换成怎么传
Python 包mirrors.aliyun.comPYPI_INDEX
Go 模块（编 Caddy）goproxy.cnGOPROXY
spaCy 模型ghfast.top 前缀SPACY_MODEL_URL

三个都是 Dockerfile 里的参数，默认仍是官方源—— 仓库里的默认值不要改，换源是那台机器的事。 实际用的命令存在服务器上 /root/build-er.sh 和 /root/build-caddy.sh， 重建照着跑，不用重新想。

一个和本项目无关但值得记的坑：pkill -f <模式> 会杀掉你自己那条命令。 ssh host 'pkill -f "X"' 的远端 shell，命令行里就含着 X，于是它匹配到自己， 后半截脚本静默地不执行，看起来像 ssh 断了。一小时里栽了三次， 第三次是换成 pgrep 之后还栽。正确做法是先取 PID 再按 PID 杀。
§6

备案：一个被实测推翻的判断

这一节是这次最重要的发现

动手前我判断：「未备案只挡 80/443，高端口不在封禁范围， 所以 HTTPS 开在 8443 就能用。」这个判断是错的。

直连在 https://reader.cntick.top:8443 上确实跑通了—— 证书签发成功，从公网取 /health 返回 200，管理台、客户端接口、安全响应头全部正常。 四十分钟后，同样的请求全部失败。

怎么确定是备案拦截，而不是别的

一开始的几个判断都不成立，值得记下来：

×不是安全组。 端口通着，明文 HTTP 打 8443 拿得到 Caddy 的 400。
×不是 MTU 黑洞。 曾经很像：小包过得去、TLS 握手的大包过不去，而客户端侧量到路径 MTU 只有 1488。 但服务器出方向 1472 带 DF 通、5 MB 的 TLS 下载正常。
×不是 Caddy。 它的日志从证书签发之后再没有任何连接记录——请求根本没到它那里。
×「换个 SNI 也失败」这个对照不成立。 我用 SNI=example.com 做对照，也失败，于是一度以为「不是按域名掐的」。 但 Caddy 只配了一个站点，对陌生 SNI 本来就会中断握手—— 这个测试分不出两种情况，等于没测。

决定性的那一个测试

对同一个 IP、同一个端口做两次 TLS 握手，唯一的差别是带不带 SNI：

握手结果说明
不带 SNI有字节回来 Caddy 回 fatal internal_error：没有 SNI 它挑不了证书
带 reader.cntick.top一个字节都没有 连接静默中断，服务端毫无察觉
明文 HTTP，同端口400Caddy 应答的

同一条路、同一个端口，只有带那个域名 SNI 的 TLS 被中途丢弃。 这是决定性的：端口是通的、Caddy 是好的、MTU 是好的、TLS 本身是通的—— 被识别并处理掉的就是那个域名。

要记住的不只是结论，还有方法。 「换个 SNI 也失败」和「不带 SNI 有回应」看起来是同一类测试， 前者分不出两种情况，后者分得出。判断一个测试有没有用，问的不是「它报不报错」， 而是「它区分得开吗」。
