词组与用法

词组识别只认得出三分之一，认出来的没有释义。而查下去发现 一多半根本不是词组，是某个义项的用法——柯林斯早就把这两件事分开了， 我们一件都没做。这个 Phase 两件一起做。

最要紧的一条是「什么算词组」不再由我们写的词性规则决定， 而是照一张现成的考纲短语表查表——P10 那一手的同一个形状： 义项集当年也想让模型重建，粒度控制不住，最后是直接导柯林斯，模型调用从 14,500 次降到 0。
这份文档里所有的数都是 2026-09-21 在当前语料（498 篇）上现场量的， 不是从 P2 §18 抄来的——那批数量于 2026-09-07/09，前提已经变了三样（§2）。

§7b

填 0 的意思是「这一处不是词组」

2026-09-21，用户问了一句 「run into 是跑进的时候，这个算固定搭配还是 into 的用法？」 ——答案是后者，而它纠正了我前一条的一个错误建议。

我原本提议「给每个词组补一条字面义」，因为柯林斯的 run into 只有四条 （遇到问题／意外碰到／车辆撞上／费用高达），没有「跑进」， 于是 He ran into the room 那一处对不上任何一条。 那个提议是错的：字面用法不是 run into 的一个意思，那里根本没有 run into。

一介词换得掉，就说明它属于后面那个名词短语 ran into / out of / across / toward the room 都成立，意思跟着空间关系变； 而 ran into an old friend 的 into 换不得。
二回答得了「在哪」，就说明它是地点状语 Where did he run? → into the room ✓；→ into an old friend ✗。

所以正确的语义是：标注器填 0 ＝ 这一处不是词组。 不整体渲染，run 和 into 各自显示自己的义项——它们本来就各自标注过。
而这把我们以为放弃了的东西白送了回来：「这一处算不算词组」的判定 成了义项标注的副产品。不用单独问，问「是哪个意思」时，「都不是」这个答案就是它。

§11

契约怎么改，以及「必须最新版本」怎么落地

2026-09-22

契约是服务端和客户端之间说话的格式：一篇文章下发时长什么样、 每个词带哪些信息、复习卡片有哪几栏。这一节是这个 Phase 要动它的全部清单。

⑱ 把这一节的前提换掉了。原来的规矩是架构铁律 7 「只增不减、不改字段含义」，理由是侧载安装的客户端更新滞后。 用户 2026-09-22 说那条前提不成立：「那个铁律是 ai 瞎写的。 我们现在要求客户端必须是最新版本。」于是下面第三、第四类才做得成—— 在旧规矩下它们要么开 /v2/，要么写一条记名放宽。
但别把 ⑱ 读成「契约随便改」：铁律 5（内容 id 不许变）没跟着塌， 它靠的是另一个理由，见方框 ⑱ 最后一段。

一、加字段：文章里的词组块

现在下发的一个词组只有一行中文（translation）， ③ 定了词组要带着义项走，所以要加四样：

加什么装什么为什么非有不可
phrase_id词组表发的号 设备上的标记从此指着它，所以一旦发出去不许变（铁律 5）
senses这个词组的几条义项，各自带 id 和中文 account for：占比例／解释／对…负责。点开照旧全列（③）
sense_id这一处是哪一条，标注器填的 填 0 ＝ 这一处不是词组（§7b）：He ran into the room 不整体渲染，run 和 into 各显示各的
marks / states改成按义项分 从「你标过这个词组」变成「你标过它的『解释』那条」。 单词那边本来就是这个形状，词组抄过来

二、加字段：义项上的搭配（用法）

两处各加一个字段：文章里点词看到的那份，和复习揭晓屏那份 （review/contract.py 的 WordSense）。 ⑰ 的全部实现就是这一条——数据备好、下发得出去，复习逻辑一个字不动。

还要在响应顶层的 capabilities 里加声明位。 那个角落回答的是「这里是空的，因为没数据，还是因为服务端还没实现」； 现在只有一个 phrases，词组义项与搭配各需要一个， 否则客户端分不清「这个词组没有义项」和「服务端还没导」。

三、删字段：translation 与 definition

词组那一行中文。⑱ 之前的写法是留着它、填第一条义项的中文， 理由是老客户端还在读；那个理由没了，就直接删—— 留着就是两份中文各存一处，而两份必然漂移。少一处会说谎的地方。

四、改含义：ReviewItem.sense_id

它的说明现在写着「词组恒为 0——词组不是别的东西的一个义项」。 ③ 一落地这句就不成立：词组有自己的义项，它装的是义项 id。 三条同时成立，所以这一改的代价是可以算清的：

1读者只有我们自己的 Core。P9 之后服务端不再下发复习包， 复习卡片是设备自己拼的，而 Core 跟 App 一起发版
2这个 Phase 里只有 ercli 会产生词组记录。 界面初版不认词组（P6 §7 那笔账还没还），手机上标不了
3没有老数据指着旧含义。实测 study_marks 与 study_states 都是空的

五、只改说明，不改行为：Token.in_phrase

它现在的说明是「这个词是词组的一部分，所以它自己的释义是在不知情的情况下标的、不可信」—— 那是 P2 时代的话，当时标注器不知道词组存在。这个 Phase 之后它的意思变成 「标注器确认了这一处是词组的一部分」。客户端行为一个字不用改 （Display.swift 写死：词落在词组里就显示词组的意思）， 变的只是理由——从「警告：这条标注不可信」变成「确认：这里该看词组」。

六、版本握手（⑲）

要比的是契约版本，不是 App 的 build 号。这两个是不同的东西： build 号只有 App 知道、ercli 根本没有； 而读写字段这件事发生在 Core 里（契约类型是 ERContract，解码也在 Core）， 所以要问的是「这份客户端说的是契约的哪一版」。 一个整数，跟着 client/openapi.json 走， 每次发生「客户端必须跟上」的变更就 +1。App 的 build 号可以另外附上， 但那是诊断用的（日志里好认是哪台设备），不参与放行判断，归 host。

1 Core 每个请求带上 X-Contract-Version 归 Core 不归 host，判据是 Transport.swift:25： 令牌是 host 知道的事，版本是 Core 自己知道的事。一处写死， App 与 ercli 同时就对了
2 服务端一条配置项 min_contract_version，只拦 /v1/client/… 低于它就回 HTTP 426 Upgrade Required ＋ 一句中文， 客户端照着显示「请更新 App」
3 Core 专门认出 426，不当成普通网络错误 当成普通错误就会一直重试、一直转圈（P9 §17 那个症状的形状）。 正确的行为是停掉同步、把「该更新了」报给 host 显示， 而发件箱里攒着的事件一条都不许丢——更新完照样要上报

三个坑，不写死照样会栽：

一老客户端根本不发这个头。 服务端看到「没有这个头」必须当成最老，不能当成「未知、放行」—— 否则最该拦的那个正好绕过去了
二发版顺序：先发客户端，再拧服务端的最低版本。 反过来就是自己把自己锁在外面——手机连不上， 而唯一能改这个设置的开发者选项也在手机上
三管理接口和 /health 不拦。 开发者选项走的是另一把凭证（铁律 6 那条记名例外）， 而版本太老正是最想用它来诊断的时候

验法两条，所以这条规矩不是一句愿望 （架构铁律开头那句）：带老版本号的请求拿不到今日包；不带这个头的请求同样拿不到。

一、B 档不干净，而**抽样看不出来、对照一次就看出来了**

㉑ 第一次跑，30 条阳性对照错了 6 条。查下去：六条全是模型对的， 错的是我的对照——B 档里混着两种块：

碎片as far as ＋ is concerned 是一个词组被分段加粗，所以 as far as 只是半个 （for all ＋ are worth、as if ＋ own the place 同理）
合住beside yourself with ／ beside the point 是两个词组挤在一块， 而那一块的中文「非常；极度」只描述前者

两种都会让读者点开看到**不是这个词组的中文**，正是这个项目最怕的错。 §13 抽样 14 条全对，没看出任何一种；对照跑一次就照出来了。 规则因此细分出 B* 档：一个加粗串只有在它是那块加粗的全部时才算干净， 否则交给判定。改完对照 29/30 ＋ 30/30，而 B* 实际判下来 360 对 18—— 它确实很干净，但那是判完才知道的。

二、表名撞车：phrases 两个库里各有一张

ECDICT 在 dictionary.db 里本来就有一张 phrases（31.8 万行）， 而每个连接都挂着所有库——不带库名的 phrases 解析到哪一张， 取决于连接是从哪个库开的。已改名 phrase_list。

判定脚本崩的那一次正是撞上它，而且是最能说明问题的形式：那个进程在改名之前 启动，跑的是旧代码 SELECT ... FROM phrases，改名之后这条语句 解析到了 ECDICT 那张表，报的是「no such column: text」—— 一个听起来像「表结构错了」的错，实际是「读错表了」。

三、单义词组不能预填

标注器对单词有条捷径：只有一个义项就直接填，不问模型。对词组不成立—— 词组的第一个问题是「它在这儿到底算不算一个词组」。实测： talk about 在柯林斯里只有「这才叫…；真是」（Talk about lucky!）一条， 于是预填把语料里每一句平常的 talked about 都标成了那个意思。 不报错，全错。取消这条捷径之后它正确地判成了「这一处不是词组」。

四、一个不存在的类别名，让判断静默失效

扫描器里写着 BREAKING_KINDS = frozenset({"punct"})—— 而这个项目里标点的 kind 叫 nonword（ingest._classify）。 于是「跨标点就断开」这个判断永远不成立，语料里抓出了 at - home、 talked about . 这种跨逗号跨破折号的 span。 一个永远不等于任何东西的名字不会报错，只会让判断静默失效—— 坑 §6.7「分不出两种情况的断言等于没有断言」的同一族。改成正面列举 {"content","function","proper"}，4,309 → 4,219 处。
