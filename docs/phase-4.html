§1

这个 Phase 是怎么来的

2026-09-11 盘了一遍主文档，问的是「还有什么基石缺着，能不能开手机端」。

盘出来的结论是：先做手机端会撞上一个循环。P3 当时把两项人工验收推迟，理由是 「管理页上坐三天量出来的是凑合跑的体感，要等手机上每天真的在用」。 但现在就做出手机端，它每天也用不起来——生成文 2 篇、没有每日生成、没有今日包。 它能提供的就是「452 篇真题里自己挑一篇 + 卡片复习」，跟 Web 测试页是同一个形状，只是换了块屏幕。 用它量出来的仍然是凑合跑的体感，循环没解开。

所以 P4 排在手机端前面：把内容供给和今日包补上，手机端拿到的才是一个每天真能用的后端。 （那两项人工验收本身已于 2026-09-11 处理：D「真跑三到五天」撤销，E「句子质量抽验」保留，见 §8。）

所以先补供给与今日包，再做手机端。补完之后，手机端开工时后端已经是终局形状。

同一次盘点还清掉了两组设计：读后抽查（原 §D 三项）连同 A4 假性认识修正、A5 隐式信号采集 （归档 §F），以及 E2 双通道复习（归档 §G）。两组清掉的理由是同一条原则—— 这个系统的一切都建立在你自己的标记上，系统不替你查证、不替你猜、也不替你安排文章里的复现。 清掉之后 P4 的范围反而清楚了：它只管把内容备好、打包、送到，不碰任何「判断你会不会」的事。

§2

定下来的十九条

一行一条，钉住

照 P3 的规矩，讨论的结论先在这里列全，后面各节只是展开。

#决定
1不做文章复习通道。E2 双通道已从主文档移出（归档 §G）。依据是实测：库里有 due_at 的词一共 11 条，未来五天到期分布 3/2/1/1/1，而文章通道要的是每篇 15–18 个复习词位——做出来也只能塞一两个词，验不出它唯一值得验的两件事（语境复习是否真的更好、硬塞会不会把文章写怪）。「在新语境里再碰一次」这个诉求由 P3 的句子池接走了。
2每天备 3 篇。一次生成一篇，当场校验，够 3 篇为止。串行，不并发，也不批量攒着挑——挑是 §B3 的过量生成择优，不在本 Phase（见 §6）。
3生成上限 12 次，是熔断不是配额。一篇一篇生成到够 3 篇为止，正常情况下用不着关心上限——它防的是链路坏掉之后的无出口循环（模型被换、提示词写坏、大纲规则出 bug，合格率掉到 0）。这也是「后台任务与等待」那条规矩：等待循环必须有超时上限。
12 这个数是算出来的：实测合格率 60–80%，凑够 3 篇的期望次数是 3.8–5.0；上限 12 时「正常情况却凑不够」的概率在 0.3% 以下（上限 8 是 1.1–5.0%，一个月误报一两次——报警一旦开始误报就没人看了，而 Bark 这条链路是夜间任务唯一的出口）。碰到上限：停、Bark 报一条、当天有几篇算几篇。
4合格线（拦下）三条：超纲率 ≤ 1%、目标词命中 ≥ 20/25、每段至少 1 个目标词。判据全部来自已有的 checker，查表，零模型调用。
5篇长与均句长只记录、不拦下。实测篇长 413–521 词，按 §I 的区间卡会刷掉全部（四级）或大半（六级），而它们在要紧的判据上全是好的。写长了点不等于不能用。超出 ±15% 记一条日志。
均句长同样不拦，理由不同：2026-09-11 的三方对照里，两个候选模型的均句长都是 15.8（gpt-5.5 15.8 / deepseek 关思考 15.9），拦了两个一起挂，它区分不出好坏。它对 §I 的 23 差着三成，那是归档 §B 已经认下的那笔账——密度提三倍换句法降级，当时选了密度。要翻这笔账得回去改密度，不是在合格线上拦。
6目标词排除已经在学的。pick_target_words 的 exclude 参数一直存在、从来没有调用方填过——填上 study_states 里不在 new 格的词。不接的话，每天备的文章会拿你正在复习的词当新词教。
7同一天的三篇之间目标词互斥，避免三篇教同一批词。
8新增 GET /v1/client/today，内联全文。实测一篇约 300 KB，三篇不到 1 MB。清单式的话联不上网就只剩清单，那就不叫今日包了。/library、/articles/{id}、/reviews 全部保留不动（铁律 5 只增不减）。
9今日包不装真题。真题走专门入口 /library?source=cet4|cet6|kaoyan（P2 已有）。推论要写进契约文档：今日包 ≠ 今天的全部内容，否则写手机端客户端时会以为拿了今日包就够了。
10兜底生成默认 04:00，控制台可改。
11三层保险一次做齐（主文档 §H）：读完即补（订阅 article.finished，库存低于下限就补一篇）、定时兜底、管理台手动触发。补库存走订阅事件接入，不改阅读那条流程（铁律 6）。
12复习作答新增批量端点，带客户端生成的幂等键；单条端点保留不动。选新增而不是给老端点加字段，因为契约只增不减，焊进去就改不了，新增端点将来还能再加。
13任务状态入 learning.db，不入 logs.db——后者 30 天轮转，会把「下次该跑的时间」清掉，症状是静默停摆。
14定时任务不引第三方依赖，进程内 asyncio 循环，两种周期够用：每天某时某分、每若干分钟。不引 cron 表达式，不引 APScheduler——这点需求不值一个依赖，也不值一次跨平台的坑。
15reading_fresh_days 保持 3 天。每天三篇的话货架上稳定在九篇上下，正是 B9 要的「打开就是十几篇、一眼能挑完」。（按每天八到十篇时曾考虑改成 1 天，前提没了。）
16加餐改成朴素版：还想读就再多给一篇。原本「装次日到期的复习词、今天多读明天就轻」的性质随 E2 走了。
17选文规则关在一个函数里，每次决策入决策日志。它是明知临时的规则——没有水平估计，只能按「新备未读优先」排。§A 将来上线要换，换的时候只换那一处。
18写文章继续用 gpt-5.5；deepseek-flash 关掉思考后作为已验证的备选。2026-09-11 三方配对实测（同样 10 个种子、同样的目标词，见 §4）：两者合格率打平 8/10，超纲、均句长、最长句全部持平，只差目标词命中（24.4 对 22.3），而 deepseek 快 8.5 倍。
不换的理由是省下的时间不值那两个词：大头在标注（两边都是 5 分钟），换模型只把每天 10.5 分钟压到 6 分钟，而那是凌晨四点没人等的四分半。
备选要留着且已经验过：中转站额度断了、每天篇数要往上加、或者充值不及时，直接切。切的时候必须两件一起做——关思考 ＋ 给足预算。只换模型不关思考是 5/10 加 61 秒，比现在更糟。这条反直觉，最容易只做一半。
顺带订正：deepseek-v4.1-flash 这个名字在中转站上是 MODEL_NOT_AVAILABLE，因为 DeepSeek 官方已把名字改成不带版本不带日期的 deepseek-flash，中转站跟着改了。主文档 §M 那条「等中转站放开」要跟着改。
2026-09-16：这条不再是现状。中转站与 ShuaiAPI 当天双双断供，写文章改用 gemini-3.8-flash-high（自建网关，免费），并为它改了提示词——见 §4 末尾「中转站断供之后换 gemini」。那里有两条与本条相反的事实：关思考对 gemini 无效（网关忽略该字段），以及模型换了之后合格率主要由提示词决定——同一个模型 0/10 与 7/10 的差别全在提示词上。
19每一个用模型的地方各有自己的开关：一个提供商，一个思考开关。现在 9 个 worker 里只有 3 个有自己的提供商配置项（gen_provider、review_gen_provider、annotate_provider——而最后一个是空的），其余 6 个硬落到「默认提供商」；思考开关则一个都没有，client.complete() 根本不接受这个参数。
做法：Worker 按 kind 自动登记两个配置项（提供商、思考三态），管理台「模型」页一页列全；现有那三个键走版本化迁移搬过去，不丢已有设置。这条是铁律 6「参数一律配置化、新模块一处登记自动挂载」的直接应用。
但默认值只改写文章那一处。关思考的实测只覆盖 generate_article；另外 8 处（标注、造句、判词组、义项集、词族）关掉会怎样没有测过，默认一律保持现状（不发这个字段）。要改哪一处，先在那一处拿数说话——坑 §2.4 记的就是把「写文章」和「造例句」的横评结论搞混那次。
§3

A · 框架能力

决定 10、13、14、19

一 · 定时任务

排第一是因为 B 和 C 都踩在它上面：项目现在根本没有「定时任务」这个位。

core/registry.py 的 Module 规格里只有 migrations、两个 router、admin_pages、 subscriptions、on_startup。§H 写的「读完即刻生成 → 固定时间兜底 → 控制台手动触发」三层保险， 第二层无处可挂。

1给 Module 加一栏 tasks——模块自己声明任务名、标题、周期、handler、开关配置项。按铁律 6，新模块登记一次自动挂载，不改调度器。
2调度循环跑在进程内，每分钟醒一次，比对 task_runs 表。选进程内而不是 Windows 计划任务，是为了开发期与将来 Docker 走同一条路。
3新表 task_runs：上次跑、结果、耗时、trace_id、下次该跑。重启不漏跑也不重复跑是它的唯一职责。
4管理台「任务」页：注册了哪些、上次结果、下次时间、手动触发按钮、单个开关。
5失败走 Bark（core/notifications.py 的注释里写的就是夜间生成这个场景），带去重。2026-09-11 已启用并确认手机收得到——决定 3 的熔断报警、任务失败通知全靠它。

1按 kind 自动登记两个配置项：提供商（空＝用默认）、思考三态（跟随模型／强制开／强制关）。新加一个 worker 就自动多两个开关，不用记得去补——铁律 6。

5默认值只改写文章那一处。其余 8 处关思考会怎样没测过，一律保持现状。要改哪一处，先在那一处拿数说话。
§4

B · 每日供给

决定 2–7、11、18

后半段其实已经全自动了。缺的只有两件：谁按第一颗按钮，谁替你看那一眼。

现在的链路是 生成 → 你人眼看 → 点入库 → 自动标注 → ready。 ingest_draft 之后 annotate 自动跑，每批之后调 finalise_if_annotated 翻 ready， 连词组扫描都顺带做了。人只在中间那一步。

替你看的那一眼

判据不用新造。checker 是 P1 就实现的东西（§B2 本地校验），每篇草稿的这些数它已经算好了， 现在只是显示给你看：超纲率、目标词命中、每段落了几个、篇长、均句长、句法频率对基线。 所谓合格线，就是给其中三个定阈值，让机器替你做那个「能用／不能用」的判断。

而 §B2 的原文本来就写着这件事：「……算出超纲词清单、目标词命中率、按当前水平预测的真实生词率。 不达标的做定点改写，或直接丢弃。」所以它不是新功能，是把已经算好的数接到一个已经写在设计里的动作上。

它和 §B3「过量生成择优」不是一回事，虽然字面像。 B3 的判据是让模型逐句判搭配、零 flag 的才留（每句一次调用）；这里的判据是查表。 择优不在本 Phase。

三条结论：

① 关掉思维链不降质量，是提质量：5/10 → 8/10，超纲降一半，句子还长了 2.8 个词。 思维链在这个任务上只买到目标词命中（24.5 对 22.3，而且极稳：开思考十篇全在 24–25）， 赔掉的是超纲——它推敲怎么把 25 个词都塞进去，塞的过程中顺手拽了纲外的词。

② 合格率主要由题目决定，不由模型决定：十个种子里六个至少挂了一家，只有四个三家全过。 这一条直接作废了先前那个 11/11——那是 generation_drafts 里旧草稿攒的， 每篇题目各自随机，比不得。同一批种子下 gpt-5.5 是 8/10。

③ 失败模式不一样：gpt-5.5 从没在命中线上出过事（最低 23/25）； deepseek 关思考有一篇 18/25 直接挂、一篇 20/25 压线过。换过去等于把一部分失败从「超纲」挪到「命中」。

仍然要打的折：10 个种子不算多，而且都是同一套提示词、同一个学习等级。 上线后头两周盯 llm_jobs 的丢弃率，实际值偏离这三行太多就回来改决定 3 的上限。

2026-09-16：中转站断供之后换 gemini，连带把提示词改了

决定 18 那套分工在 2026-09-15 当天全断了：基元律动余额不足（四个 key 是同一个账户，换 provider 换不出余额）， ShuaiAPI 通道不可用。用户另配了一条免费的路——gemini-3.8-flash-high， 自建网关 gcli2api 转 OpenAI 协议。这一节是它的横评，以及由此逼出来的提示词改版。

方法照搬上面那一轮：同样 10 个种子、同样的目标词、同样的合格线，一样跑 pipeline.write_one。 先做了阴性对照——在跑 gemini 的那台机器上重算历史草稿的超纲率（0.73→0.73、1.36→1.36、 5.08→5.08），逐位复现，所以量出来的差别不是环境差别。 两台机器同一个 seed 给出的目标词与话题也逐字对过，跨机比对成立。

也就是说它不是乱蹦词，是默认按六级／考研的笔调写，抽象名词随手就来。均句长 18.7 对 15.8，同向印证。 seed 1 与 seed 2 做过同题头对头：gemini 2.67% / 6.04%，gpt-5.5 在同一话题下 0.00% / 0.44%—— 不是话题刁钻，是模型。（gpt-5.5 只跑得了两篇，ShuaiAPI 那点余额当场用光。）

提示词：讲考纲的名字，不要讲词数

原来那句是「限制在最常见的约 4000 个英语单词以内」。这正是坑 §1.1 的形状—— 词数是模型算不出来的东西，它只能大概比划。而「六级词」「考研词」是它知道的类别： 它写 mechanism、municipal、rigorous 不是不守规矩， 是感觉不到这些词难，直到你告诉它这些词属于哪一级。

五版，每版同样的种子，仓库代码一行没动（变体是在一次性脚本里 patch build_prompt 的返回值）：

版本加了什么超纲中位合格命中
原版「最常见的约 4000 个词以内」5.82%0 / 1023.7
v1讲考纲：四级大纲以内，六级／考研／雅思托福 GRE 才学的词一个不用2.12%※1 / 423.2

※ v1–v3 是 4 个种子的初筛，噪声大（同一版同一种子两次跑能差 0.4 个百分点），只用来排序，不当结论。

三段是互补的，不是同一句话说三遍：2.12 / 3.28 / 3.67 各自单独，合起来 0.88。 v5 那一段是为了压住前四段压不掉的那一类——抽象词没了之后，剩下的越界词全变成 storehouse、smokestack、townspeople 这种复合名词， 而「必须写具体的事」是另一条硬要求（§B 内容要求）。所以那一段给的是出口而不是禁令： 照旧写具体的人和事，只把名字换成常见词组成的说法。不这么写，模型会靠写空泛来守规矩。

没有把命中率赔进去：24.1 对原版的 23.7，比 deepseek-flash 关思考的 22.3 还高。 十篇里有三篇 0.00%。

落地在 prompts.py 的 _ceiling_block()，PROMPT_VERSION 升到 p1b-2。 按 allowed_tiers 参数化，将来把系统对准六级时这段话会自己改口； 越界词对照表和具体名词那两段的例词全是四级的越界词，只在四级这一档给出，换等级要重新测一批。

要打的折，三条： ① 只在 gemini 上验过，gpt-5.5 在新提示词下没测（额度当场用光），所以「新提示词对所有模型都更好」是推的不是测的； ② 10 个种子仍然不算多，而单种子的波动能到 0.4 个百分点； ③ 合格率 7/10 落在决定 3 算 gen_daily_attempt_cap 时假定的 60–80% 区间内，上限 12 不用动。

顺带查出一个 checker 的假阳性

v4 那一轮里有三篇的「超纲词」是 vance（虚构人名 Dr. Vance，后文单用时 spaCy 不再标成专名）、 boer / dutch（民族名，Dutch 被标成形容词）、c（vitamin C）。 checker 本来会跳过 PROPN，这几种漏了。剔掉它们，v4 实际是 7/10 而不是 5/10。

度量没有动。发现噪声就顺手改宽算法，正是坑 §1.2 的反面——那样量出来的好看数字谁也不知道是真的还是算法让的。 记在这里，要不要修是独立的一件事，它影响的是所有模型的评分。

每天的代价

步骤次数耗时输入 token
生成（串行，一次一篇，gpt-5.5）~4.3~5.4 分钟~22k
标注（每篇 5 批，并发 3）3~5 分钟~51k

生成次数是 4.3 不是 3：合格率 70% 时凑够 3 篇的期望次数就是 4.3，按 3 算会低估四成。

标注比生成贵三倍，而且换模型省不掉它。单篇实测：生成 77 秒 / 5,204 输入 token；标注 105 秒 / 16,981 输入 token。 换成 deepseek 关思考，生成那一行从 5.4 分钟压到 40 秒，但标注那 5 分钟原样不动—— 总时长 10.5 → 6 分钟。省的是少数部分，这也是决定 18 不换的算术依据。

串行还有个附带好处——中转站 20 rpm 的限速彻底不用管。

C · 今日包与离线闭环

决定 8、9、12、17

今日包装什么

字段内容

复习作答现在离线跑不了

这是翻代码翻出来的，不在任何文档里。

/reviews 的响应已经是离线形状——每张卡片带着句子一起下发，客户端本地跑加权抽取， 权重衰减参数由服务端下发。这部分是对的。

但 /reviews/answer 是一次一答的在线 POST，没有本地队列、没有幂等键。 阅读那边有（reader.html 的本地队列加 idem_key），复习这边没有。 地铁里做复习，每答一题都失败。

它破的是架构铁律 2：「交互事件先存本地，联网后批量上报，每个事件带客户端生成的幂等键； 在线和离线走同一条代码路径，不是两套。」读后抽查取消之后，复习是唯一的产出型交互—— 这条不补，手机端的「离线可用」就只剩阅读那一半。

做法：新增批量端点收一串作答，每条带幂等键，服务端按顺序重放—— session.answer 本来就是顺序状态机，补的是去重。 Web 复习页接上同一套队列：它是开发期工具（铁律 8），但它是唯一能验证离线形状的地方。

选文规则

没有水平估计的情况下：新备未读的生成文优先（货架筛选 P2 就做好了，按备稿时间加未读判定）， 加餐再给一篇。不掺真题（决定 9）。

路上抓到五个静默失败

都是「不报错、但东西悄悄不工作」那一类，这个 Phase 的价值有一半在这里。

✕recover_interrupted() 只恢复得了「昨天以前」中断的任务。 updated_at 存 ISO（T 分隔），却拿 SQLite 的 datetime('now')（空格分隔）比—— 'T' 的码位大于空格，同一天的比较永远为假。当天崩溃的任务永远停在 running， 文章永远打不开。已有的 bug，已修，并单独记成坑 §6.3。
✕「下次运行时间为空」＝这个任务永远不再跑。 夜间备稿二十七分钟一次没跑，runs 一直是 0，全程零日志—— task_runs.next_due_at 是 NULL，而判定是 due <= now，None 永远不满足； 播种又只在行不存在时才写。这个状态真实可达：收尾时周期解析失败就会写成 NULL， 从此永远不跑，把周期改回正确的也救不回来。修法是值为空就重排并记 WARNING， 且重排到下一次而不是「立刻」——修复动作不该顺手多跑一次生成。 已记成坑 §6.4，守卫 verify_phase4.py A3.3。
✕标注任务能「成功」地什么都不做。文章被重新分析之后 token id 全变， 而任务攥着旧 id：每批都找不到活干、报成功、任务显示「全部完成」、文章永远停在 annotating。 全程零日志。修法是按文章自愈而不是按任务——备稿开头把所有「备好但没就绪」的文章 按当下真实缺的 token 重新排上。
✕每天备的文章都留下未判的词组候选。入库只做结构扫描（不花钱）， 判定是另一步；不接上的话，词组在阅读页里直接不显示，而且不报错。 三篇文章留了 12 处，是 verify_phase2.py 7.9 变红才发现的。 现在备稿收尾会等标注跑完再判词组。
✕我自己引入又修掉的一个：把单篇生成抽成共用函数时 scheme 被写死成 anchor，控制台上选的约束方案会被静默忽略。
