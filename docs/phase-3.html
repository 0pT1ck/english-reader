§1

这个 Phase 是怎么来的

原来的 P3 是「自适应」。2026-09-08 连同它后面那半张路线表一起整体归档，重新设计。

归档的两个理由记在主文档 §K 表后。简短说：P2 吃掉了原本排在后面的一大半（语境标注、难度画像、 第三层释义、词组、三档标记、客户端契约），旧 P3 那一行只剩下「把客观难度换成对你的生词率」一列； 而且旧路线按「能力」切，而缺的东西要按「实际在跑的那个循环」切才看得清。

那个循环是：打开阅读页 → 在 453 篇里挑一篇 → 读 → 点词 → 标记 → 读完 → 结束。 它最大的空洞是第一条：读完之后什么都不发生。所以新的 Phase 3 就是复习。

同时定下的方法：只规划当前 Phase，不提前规划未来。主文档 §K 从今往后只有「已完成的」和「当前这个」， 归档的六行留着当记录。当前 Phase 中发现的未来需求记进 §M 待定，不动手。

12绝对不要四选一。给了选项就能排除法蒙。判定靠自评：点开答案，你自己说想对了没有。

14每日复习量暂不设上限，到期多少复习多少。负载均衡算法待优化，已记入主文档 §M。
15当天收尾只看一条：池子空了。降权是让路，不是出口——今天过不去的词，今天结束不了。
16句子优先不重复，池子抽空了才允许重复。是优先，不是禁止。

18「不认识」当天就复习一次；「模糊」当天不复习，第二天开始，第二天记住了就多隔几天。P2 定的「模糊只记录不调度」到此为止——那句话的前提是 P2 根本没有调度。
19两个池子分开记：当天标记的一个，算法到期的一个。怎么呈现（混着抽／一个入口先后走／两个入口）留着以后选，现在只要数据上分得开。
20看义想词的题面给中文义项，可点开看英文概念定义。给英文容易泄题——nationality 的定义里就带着 nation。
21挖空里填句中的实际形式（addressed 而不是 address）。题面是完整句子，填原形语法不通；而「读到能认出」本来就包含认出变形。
22看义想词也有四级渐进提示，第 1 级是首字母。专治「着手解决也可以是 deal with」这类歧义，见 §3。
23句子在读完文章那一刻就生成，夜间批次补足、有余力就往前建。句库是长期资产，不是够用就停。
28控制台加一张词表（2026-09-09 加）：标记过的每个词，一行上并列显示上次评级、记忆强度、难度、轮次与失误、下次到期、当初在哪遇见、以及给它编好的句子。「排期看着不对」在没有它之前是无法证伪的——你只看得到哪天，看不到凭什么。
27最长间隔压到 180 天。FSRS 默认 36500 天是给「终身记住」设计的；这个项目瞄的是有日期的考试，排到考试之后等于没排。配置项 fsrs_maximum_interval。
26点了提示就算这次不会（2026-09-09 人工验收当场定）。看了提示想起来也不算——那不牢固。判定在第一次点提示时就下了，降权、放回池子，后面几级只是让你看清答案。
25复习页带一个「模拟跳到下一天」（2026-09-09 实施时加）。复习是按天调度的，不快进就得真等几天才看得到第二次复习。它在骗系统说今天是哪天，所以非零时页面一直挂提示，验收脚本直接判失败——在模拟的未来里通过验收什么也证明不了。
24调度用 FSRS，依赖 py-fsrs（MIT），不自己抄公式。关掉它自带的 learning steps——当天重复到会我们已经用伪随机降权做了，两个都开会重复计数。一天算一次复习。细节与理由见 §5。
§3

一次复习长什么样

决定 7–12

当天到期的词进一个池子，每次按权重随机抽一个，问它当前解锁到的那个方向。

抽中一个词 → 问它当前解锁到的方向

看词想义  句子里的词高亮，问：这里是什么意思？
        想出来了 → 点「会了」→ 显示答案让你核对 → 确认对了
                  → 解锁看义想词，放回池子
        想不起来 → 点一层：出现你当初读到它的那句原话
                  → 再点一层：出中文意思
                  → 再点一层：跳回原文
                  → 记一次没答上，权重降低，放回池子

看义想词  同一个义项，换一条句子，词挖空，旁边给义项
        填出来了 → 这个词今天完成，出池
        填不出来 → 看义想词重新上锁，退回看词想义
                  → 权重降低，放回池子

池子空了 → 当天结束 → 可选：对当天所有词做一轮拼写强化

为什么「放回池子」比「接着问」好

看词想义过了之后不是立刻问看义想词，而是放回池子、隔几个词才轮到它。 刚看完答案就问，考的是几秒钟的短期记忆；隔了几个词再问，那才是真想起来了。 随机抽取自动做到了这一点，不用额外设计。

为什么不定次数上限

「重复到会」需要一个出口，但硬性的「问四次就放过」不妥当——它按次数一刀切， 而不同的词该给的机会本来就不一样。改成权重按失败次数衰减（例如每错一次减半）： 错得越多越抽不到，但不是禁止，运气好还是会轮到。

当天的收尾条件只有一条：池子空了。降权只是让卡住的词少出现、给别的词让路， 不是给它一个出口——「一直重复直到学会」就是字面意思，今天过不去的词，今天就结束不了。

代价要认：状态特别差的一天可能会被一两个词拖长。这是明确接受的， 换来的是「今天复习完了」这句话没有水分——不存在「今天有三个词没拿下但也算完成」的中间状态。

看义想词的四层提示，以及「着手解决也可以是 deal with」

给中文让你想英文，答案常常不唯一：「着手解决」对得上 address，也对得上 deal with、solve、tackle。 这个歧义是真的，但它撞上了已经定过的第 12 条——不要四选一，判定靠自评。

那么这一步天然是练习而不是检验：系统不判你对错，是你自己看到答案后说「我想起来了没有」。 你想到 deal with、点开看到 address，你自己知道没想起来那个词—— 而调动这个义项的过程本身已经是一次有效的提取。换成四选一，歧义才会变成硬伤。

但还是不该让人白想，所以对称地做四层，第 1 级给首字母：

第 0 层  挖空的句子 + 中文义项
         The government must ＿＿＿＿ the problem of air pollution.（着手解决）

想不出 → 第 1 层  首字母          a＿＿＿＿＿＿
想不出 → 第 2 层  你当初读到它的那句原句
想不出 → 第 3 层  答案

首字母几乎零成本，却把歧义砍掉九成——deal with、solve、 tackle 全排除。它不改变自评的性质，只是少让你白想。 而「用到第几层就是评分」这条原样适用：第 0 层想出来的，和要看首字母才想起来的，本来就该记不同的分。

还有一层天然的收窄：那个空要填的不是「任何一个意思是着手解决的词」，而是你标记过的那个词。 整场复习里每一个词都是你自己标的，这是上下文自明的。中文 + 句子 + 首字母叠起来，实际歧义比孤立看小得多。

两个池子，以及「模糊」什么时候开始

当天的复习由两批词组成，数据上分开记：

池子装什么第一次复习
当天池今天读文章时新标记的标「不认识」的当天就来一次；标「模糊」的当天不来，第二天开始
算法池记忆状态算出今天到期的由调度决定

怎么呈现留着以后选——混着抽、一个入口先当天后算法、或者两个入口，三种都行， 差别在体验不在数据。现在只要求两批分得开。

「模糊」这一档到这里才真正生效。P2 定的是「只记录不调度」，但那句话的前提是 P2 根本没有调度；P3 有了调度，它就必须回答。答案是：当天不问（你刚读完，现在懂）， 第二天开始进队列，第二天还记得就多隔几天——起始间隔和衰减归算法。

句子优先不重复，池子抽空了才允许重复

看词想义刚给你看过含 address 的 A 句，看义想词再拿 A 句挖空，答案等于白送。 所以优先抽当天没用过的句子——这也是句子池要备 5–10 条的原因之一。

但这是优先，不是禁止：当天这个词反复没拿下、池子里的句子都用过一遍了，就允许重复用。 重复一条旧句子，总好过因为没句子可出而把这个词放过——而按上面那条，当天本来也没有「放过」这个选项。

怎么保证生成的句子不跑偏

用现成的机器，不让模型自己判断自己：

1过量生成 一次多要几条（比如 12 条），不要求它「写 8 条好的」——本项目已三次证明模型对数量约束无感。
2逐句机器校验 还原词形 → 查词典 → 算超纲。生成文章那套校验器本来就在做这件事，是纯查表，零误判、零模型成本。 再加长度、目标词是否真的出现、有没有把答案直接写进句子。
3不合格的直接丢 留够 8 条就行。这跟主文档 §B3「过量生成择优」是同一个做法，而且这里的判定完全是机器的。

§5

评分与调度

决定 11 · 24

「一次就想起来说明记得牢，反复才想起来说明不牢」——这个直觉要落成两个维度。

维度数的是什么含义
当次表现今天这个词被问了几次才两个方向都过这一次的评分。一次过等于最好
累计轮数到今天为止总共复习过几轮这个词的难度。轮数少就稳下来了，说明牢

用 FSRS，而且不自己抄公式

FSRS（Free Spaced Repetition Scheduler）是 Anki 现在的默认调度器， 从数百万条真实复习记录拟合出来，而不是像 1987 年的 SM-2 那样拍出来的公式。 依赖 py-fsrs（PyPI 上叫 fsrs，MIT 许可，v6.3.2，Python ≥3.10， 调度器本体无第三方依赖）。

不自己实现：v6 有 21 个默认参数，记错一个就是一个安静的错误—— 这个项目已经三次栽在「数字看着对其实错了」上（累积标签、英美拼写、超纲派生词）。 引一个 MIT 的无依赖库，比抄一遍公式便宜也安全。

许可上要小心的是另一件事：py-fsrs 是 MIT，可以直接依赖； 但 Anki 本身是 AGPL，绝对不能抄它的代码——AGPL 会传染整个项目。 同一个组织下别的仓库也有 AGPL 的，引之前逐个核对。

它的状态量正好就是我们留的字段

FSRS是什么我们 §8 留的字段
Difficulty这个词对你有多难，答差了就涨难度
Stability现在这个记忆能撑多久记忆强度
due下次该问的时间下次到期时间

一个字段都不用改。当初那条「状态字段按算法无关的形状留， 别把某个算法的内部参数焊死进表结构」，守对了。

「累计轮数」是结果，不是输入——所以不写加权公式

FSRS 的输入只有三样：旧的 D 与 S、这次隔了多久、这次答得怎样。 复习过几轮本身不进公式。

那决定 11 的第二个维度怎么办？它已经在 D 里了：一个词你复习了八轮还在队列里， 必然是因为答差过好几次，而每次答差 D 都涨了一点。 所以不需要我们再写一套加权——写了就是重复计数。这条是 2026-09-09 查清 FSRS 之后 对决定 11 措辞的修正，写在这里是因为不写的话实施时一定会去写那套多余的公式。

评分怎么映射

FSRS 吃四档评分（Again 1 / Hard 2 / Good 3 / Easy 4）， 我们的信号更细——当天问了几次才两个方向都过：

1 次过   → Easy
2 次过   → Good
3 次过   → Hard
4 次及以上 → Again

关掉 FSRS 自带的 learning steps

FSRS 有自己的「当天多次重复」机制（learning_steps，默认像 1 分钟／10 分钟）。 我们已经用伪随机降权做了同一件事（决定 9、10），两个都开就会重复计数。

所以口径必须写死：当天整体算一次复习，评分反映当天重复了几次， 而不是每重复一次就算一次。learning_steps 设为空。

optimizer 先不装

py-fsrs 的参数优化器是可选依赖（fsrs[optimizer]）， 能拿你自己的复习历史重新拟合成你个人的遗忘曲线。但没数据的时候做了也没用—— 先用公开的默认参数跑，攒几个月再说。这正是「复习历史完整落表」那条要换来的东西。

参数本身进配置项，控制台可改。

怎么验它是对的

调度器是个纯函数（旧状态 + 评分 → 新状态 + 到期时间），没有数据库、没有网络。 所以能用注入的时间直接跑，这正是验收 A 要的。除此之外拿能直接看的已知答案验： 连续答对，间隔必须递增；连续答错，间隔必须塌回去。 照抄一个库不代表接对了，接错了同样是安静的错误。

词组为什么不做

两个目的被混在一起了，而它们的价值差很远。

目的一，不给错释义：你点 account，句子是 sources account for a third of supply，系统不能回你「账目／账户」。 错误输入是这个项目唯一最怕的东西，实测每篇约 5 处。这一层 P2y 已经做完了， 成本付过、收益在手。

目的二，把词组当学习对象：建义项集、进复习队列、挖两个空、拼写、句子池。 这一层从来没有被单独论证过——它是顺着「词组也进 study_states」被带出来的。 P2y 定案的六条里没有一条承诺复习；合表那条说的是「复习调度要混着排序」，那是留位置，不是承诺。

而它现在唯一的证据是：已有的 12 条标记里，1 条是词组。 与此同时它是 P3 里最贵的一块——义项存哪张表、挖空要挖两个词、拼写拼一个词组、 句子池几乎全靠生成（词组在语料里中位数 1 句，56.5% 只出现过一次）。

推迟几乎没有代价：识别和释义照常跑，你照样能标词组，只是暂时不排期。 读一两个月之后，「标记里词组占多少」就是个实测数字，那时候再决定，而且起点更好 （Wiktionary 的多词条目已经在手，见 Phase 2 文档 §18）。 这跟 P1c 的教训是同一条：在使用它的功能出现之前先定格式，就是在没有反馈的情况下猜。

代价要认，而且必须验：stick to 现在就躺在 reviewing 池里， P3 之后它仍然不会被复习。这是明确的已知缺口，不是遗漏—— 所以验收里有一条专门查它确实是被有意跳过的，而不是被静默漏掉的。

界面按铁律 8 做在 Web 上，认它是开发期测试工具、将来重做。 要不要改铁律 8 是另一场对话，不在 P3 里开。

§10

验收标准

10 项

调度是按天算的，验收要么等时间流逝，要么造时间。两条都要。

A自动检查：用注入的时间跑调度 今天标一个词，把「现在」拨到三天后，看它该不该出现、出现在哪个方向、 答错之后下次到期有没有提前。不靠真等。
B自动检查：不变量没破 复习不改变词池位置（那是 P2 的不变量）；撤销标记后条目退回 new 但遇见记录保留； 句子池里每条句子都过了超纲校验；拼写记录只写不读。
C自动检查：句子池够用 随机抽 50 个进了队列的义项，每个都凑够了目标条数；生成的句子里目标词确实出现， 且除它以外没有超纲词。
C2自动检查：词组是被有意跳过的 item_type='phrase' 的条目留在 reviewing 池里、遇见记录照常， 但一条都不出现在复习队列里。查的是「有意跳过」而不是「碰巧没查到」—— 所以断言的是「池里确有词组条目，且复习队列里一个都没有」，两边都要成立。
C3自动检查：「模糊」当天不出现 同一篇里标一个「不认识」、一个「模糊」：当天的队列里有前者、没有后者； 把时间拨到第二天，两个都在。这是 P2「模糊只记录不调度」那句话到期的地方， 必须验出差别，否则三档就白分了。
C4自动检查：看义想词的题面锁得住 挖空处填的是句中的实际形式（addressed 不是 address）； 第 1 级提示给的是首字母；同一天里看词想义与看义想词抽的不是同一条句子， 除非句子池已经抽空。

D 不再是验收标准，E 仍然是（2026-09-11 改）

2026-09-10 原本把 D 与 E 一起推迟，等手机上装着自己的 App、每天真的在用了再验。 2026-09-11 拆开处理，因为这两项的性质根本不同。

D「真跑三到五天」不再作为验收标准。它验的全是体感——原句能不能勾起记忆、 当天重复到会烦不烦、歧义烦不烦——而按架构铁律 8，现在唯一能跑复习的管理页是开发期测试工具， 在它上面坐三到五天，量出来的是「凑合跑」的体感，用错的场地量出来的数据会让人对着错的东西改。 而手机端就是下一个 Phase，这些问题到那时会在日常使用里自己得到回答。 与其挂一个验收项在这里等着，不如承认它不是这个 Phase 能验的东西。

·记忆列由 reading 的迁移 5 添加，不是复习模块加的。 表是 reading 的——跟 P2 里 devices.learner_id 由 core auth 添加同一条规矩： 谁拥有表谁加列。另起一张平行的状态表会把「这个义项现在处在哪」劈成两半。

人工验收当场改出来的七件事

自动检查全过之后，第一次真用就撞出七个问题。两个是脚本永远查不出来的， 一个是脚本查得出但我没写。

一、看词想义把英文词当成了答案

它问的是「这里是什么意思」，最深一级提示却给出 yields—— 答了一个没人问的问题。看词想义的答案是中文义项，看义想词的答案才是那个词。 第一版两个方向都写成了后者。

顺带把第三级改回方案原本写的跳回原文（生成句没有出处时退回英文定义）—— 中文在第二级已经给过了，第三级再给一遍是空的。

验收补了 6.6：断言同一份响应里两个方向的答案都齐备。这条脚本查得出，是我漏写了。

二、按钮点不动，因为异常被吞了

症状是点「对了」毫无反应。真因有两层：

第一层：揭到最后一级提示时，页面替你偷偷提交了。条目在服务端已经翻篇， 屏幕上还停在那道题；再点「对了」，服务端回 400 这个词今天已经过了—— 而页面没有任何地方接这个异常，按钮就静静地死了。

第二层：改了之后仍然复现，因为浏览器还在跑旧的 JS。 页面自带逻辑而开发期一天要改好几遍，缓存的副本看起来和「没修好」一模一样。 复习页现在返回 Cache-Control: no-store。

三处一起改：不再偷偷提交（揭完提示后由你点「下一个」）； 所有提交走一个 guard()，进行中禁用按钮、出错显示在页面上并自动重取； 错误行挪到面板外面——第一版把它放在题面 div 里，于是答案面板打开时报错写进了隐藏元素， 页面看着就是冻住的。

三、按钮的可用性靠样式守，不算守

修完之后在假 DOM 里重放，发现「答案面板没打开时点『对了』」照样会提交—— hidden 只是不显示，处理器还在。

改成一个显式的状态机：asking（题面）／revealing（答案面板）， 四个按钮各自检查状态。一条写在 style 属性里的规则不是规则。

四、404 带着 trace_id 发出去，却什么都不写

页面报「出错了：Not Found（trace e7369f…）」。拿这个 trace 去 logs.db 查—— 零条记录。

病根在 core/errors.py 的 StarletteHTTPException 处理器： 上面写着注释「多半是路径写错的 404，保持 INFO 级：拼错地址不算事故」， 而下面没有任何一行 log 调用。注释描述了意图，实现从来没有跟上。

后果正好打在日志规范承诺的那一点上——「trace_id 贯穿一次请求，并出现在错误响应里， 用户复制给 AI 就能定位完整链路」。把 trace 贴过来查出来是空的， 那把 trace_id 放进响应的全部理由就没了。

补上之后，同一个 trace 查回来是：{"status":404,"path":"/v1/client/…","method":"POST"}。 写进验收脚本 9.4（P0，因为这是地基层的保证，不是 P3 的），P0 因此从 29 项变成 30 项。

这次那个 404 的路径仍然不知道——它发生在补日志之前，没留下任何东西。 活服务和磁盘上的代码路由表一模一样，页面用到的地址在活服务上全部存在（401/405，不是 404）， 所以它是个页面之外的地址。重启服务之后再复现一次，一条查询就能定位。

五、页面继承了控制台的全局作用域，撞了名字

补上 404 日志之后，同一个 trace 立刻查出了路径：

{"status": 404, "path": "/v1/admin/reviews/answer", "method": "POST"}

页面在往 /v1/admin 发本该发去 /v1/client 的请求。 原因是 base.html 里有个全局 async function api() 走 /v1/admin，而复习页也定义了一个同名的走 /v1/client—— 同名函数声明在同一个作用域，后解析的赢，而 base 的脚本排在内容块之后。

于是症状极具迷惑性：页面加载正常（首次请求早于 base 被解析）， 之后每一次点击都 404。看起来就是「按钮点不动」。 连报错文案都是 base 那个 api() 的格式（msg（trace …））， 这本可以早点提醒我，但当时错误被吞了根本没显示出来。

P2 的阅读页把自己的 helper 命名为 client()，没撞——是这一版抄错了名字。 改名之外，整段脚本包进了 IIFE：把碰撞变成不可能，而不是只是不太可能。

写进 verify_phase0.py 4.9：扫描每个继承 base.html 的模板， 顶层声明不许覆盖控制台的全局名（api／toast／humanBytes）。 按惯例做了对照——阴性：现在的复习页零撞车；阳性：故意重定义 api 与 toast 的模板被准确报出。P0 因此 30 → 31 项。

六、验收脚本只在「今天碰巧有到期词」时才跑得动

复现完这一轮之后再跑验收，2.1 和 4.x 全红——不是代码坏了，是今天的词已经复习完了， 队列空了没得走。

一个只在某些日子能过的验收脚本，等于没有验收脚本。改成自己种一个到期的探针条目、 连同两条句子，走完再全部删掉——第 3 节本来就是这么做的，其余几节忘了照做。 现在连跑两次结果一致，四张表零残留。

七、hidden 没能隐藏，于是按钮「看得见但点不动」

最后一个，也是最阴的一个。base.html 里有：

button, .btn { … display: inline-block; }

这条比浏览器自带的 [hidden] { display: none } 优先级高， 所以给按钮设 el.hidden = true 只让它失效，没让它消失。

于是：点了提示 → 这一轮判为不会、btn-know 被「隐藏」（其实还在）→ 你去点它 → 逻辑守卫正确地拒绝了 → 看起来一点反应都没有。 代码是对的，屏幕是骗人的——这种最难查，因为没有任何东西出错。

修在 base.html 加一行 [hidden] { display: none !important; }， 不修在复习页——任何模块页藏一个按钮都会踩到它。 写进 verify_phase0.py 4.10，P0 因此 31 → 32 项。

怎么找出来的：把页面的 JS 抽出来在 node 里重放

前两轮都在猜。第三轮把 <script> 抽出来，配一个假 DOM 和假服务端， 照着人工验收的点击顺序重放——一次就看清了哪一步没动、哪一步动错了， 包括「面板没开时点对了照样提交」这个用眼睛看不出来的。 这跟这个项目一贯的做法是同一条：要判断就给它具体对象，别靠猜。

§14

算法验证，以及它挖出来的两个标定错误

2026-09-09

单元检查只能证明「调用参数递对了」。整套跑一年会不会出问题是另一回事， 要验它得先有一个可以被排期的学习者。

接线是对的，这一条测得很干净

做法：让仿真里的学习者严格按 FSRS 自己的可提取性曲线遗忘。 这样两个记忆模型不会分歧，剩下能出错的只有接线——单位、评分映射、一天算一次、状态存取往返。 400 词 × 400 天：

目标保持率0.900
偏离0.0005
实测一次过率0.905

秒当天、评分反了、当天重复被算成多次复习——任何一处接错，这个数都会明显跑偏。

换一个遗忘模型：这不是 bug，是 optimizer 存在的理由

把学习者换成半衰期式、且比默认参数假设的更健忘，FSRS 就排得太晚 （3.5 个半衰期，该是 0.152），一次过率掉到 0.28。

任何间隔重复系统面对「跟训练数据里的人不一样的学习者」都会这样。 但这给方案里那条决定配上了数：如果你的遗忘比默认参数快，一次过率会从 0.90 掉到 0.28。 所以「攒够历史再用 optimizer 拟合成自己的曲线」不是锦上添花。

标定错误一：把「答对」当成了「太简单」

仿真里一路顺利的间隔是 8 → 66 → 180 → 180，看着就太远。追下去是映射的问题： 原本写的是 一次过 → Easy。

但在 FSRS 里 Good = 答对了，Easy = 毫不费力，别再拿它烦我，后者带额外加成。 「第一次问就答对」只是答对。而我们根本没有能区分两者的信号——那需要量「答得多快多轻松」， 我们不收这个数据。硬造一个出来就是无中生有。

定案（本人 2026-09-09）：默认从 Good 起评，Easy 由你自己标。 界面上「对了」旁边多一个「太简单了」，只在这一轮零失误时出现， 而且服务端也要检查——磕过就不认，客户端说了不算。

标定错误二：数的是「问了几道题」，而一轮天生两道

这两个错，单元检查都查不出来

1.1–1.6 全过的时候，这两个标定错误一直在。它们不让任何东西报错，只是让间隔安排得不对。 能把它们暴露出来的只有「让它跑一年然后看涌现出什么」。
