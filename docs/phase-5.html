§1

为什么拆成两半

原本的 P5 是「iOS 客户端」一整件事。拆开之后，前一半的性质完全变了。

做手机端要面对三件从没遇到过的事：我没有 Mac（编译要借道 CI）、我看不见界面（要靠截图传回来）、 装真机要等别人的开发者账号。前四个 Phase 里，改完就能跑、打开就能看、你就在旁边——这三样一样都没有了。

但把 Core 单独拎出来之后，这三件事一件都不涉及：

✓不需要 Mac。Core 是纯 Swift，实测在这台 Windows 机器上能编能测（§3）
✓不需要看界面。P5 根本没有界面，验收靠命令行工具真跑一遍（§10）
✓不需要签名、TestFlight、你朋友。一样都用不到

而且顺序上也对：Core 装着这件事里最容易写错的部分——复习状态机、离线队列、幂等键。 这符合项目一贯的风险前置（主文档 §K：「最不确定的东西最早验证，而不是最容易的先做」）。

「没有界面怎么验收」这个问题有先例：P1 就是一个命令行生成器，没有界面，照样验收了—— 它的完成定义是「用词在范围内、句法是正常书面语」，靠跑脚本打数出来。 所以在这个项目里，「可验收」从来不等于「有界面」。

Core 与界面：一条机器能查的边界

决定 4
换成安卓客户端也要一模一样的 → Core。换成安卓会长得不一样的 → 界面。
Core界面
抽下一道题什么时候弹释义面板
幂等键怎么生成高亮用什么颜色
字符区间映射到第几个 token把 token 画成三种下划线

为什么值得

1这条边界是机器能查的。CI 里一行 grep 就能守住「Core 里不许出现界面框架」。这是项目一贯的做法——守卫才是保护，散文只是解释。绝大多数架构规矩会静默腐烂，这一条不会。
2它把架构前提 1 从承诺变成事实。「客户端零业务逻辑」这条已经被离线要求咬掉了一块——复习状态机必须在客户端有一份。Core 的意义就是把这块圈出来、标清楚、能测试，而不是让它散在视图里。
3对「谁来维护」最关键。这个项目的维护者不是读代码的人，是下一次会话的 AI。「好维护」的实际含义是：下一个会话能不能不靠记忆就判断出一段逻辑该放哪。

代价

!边界会漂，方向可预测。危险的不是界面代码跑进 Core（grep 当场抓住），是反过来：某个判断因为写在视图里更顺手就留在了界面层，同一件事两边各一半。这个 grep 查不出来，只能靠上面那条判据加 Core 的测试覆盖。
!Core 必须持续保持跨平台干净（不碰平台专有 API，网络只定义协议）。这是要一直守的约束，不是一次性的。守不住时的退路是把 Core 的测试挪回 macOS，分层原样不动。
§6

本地存三类东西

决定 8、10

起初问的是「本地用什么存」，问错了——三样东西性质完全不同，只有一样需要崩溃安全。

内容大小丢了会怎样
一、发件箱还没上报成功的事件（标记、读完、作答）很小真丢了。这是客户端唯一独有的数据
二、元信息标题、字数、句数、难度、读没读完、读到第几句、有没有缓存正文每篇几百字节能重拉，但留着很便宜
三、正文缓存全文、token 分析、释义表、词组、复习句子约 300 KB / 篇无所谓，重新拉一次

推出来的结论很直接：客户端需要的不是一个数据库，是一个可靠的发件箱，外加两份可以随时扔掉的缓存。 这是架构前提 3 的直接后果——服务端是唯一事实来源，客户端存的一切都只是缓存。

不缓存数据库，只缓存「今天这一份」

东西大小
dictionary.db（404,011 词条）111 MB
learning.db（461 篇文章、215,910 个 token）40 MB
content.db（13,741 条义项）20 MB
整库合计171 MB，且一直在涨
一天的今日包（3 篇正课 + 1 篇加餐）约 1.2 MB

差两个数量级，因为 /today 下发的不是「数据」而是当天用得上的那个切片： 文章全文、文中每个词的释义、当天的复习卡片与句子。 404,011 条词典、13,741 条义项，一条都不下发——点词查词能离线用，是因为释义随文章一起打包了， 不是因为手机上有本词典。

不缓存整库还有一个不是因为大的理由：手机上一旦有了全库，就会忍不住自己算—— 选文、难度、调度，而那正是铁律 1 要防的事。把客户端限制在「只有今天这一份」，等于让那条铁律在物理上更难被破坏。

清理缓存

1
读完的、没读完的，都留着不按「读完就清」自动处理，由用户决定。
2
用户指定清理哪些清理只删手机本地，不删服务端——服务端那份是事实，本地这份只是副本。
3
清理后标题、字数、进度仍在因为元信息属于第二类，不在清理范围。点开某篇触发重新拉取（走 /v1/client/articles/{id}，P2 就有，后端一行不用改）。
不变量：清理缓存绝不能碰发件箱和元信息——只删能重新拿回来的东西。
破了它是静默的：用户点一下「清理缓存」，把还没上报的标记一起删了，屏幕上什么都不会发生， 那些词就永远不进复习队列了。跟「入库绝不写 study_states」是同一个形状—— 没有报错、没有日志、只有后果。
验收要有专门一项：造几条未上报事件 → 清理全部缓存 → 断言事件还在。

要认的代价：清理过的文章，在离线状态下点开会打不开。 这是用户自己选的清理，代价合理，但 Core 要能把这个状态表达出来 （已缓存／只有元信息／正在拉取／离线拿不到），否则界面只能显示一个转圈。

§7

发件箱，以及一个服务端的洞

决定 9、11、12

发件箱是客户端唯一不能丢的东西：标记了一个词、读完一篇、答了一题，在送达服务端之前只存在于手机上。

一条事件一个文件

写的时候先写一个临时名，再原子改名；上报成功就删掉那个文件。顺序靠文件名里的序号—— 复习作答必须按顺序上报（答对才解锁反向，服务端明写「顺序是客户端的」）。

选它不是因为它丢得少，是因为它可能出错的地方更少。另一个候选是「一个追加式日志文件 + 已发到第几行」， 两者在崩溃时丢的其实是同一条——正在写的那一条，而那一条用户还没看到成功。 真正的差别在别处：日志文件只会变长，隔一阵要压缩一次，而压缩是在重写整个文件—— 崩在中间可能一次丢掉很多条还没发出去的事件。一条一个文件没有这个动作，也就没有这个丢法。

不管哪种存法都成立的一条：先落盘，再在界面上确认。 顺序反了的话，用户看见「已标记」但其实没写进去，崩溃之后就成了静默丢失。

删之前要跟服务端逐条比对

批量上报逐条回状态（accepted / duplicate / failed / rejected），所以规则写死成：

只删服务端在 results 里明确回了成功的那几条，按幂等键一条一条对。 没出现在回应里的、回了失败的，一律不删。绝不能「HTTP 200 就整批删」—— 一批里可以部分失败，服务端代码注释明写着「一条坏的不拖垮整批」。

至于「发出去了但没收到回应」（断线、超时），协议本来就设计好了：重发就行，服务端靠幂等键认出来，回 duplicate。

但 duplicate 这个回答现在不可信 ← 决定 12

服务端处理一条事件是两步：先存档，再执行。

1
存档成功、执行失败回 failed，客户端保留文件、稍后重发。到这为止都对。
2
重发时撞上唯一索引，直接回 duplicate根本走不到执行那一步。
3
客户端以为成功了，删掉文件那条事件从来没执行过，而且再也没人会重试它。

具体后果：假如那条是 word.marked—— 你标记了一个词，屏幕上也显示标记上了，但它永远不会进复习队列。没有报错，没有日志。 这正是「跨 Phase 静默错误清单」里的形状。

查证过：没有任何地方会重试 error 不为空的事件。 目前库里 420 条事件、失败 0 条，所以还没发生过——但路径是通的（执行那步会因为未知条目类型、数据库锁、缺字段抛异常）。

补法：重复上报时先看那条之前执行成功没有，没成功就再执行一次。 选它而不是「在回应里加个字段说明上次成没成」，是因为只有它能自愈—— 加字段只是让问题别被误判，那条事件仍然没人执行。而且它不改契约、不改客户端， 做完之后 duplicate 才名副其实，客户端「回了 duplicate 就删」的规则才真正站得住。

验收要按阴性 + 阳性对照验（坑列表 §4.3）：
① 造一条注定执行失败的事件 → 上报 → 断言客户端没删
② 修好失败原因 → 重发 → 断言服务端这次真的执行了，且客户端这才删
③ 正常事件 → 上报 → 断言正常删掉（确认规则没把好的也卡住）
§8

契约类型从哪来

决定 13

「类型」就是一份写在代码里的说明：这坨数据有哪些字段、每个装什么、哪些可能是空的。 它决定了错误在什么时候被发现。

现状是主文档 §M 记着的那条：客户端接口返回 dict[str, Any]， 所以 /openapi.json 里响应体是 {"type":"object","additionalProperties":true}—— 知道有 /today，不知道它返回什么。75 个端点，每一个都这样。

所以顺序是：

后端声明响应类型 → OpenAPI 有了真 schema → 生成 Swift 类型

§M 当时已经否掉了另一条路：正确的补法不是另写一份契约文档（两份必然漂移， 而漂移时你不知道哪份是错的），而是给响应声明类型，让代码自己说清楚。

为什么直接用生成的，不另建一套

真正的分歧只有一个：后端改了契约，谁来告诉你？拿最常发生的「后端加了一个字段」走一遍—— 这个接口的铁律是只增不减，所以加字段就是日常：

直接用生成的生成 + 自己再写一份全手写
要动几个地方1 个：重新生成3 个：重新生成、自己的模型、转换层1 个，前提是你知道要加
忘了会怎样忘不了，就一条命令这个字段静默消失，不报错根本不知道后端加过
后端改了字段类型编译器当场指出所有用到的地方转换层编译报错，能发现运行时才炸，可能在手机上
代码读起来类型名冗长，要用别名缓解最干净最干净
一句话区别：直接用生成的，把契约变化变成编译错误；另建一套，把一部分变化变成静默遗漏；全手写，把所有变化变成运行时错误。

冗长的解法是类型别名和 extension（给同一份模型加便利方法）， 而不是再建一套模型——extension 加了不会漂，第二份模型必然漂。

还有一条反而是好事

后端的响应声明写得糙，生成出来的 Swift 就难用（字段全标成「可能为空」，Swift 这边到处要判空）。 这把压力压回了后端——想让手机端好写，后端的契约就得认真写。而后端是这个项目要长期留着的东西。

§9

复习状态机怎么保证不走样

决定 14

讨论里一度以为重复的是「Swift 和现有的 JS」。查过代码之后发现找错了对象。

真正重复的是 Swift 和服务端的 Python

复习页的作答处理有两个分支，注释写得很清楚：

if (res) {
  // 在线：服务端说了算。      ← 直接用服务端回的 asks/misses/done
} else {
  // 离线：先按规则往前走，好让这一天能做完。服务端补报之后会覆盖，
  // 所以这里只镜像那几条明写在契约里的规则，不自己发明任何东西。
}

所以设计意图早就定了：服务端的 session.answer() 是权威，客户端只在离线时镜像那几条规则。 Swift 要写的就是这个镜像。两边逐条对过——今天是一致的 （答对第一向解锁第二向、答对第二向算完成、答错回到第一向并把权重减半）。 问题不是现在错了，是将来会不会悄悄分叉。

两道保险，抓的不是同一类错

服务端导出向量命令行客户端在线对拍
怎么做写个脚本，用服务端真实的那段代码跑几百个场景，把「这样作答 → 应该变成什么状态」导成 JSON 进仓库；Swift 测试读它跑一遍在线答题时，客户端先按离线规则自己算一遍，再拿服务端的回应比，不一致就记一笔
抓什么纯逻辑写错了接线错了——状态机算得对，但上报时传错条目编号、或把作答顺序发拧了
抓不到什么它把状态机单独拎出来，不联网、不走 HTTP，所以结构上看不见接线错误要联网、不好重现
能进 CI 吗能，每次推送都跑不能，要有真服务端
最大毛病向量是快照，服务端逻辑改了它不会自己更新——Swift 对着过期答案照样通过慢

向量那个毛病有现成解法，跟生成代码同一个做法： CI 检查「重新导出后没有 diff」，服务端逻辑一改这条检查当场变红。 项目里有先例——verify_phase2.py 7.5 那条验收项就到期过。

对拍是便宜的保险，不是必需品。命令行客户端本来就要连真服务端答题，加的只是一次比较。 省掉它的代价具体是：离线那天你以为做完了，第二天一拉今日包发现还有几个词没做完—— 因为客户端每次重新拉包都会拿到服务端的版本，这种不一致会自动被纠正，不丢数据， 但你不知道发生过什么。没坏，但也说不清，正是这个项目最烦的那种。

手工设计的边角场景掺进向量里：连错五次、当天全做完、最后一题答错——随机撞不到的地方靠人指定。 但不单独用手写向量，因为那样没有权威来源，两边都「通过」可能只是两边都错。

§14

一个词该怎么显示

决定 17

讨论这条之前先看了现有阅读页在做什么，发现它不只是「好不好看」。

底下有两条规则，而且都是踩过坑才有的

现在的 classesFor() 里有一条优先级链——一个词可能同时是好几种，得按顺序挑一个：

专有名词 > 超纲词（且这篇要标超纲）> 目标词 > 派生词

还有一条更绕的，注释里写明了它的来历：

词在词组里时，不画它自己的标记底色——因为点词组里任何位置都是打开词组， 画了就是指向一个你从这里够不着的记录。
第一版没这条，实测丢了信息：28 个超纲词和 34 个派生词的标记被词组底色盖掉了。

画错了不报错，只是安静地给错信息——正是这个项目最怕的那种。 而且这个项目马上就有两个客户端（P5 的命令行、P6 的 iOS）， 这条链放在界面里现在就要写两遍。

定下来的分法

Core 出语义（选这个）Core 只转发原始字段Core 直接出样式名
Core 给出什么「这个词是超纲词，标记状态是不认识，它自己的标记不要画」原样转发服务端的十几个字段「用虚线下划线 + 红底」
优先级链写在哪Core，一份每个客户端各写一遍Core
界面还能决定什么下划线实虚、颜色、换别的记号全部几乎不能——换个设计就得改 Core
命令行客户端能用吗能，它把「超纲词」印成别的符号能，但要再写一遍链不能，终端里没有「虚线下划线」
写错了会怎样Core 的测试能抓静默显示错信息能抓，但 Core 绑死了一种设计

一句话区别：Core 出语义，是把「是什么」和「长什么样」切开； 只转发，是让每个客户端自己判断「是什么」；出样式名，是让 Core 连「长什么样」一起管了。

选的理由就是 §5 那条判据——换成安卓也一模一样的归 Core： 「这个词是超纲词」在任何客户端上都一样，「超纲词画成灰色虚线」则是这个界面的选择。

代价：Core 得有一套自己的词汇（超纲词、派生词、标记为不认识……），界面照着这套词汇挑画法。 多一层名字，但这层名字正好是两个客户端的共同语言。

坑一：NO_PROXY 不设，「连不上」会变成「503」

这台机器的环境变量里有 HTTP_PROXY（v2rayN，10808），但没有 NO_PROXY—— 而 CLAUDE.md 的网络访问那节明写着它该设成 localhost,127.0.0.1,::1。 Windows 系统代理的 ProxyOverride 是对的（含 127.*、192.168.*）， 但走环境变量的程序不看它。

于是发给本机后端的请求被代理接管，连一个没人监听的端口也会返回 503 而不是报错。 对一个离线优先的客户端，这是要命的：它会把「网断了」读成「服务器出错了」， 而这两件事的处理完全不同——前者该排进发件箱等重连，后者该告诉用户。

设上 NO_PROXY 之后，同一个请求正确地抛出 URLError。

坑二：同时设 NO_PROXY 和 no_proxy，Swift 程序当场崩溃

Fatal error: Duplicate values for key: 'ProcessEnvironmentKey(value: "no_proxy")'

Windows 的环境变量不区分大小写，而 Foundation 读环境时要建一个字典， 两个只差大小写的变量就撞成重复键——直接 fatal error，不是可以捕获的错误，是进程没了。

这个坑毒在两处：触发条件太平常（很多工具习惯两种大小写都设一遍）， 而且崩在任何网络代码之前——程序还没开始干活就没了，报错信息里也看不出跟代理有关。

规矩：只设大写的 NO_PROXY，绝不两个都设。

顺带发现：Swift 6 的严格并发默认是开的

swift-tools-version: 6.0 之下，跨并发域改一个全局变量直接编译不过。 这对 Core 是好事（发件箱和复习状态机都会被并发碰到），但写的时候要按它的规矩来， 不能等写完再补。
