Mac（主场地）：http://127.0.0.1:10808，环境变量已经导好 （HTTP_PROXY / HTTPS_PROXY / ALL_PROXY / NO_PROXY / no_proxy）。 2026-09-20 实测：GitHub、PyPI、api.anthropic.com 都通，freemdict 那类下载站直连也通。

  • NO_PROXY 和 no_proxy 在这台机器上两个都设着，而这是安全的。 「踩过的坑」§7 那条「绝不两个都设」只对 Windows 成立——那边环境变量不区分大小写， Foundation 建字典时会撞重复键、进程当场没（Fatal error: Duplicate values for key）。 macOS 和 Linux 区分大小写，是两个不同的键，不会撞——这台机器上就是两个都设着，别来「修」它。 这条在主场地搬到 Mac 之后要紧了：ercli 和 swift test 都在这台机器上跑。

Windows 备用工具链

仅在使用 Windows 备用环境时读取。以下为 2026-09-12 安装与实测记录，不把那台过期数据当正本。

主路径现在是这台 Mac（Xcode 27 自带 Swift 6.4），见「开发场地」。 下面这套留在 Windows 上应急——原来是「Windows 备用、CI 主路径」， 现在 Mac 顶了 CI 的位置，Windows 排到了第三。 （当年还有一条「r5s 上不装 Swift」，那台 2026-09-20 退休了，这条跟着作废。）

2026-09-12 装在 D:\Software\Swift，Swift 6.3.3，target x86_64-unknown-windows-msvc。 靠 VS Community 2026（MSVC 14.51.36231）与 Windows SDK 10.0.26100.0 编译链接—— 官方文档写的前提是 VS 2022，这套更新的组合实测能用。

新开的终端已经带好了环境（安装器写进了用户 PATH 和 SDKROOT）。只有在环境变量写入之前 就启动的 shell 才要手动补，那时两样都要，缺一样都失败得很难看：

  • PATH 要两个目录：Toolchains\6.3.3+Asserts\usr\bin 和 Runtimes\6.3.3\usr\bin。 只加第一个的话 swift --version 什么都不输出，退出码也正常。
  • SDKROOT=D:\Software\Swift\Platforms\6.3.3\Windows.platform\Developer\SDKs\Windows.sdk， 不设就报 unable to load standard library。

Core 的每个依赖都要单独核实能不能在 Windows 上编，别默认「Swift 生态的应该都行」。 已验过：swift-openapi-runtime 1.12.1 + swift-http-types 1.8.0、生成器本身（产出能编译能解码）。

跑任何 Swift 程序前，代理环境变量有两条要守（2026-09-12 各栽一次，详见 phase-5.html §16）：

  • 只设大写的 NO_PROXY，绝不 NO_PROXY 和 no_proxy 都设。 这条只对 Windows 成立：Linux 环境变量区分大小写，两个是不同的键，不会撞 Windows 环境变量不区分大小写，Foundation 读环境时建字典会撞重复键—— Fatal error: Duplicate values for key，进程直接没了，不是能捕获的错误， 而且崩在任何网络代码之前，报错里看不出跟代理有关。
  • NO_PROXY 必须设上（本机环境里原本没有，只有 HTTP_PROXY）。不设的话发给 127.0.0.1 的请求会被 v2rayN 接管，连一个没人监听的端口也返回 503 而不是报错—— 对离线优先的客户端这是要命的，它会把「网断了」读成「服务器出错了」。

Swift 6 的严格并发默认开着（swift-tools-version: 6.0）：跨并发域改全局变量直接编译不过。 对 Core 是好事，但要一开始就按它的规矩写，不能等写完再补。

模型配置与实验依据

本节配置与实验来自 2026-09-20～22 的实查和决定，操作前查生产配置；这次文档整理没有连接生产环境重测。旧提供商的余额、型号与故障码是历史记录，不是当前可用路径。标注没有贴合义项使用 -1、没有义项集使用 0，见 P11 订正；不能把下面 P10 的「填 0」原说法照搬。末段「批次 12–35 无差别、先动批次」也是较早口径，现行选择为 400，并以 A/A 噪音实验为依据。

  • 只有一条路能调通模型：gemini-3.8-flash-high（提供商 gemini，自建网关 gcli2api.cfoptick.com，免费）。2026-09-20 起只有阿里云一台， secrets.json 里只有 gemini 一个 key，llm_providers 表里只有 gemini 一行 （中转站那几个提供商的行在这台上已经不在了）。
    • 阿里云现行配置（2026-09-20 实查）：gen_provider = gemini、 llm_provider_generate_article = gemini，其余九个 worker 没有单独配， 走「默认提供商」也就是 gemini；llm_concurrency = 3、 llm_requests_per_minute = 18；夜间备稿 task_generation_daily_enabled = true、 04:00。
    • 原先记着的「两处指着不存在的东西」2026-09-21 实查已经不存在了： 那台的 llm_thinking_generate_article 是 off、review_translate_provider 是 gemini， 两处都对。留这一句是因为这份文件上一版说反了——照着它去「修」会改坏正确的配置。
    • 夜间备稿现在可以安心开着：从前两台各自 04:00 生成会让 content.db 静默分叉， 所以 r5s 那份一直故意关着；现在只剩一台，那个理由消失了。 但做数据大动作时仍然要先关（比如 P10 的全语料重标注， 不关它就是一边清洗一边进新文章，把靶子搞成移动的）。
    • 它必须配 p1b-2 提示词才能用：同一个模型，旧提示词 0/10 合格、超纲中位 5.82%， 新提示词 7/10、0.56%，与 gpt-5.5 当年的 8/10 / 0.39% 基本持平。 差别全在提示词上，不在模型上。五版实测与三条要打的折见 phase-4.html §4 末节。
    • 关思考对它无效：那个网关忽略 enable_thinking，拨哪边结果都一样。 「切模型必须关思考 ＋ 给足预算」那条是对中转站的 deepseek 说的，别照搬到这里。
    • 标注这一路 2026-09-20 测了（P10），结果要记住： 它比当年标全语料的那个模型爱说「没有贴合的义项」得多—— 同一篇文章、同一套义项集，gemini-3.8-flash-high 给 4.6%， 而库里旧标注留下的基准是 0.6%（那是中转站的 deepseek 标的）。 这不是义项集的锅：拿旧义项集配这个模型重标一遍，还是 4.6%。 调批次（35→12）和调候选顺序都试过，都在噪音范围内，两个假设都被自己的实验推翻。 决定是接受它——填 0 是安全的失败（读者退回去看词典）， 而硬选一个错义项才是这个项目最怕的事。详见 phase-10.html §13③。
    • 造例句这一路仍然没测过，只是跟着默认提供商走到了它身上。质量存疑先查这里。
    • 标注的批次大小，实测对质量没有可辨别的影响（2026-09-21 定案，前一天的结论已推翻）。 关键是先量噪音底数：temperature=0.1 不是 0，同一篇文章、同一个配置跑两遍， 一致率 99.3%、单边作答 5 对 1。而批次 35 对 100 是一致 97.5%、单边 1 对 8， 再跑一遍变成 8 对 2——方向都能反过来。
      所以配置间的差异淹没在模型自身的随机性里。 2026-09-20 我记过一串「12 → 5.6%、35 → 4.2%、400 → 0.7%」的曲线并写成「越大越准」， 那是单次测量、没有对照，读的是噪音。坑 §4.3 的第三个实例，这次是自己造的。
      既然质量无差别，就按成本选：批次 400（整篇一次，最长的文章 328 个实词） 要 405 次调用，批次 35 要 2,157 次。用 400。

    • 标注不吃推理，吃注意力，所以不能降档（同日实测，批次 100）： flash-high 4.6%、flash-medium 5.2%、flash-low 6.5%，而且 medium 最慢。 它的任务形状是「从列表里挑一个编号」，但要在几百条候选里保持注意力—— 那正是低档模型先丢的东西。

后台任务与等待

批量任务动辄跑几十分钟，必须放后台。等待它的方式犯过两次同一类错误，见「踩过的坑」§7.2。

  • 查状态优先查数据库，不要轮询日志文件。 批次任务表里就有 status 和 done/total （llm_jobs），那是权威来源，也不会被清理脚本删掉。
  • 等待循环必须有超时上限，超时就退出并说明情况。绝不写没有出口的 until … do sleep。
  • 清理放在最后一步。 还有东西在监视某个文件时，不要删它。
  • 任务结束后确认没有残留进程——收尾时顺手查一次，不要留给用户去发现。 按 CPU 查，也要按运行时长查：远程执行的活干在别人机器上，本地那条 ssh 的 CPU 时间几乎是 0，只有 ELAPSED 会露馅（2026-09-20 栽的，见「踩过的坑」§7.3）。 Mac / Linux 上 ps -Ao pid,etime,%cpu,command，Windows 上 Get-Process | Where-Object { $_.CPU -gt 60 }： 名字是猜的，而跑飞的往往正是那条你以为无关的一次性命令。 2026-09-12 栽过一次，见「踩过的坑」§7.3。另：Windows 上别写 find /，它会扫遍所有盘。

日志与代码规范

迁移时核对了 backend/core/logging.py 的 get_connection("events")：决策日志写入 events.db。旧文档 learning.db 的说法已订正。

日志的设计目标是：用户说"不对劲"时，AI 能查出来到底怎么了。

  • 三类分开：技术日志入 logs.db（30 天轮转，可丢弃）；决策日志入 events.db（长期保存，记录每次判断的输入、候选、理由）；业务记录本身就在业务表里，不重复记。
  • 事件名是固定标识符，不是自由文本（article.generation.failed，不是"生成失败了"）。这样才能精确过滤和统计。
  • trace_id 贯穿一次请求或任务，并出现在错误响应里——用户复制给 AI 就能定位完整链路。
  • DEBUG 平时只在内存滚动，发生 ERROR 时自动落盘该 trace 的详细记录。
  • 语言：事件名和字段名英文，说明文字中文，原始报错原样保留。不做"人话翻译层"——用户有疑问直接问 AI。
  • 通知：Bark，仅推生成失败 / 服务异常 / CRITICAL，带去重。
  • API 密钥一律不入日志。
  • 注释用英文，与标识符同语言。项目特有概念在模块头部给中英对照（如 target word 目标词 / incidental word 附带词），以便和中文设计文档对上。
  • 注释解释为什么这么做，而不是复述代码在做什么。用户不读代码，注释是写给未来接手的 AI 看的。 但注释描述的是意图，不保证实现跟上了——读代码时别拿它当实现的描述，见「踩过的坑」§7.1。
