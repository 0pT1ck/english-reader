§2

API 集成

支持哪些提供商

以 OpenAI 兼容格式为主。DeepSeek、Kimi、通义、智谱、豆包以及各类中转服务都提供兼容端点，支持这一种就覆盖了绝大多数模型——配置一个模型只需填 base_url + api_key + model。另外单独支持 Anthropic（格式不同但值得单列）。

密钥单独存放 —— 有安全含义

密钥不能进 learning.db。那个库有「下载备份」按钮，会被发到别的机器、发给排查方。密钥躺在里面等于每次备份都在传播它。

所以存 data/secrets.json：不进 git、不进备份、不进诊断包。管理控制台可编辑，用户不必手改文件。日志层已有的脱敏规则（secret / token / api_key 一律替换）在这里正好生效。

批量任务基础设施

几千个词跑几小时，需要：任务队列、进度可见、断点续传、失败重试、成本累计。

这套东西每晚预生成文章也要用——那是同一种长时间批处理（后来是 P4）。所以它不是一次性工具，要做成通用的：一张任务表记录批次状态，控制台一页显示「在跑什么、到第几个、花了多少、失败几个」，中断重启接着跑。

成本要有个数，更要有个闸

义项集是 P1b 唯一的大额开销。按十个词一批估：约 280 次调用，输入合计 40–50 万 token，输出 50–60 万 token。国产主流模型量级在十几块钱，海外旗舰模型量级在几十到一百多。词族补漏几百个词、188 条词缀翻译，都是零头。

数字本身不重要，重要的是批量任务必须能设花费上限——到线就停下等确认，而不是闷头跑完。正式跑之前先拿 20 个词试跑，用实测单价反推总价再决定全量。

密钥防泄漏要改成白名单

诊断包现在是黑名单：admin/routes.py 里显式 pop("bark_url")。加了提供商配置以后，只要有一个密钥字段进了 runtime_config 而不是 secrets.json，它就会随诊断包一起发出去。

改成在配置项声明处标 secret=True，由导出层统一排除。以后加配置不会漏掉这一步。

§3

词典缺陷

5 项

第一轮实验里 127 个「超纲词」，绝大多数是假的。在这样的数据上建任何统计都不成立。

缺陷症状修法
转义未处理 释义存的是字面 \n 两个字符，用户点词会看到 n. 州\na. 国家的 已修，导入时还原转义并重新导入
派生形式 planning / carefully / participant 未归到词根，误判超纲 由 §5 的词族关系解决
兜底造出不存在的词 other → oth。lemminflect 把 -er 当比较级剥掉，spaCy 给的 other 又不在它的候选里，于是代码采信了候选第一名——一个根本不存在的词。P1a 十六篇里出现 4 次 候选必须在词典里查得到才采信，查不到就退回 spaCy 的结果，再不行用原形。改 analyzer.py:187 那一行
连字符复合词 socio-economic 被切成 socio + economic，前者查无此词 分词时保留复合词，查不到再拆开分别查

§4

义项集

P1b 的主体

覆盖范围：粗筛后 3586 个词，全部建

目标词共 7226 个——所有带大纲标签且有词频的词，中考和高考层级也算在内。 这一条是实施时改的：原方案只取 CET-4/6/考研的 6052 个，结果 present、 spring、bear、run、set 全被排除在外， 因为它们只带中考/高考标签。而熟词僻义正是长在这类词上的——认识 bear 是「熊」，不等于认识「忍受」「支撑」。详见 §11。

按词典释义的结构粗筛（数字为实测）：

类别数量处理例
多词性 · 强候选1437建state, part, issue, power
双词性 · 待判1789建might, provide, social
单词性多义360建system, business, art
简单 · 跳过3640免费排除against, happen, area, fact

一半靠词典结构就能排除，不花钱。剩下 3586 个一次建完，不留按需补建的尾巴。

但要留一个补建单个词的入口。粗筛的判据是 ECDICT 的释义结构，而 ECDICT 的释义质量参差，漏判一定会有。控制台上一个「给这个词补建义项」的按钮，一次几厘钱；没有它，漏掉的就永久漏掉了。

粒度规则

合并的依据是英文里是不是同一个概念，不是中文翻译是否相同。

✓合并：present 的「提出 / 介绍 / 呈现」——英文都是 to show or give something to someone，中文因搭配习惯译成三个词
✓拆开：address 的「地址」和「着手解决」——概念完全不同
×不要因中文有两个说法就拆
×不要因词性不同就拆：address 作名词「地址」和作动词「写地址」是同一概念

一句话判据：记住其中一个意思之后，遇到另一个用法能自然理解就合并，会理解错就拆开。这比「概念边界」具体，模型执行时歧义更小。

每个义项包含什么

字段说明
英文概念定义义项的身份。用最常见 2000 词写，读定义时不会撞上新生词
中文投影2–3 个不同语境下的中文说法
常用度序号哪个是主义项
主题标签社会 / 科技 / 文化 / 日常生活 / 环境 / 经济 / 教育 / 健康 / 心理 / 历史，或「通用」

主题标签是搭车产出——本来就要为这几千个词调 LLM，多返回一个字段几乎零成本，却同时解决了 §6 的选词问题和 B6 的主题控制。

例句：惰性生成，搭车批处理

建义项集时不生成例句——几千个词全配例句，大部分永远不会被复习到。

改为：某个义项即将出现在复习卡片上时，先查有没有例句，没有就生成 1–3 条，并入夜里生成明天文章的那次批处理。那个时点正好已经算出明天的到期队列，不增加任何新的调用轮次，成本按实际需要分摊。

例句和原句分工不同：原句来自你真实读过的文章，带语境记忆，复习时优先用；例句是干净的典型句，补两种缺口——这个义项还没在文章里遇到过，或者遇到过但那句不够典型。

P1b 只做到一半：建表、写生成函数、留好调用入口。真正的触发时机挂在到期队列（后来是 P3）和夜间批处理（后来是 P4）上，那两样现在都不存在。所以 P1b 的验收不测例句，别把它当成这一阶段的交付物。

存放：新建第四个库 content.db

义项、例句、词族关系、词缀表都进它。

不能放 dictionary.db——那个库的定位就是「可丢弃、可重建、不备份」，backup_learning_db() 根本不碰它。把花钱生成的东西放进去，等于放在一个设计上随时可以删掉的地方，一句「不得清空」的约定挡不住误删和硬盘故障。也不放 learning.db——那是你的行为数据，和买来的内容混在一起，边界会越来越糊。

四个库正好按「丢了会怎样」分成两类：必须备份——learning.db（你的记录）与 content.db（花钱买的内容）；不用备份——dictionary.db（ECDICT 可重建）与 logs.db（可丢弃）。控制台的备份和恢复要同时覆盖前两个。

质量验证：三层，全自动

1格式校验 义项数是否合理——一个词划出八个义项基本是粒度失控。
2定义用词校验 英文定义有没有超出 2000 词范围，用已有的校验器。
3真题覆盖验证 拿 452 篇真题里该词的实际用法，看能否在义项集中找到对应项。找不到说明有遗漏；某义项在 452 篇中从未出现，可能是多余的。用已有数据，客观且免费。
§5

词族与构词分解

它和「派生形式未归到词根」那个缺陷是同一件事的两面，一起做。

数据源：词缀表可用，例词不够

ECDICT 仓库的 wordroot.txt 有 611 条：423 词根 + 110 前缀 + 78 后缀，每条带含义、类别、例词。词缀部分直接可用，只缺中文说明（原文是 state or quality of 这类英文），188 条一次性翻译，成本可忽略。

但它的 6716 个例词只覆盖我们目标词表的 30%，不足以直接建立所有派生关系。

三步，绝大部分免费

1导入 188 个词缀 + 翻译中文说明 一次性，成本可忽略。
2算法剥离建立派生关系 剥掉后缀，看剩下的是不是词典里的词且词频更高。需处理拼写变化：happy+ness→happiness（y→i）、nature+al→natural（去 e）、run+ing→running（双写）。规则有限且确定，不花钱。词根表的例词正好当交叉验证。
3LLM 补漏 不规则派生（deep→depth、strong→strength）估计几百个，成本很小。

三档划分 —— 屈折与派生必须分清

档例处理
A 完全归并 carefully ← careful
happiness ← happy		 语义完全透明、仅词性转换。不算生词——认识原形就一定认识它。这一档正好修掉第一轮的误判
B 轻量目标词 national ← nation
nationality ← nation		 语义基本可推但有具体化。按 C2：给构词提示、算三分之一名额、不进完整复习队列
C 独立词 depart ← part
recover ← cover		 语义已漂移。当作普通生词，不做构词提示——提示了反而误导

A 档的「归并」只影响判定，不影响记录。carefully 不算生词、不占目标词名额、不进复习队列，但它的遇见记录仍按 carefully 自己记，点词时显示它自己的释义加一行构词说明。这一点现在就要定死——存储形态拖到 P2 再改，代价大得多。

§6

生成质量的四条改进

① 零超纲 —— 修正了 P1a 的结论

P1a 曾据「真题有 10% 超纲」推论生成文章也该有。那是错的，因为它又把「像真题」当成了目标。两条内容线的目的不同：

目的超纲词的角色
生成文章精准投放目标词与复习词，把每个生词都搞懂干扰项：学不会，还占注意力
真题直读接触真实语料，练「遇到不认识的词怎么办」必需，那本来就是真实文本的样子

生成文章目标为零超纲，专有名词除外。可行性：P1a 实测 1–9%，而那些「超纲词」绝大多数是 §3 的五个缺陷造成的假象；修完后真实超纲率约 1–2%。

零是目标，不是废稿线。真要把每篇都压到零，需要「校验器报告 → 定点重写那几个词 → 再校验」的收敛回路，那是 P1c。P1b 交付的是把真实超纲率压到 2% 以下，并把剩下的一两个词显式标注出来：阅读界面上标明这是超纲词、暂时不用学会，给中文意思让句子读得通，但不计生词率、不进复习队列（主文档 C10）。

这比为一两个词重生成整篇划算，也比悄悄放过去诚实——不标注的话，那些词会被当成该背的词去啃，正好是要避免的注意力浪费。

② 要求内容具体 —— 这才是像不像范文的真正原因

P1a 观察到「超纲率低的文章像作文范文」，但那是把两个独立变量混为一谈。ChatGPT 那篇像范文是因为通篇抽象论述，没有一个具体事实；通义千问那篇像真题是因为有十九世纪的具体场景和细节。跟超纲率没有因果关系——用最简单的词一样能写出有血有肉的文章。

所以提示词里要加的是：必须包含具体的例子、场景或数据，不要通篇抽象论述。宁可讲一件具体的事，也不要罗列三条空泛的道理。

③ 抑制 AI 写作指纹

P1a 测出三项偏离：被动语态偏少四成、名词化偏多四成、形式主语几乎不用。针对性加三句定性要求，不给具体频率（「每篇至少四处被动」会让文章别扭）。校验器本就把这三项与真题基线并列显示，第二轮跑完一眼能看出是否改善。

④ 目标词按主题成组

随机抽八个不相关的词（anchor / humor / wagon / robe）逼得模型硬凑。改为：先定主题 → 从该主题词里取 3–4 个 → 用无主题的通用词补足到 8 个。主题标签由 §4 搭车产出。

主题偏好：社会、科技、文化、日常生活优先，其余题材照常出现但权重低。

词典缺陷：四个变五个

动手时查出第五个，而且是最隐蔽的一个：oth 不是解析残片，是 other。 lemminflect 把 -er 当比较级剥掉得到 oth，而 oth 恰好在 ECDICT 里 作为缩写存在，所以「候选必须查得到」这条守卫拦不住它。

改成：两者都认可就用 spaCy；spaCy 的答案本身是个真词就用 spaCy；只有 spaCy 给出的不是词时， 才轮到词形表决定。spaCy 读过整个句子，lemminflect 只看到一个词性标签——谁更可信本来就有答案。 leaves→leaf、left→leave、mice→mouse 全部不受影响。

英美拼写：问题不是词缺了，是标签被拆开了

ECDICT 两个拼写都收，但把大纲标签随机分给了其中一个：

词标签另一拼写标签
neighborky toeflneighbourzk gk cet4 cet6
theaterky toefltheatrezk gk cet4 cet6 ielts
colourzk gkcolorcet4 ky ielts

所以修法不是「美式转英式」，是把两个拼写当成同一个词，标签取并集。 配对靠规则生成候选，再过两道关：候选必须在词典里，且两者的中文释义必须有共同词条。 第二道关是关键——只靠规则，size 会配到 sise（人名）、 member 会配到 membre（比利时地名），两个都真在词典里。 真正的拼写对必然共享释义，巧合从不。

新增一类：已知词根的派生词，单独计

这是方案里没有、但做下来发现必须有的一档。cooperation 的词根 cooperate 是四级词，把它算成「超纲」既不公平，也让「零超纲」这个目标失去意义——按设计它本来就是 B 级轻量目标词：给构词提示、算三分之一名额。

所以校验器现在报两个数：超纲（真违规）和已知词根的派生词（合法内容）。 十六篇实测：超纲 1.69%，派生词 0.79%。

词族：规则一遍跑完，免费

35,215 个常用词里找到 10,471 条派生关系，用时 2.7 秒，零成本。分档：A 3778 / B 5974 / C 719。

精度靠三道守卫，缺一不可：词根不能比派生词更冷僻（否则 mother ← moth）、 词根词性要对（否则 early ← ear + -ly、matter ← mat + -er）、 词根必须是大纲词或频率相当（否则 reply ← rep）。 49 个陷阱词测试零误判，16 个应分解的词零遗漏。

模型只做规则做不了的事：判定语义距离（A/B/C）、写中文构词说明、把规则找错的关系降为 C。

粗筛：2962 个词需要建，不是 2766

目标词总数 6052 与方案一致。分类阈值实现时写死为「≥3 个词性 / 2 个词性 / 单词性但 ≥7 条释义」， 比方案估算时多留下约 200 个词。多花的钱有限，宁可多问不要漏。

这两个数后来又变了。跑完第一轮才发现目标词集合本身漏了熟词僻义， 补进中考/高考层级后是 7226 个目标词、3586 个需建——见 §11。

另外按 §4 的意见留了单词补建入口：控制台上填一个词、一键排队，几厘钱。

顺带修掉一个 P0 遗留的 bug

core/events.py 里 log.debug("event.unhandled", …, event=name) 与 logger 自己的第一个参数重名，只要 emit 一个没有订阅者的事件就抛 TypeError。 P0 一直没触发是因为当时唯一的事件正好有订阅者。批次任务跑完 emit 完成事件时撞上了它， 整个任务被标成 failed。

与方案的其他出入

·备份改成 zip：两个库必须一起走，只恢复其中一个会得到一个半残的装置。 恢复端同时收 zip 和单个 .db，后者按里面的表判断是哪个库，不看文件名。
·花费上限会略微超出：一次调用的花费要等它返回才知道， 所以上限是「发起前检查」，最多超出并发数减一次调用的量。已写进配置项说明。
·任务计数改成重算而非累加：失败项重试成功后，累加会同时留下一次失败和一次成功， 成本统计随之虚高。改成每次从任务项汇总，代价是一条带索引的聚合查询。

§10

第一次接真模型跑出来的问题

2026-09-06

四个都是「本地测不出来、一接真模型就全灭」的那种，记下来免得再踩。

① 思考型模型把输出预算烧在思维链上

第一个批次任务八项全部失败，报「回复里没有找到 JSON 对象」。查下来： 用的是 qwen3.8-27b，3 个词缀的回复只有 68 个字符，却花掉 376 个输出 token。 25 个词缀一批时，1500 的上限全部用在思考上，finish_reason=length， 可见文本是空字符串——于是解析器如实报告「没有 JSON」，而真正的原因被埋掉了。

改法不是让调用方去猜一个数（那个数取决于配了哪个模型），而是撞到截断就把预算翻三倍重试， 上限 16000。一次短调用就能试出来，换任何模型都自适应。同时把 finish_reason 写进错误信息，不再让它伪装成解析失败。

② 失败的任务项没留下模型的回复

这是上一条难查的直接原因。代码注释里写着「原样保留回复以备审计」， 但只在成功时保留——失败时 outcome 是 None，回复就丢了。 「没找到 JSON」而拿不到那段没有 JSON 的文本，只能手工把调用复现一遍， 而任务记录存在的意义正是让人不必这样做。

现在失败项也存回复，控制台任务行上多了「看失败原因」，展开就是模型原样返回的内容。

③ 不要让模型回显复杂的键

词缀表的键长这样：a-1, an-1、able, -ible, -ble、 circu-, circum——188 个里有 73 个带逗号或消歧编号。 提示词让模型用词缀本身当 JSON 的键，它当然复述不出来，于是回复解析成功、匹配却全落空。

四个任务全部改成按行号回答：调用方本来就知道第几行是什么， 没有任何理由要模型把标识符抄一遍。另外每个任务都加了「一条都没对上」的显式失败， 不再出现「成功但什么也没写入」。

④ 词缀表的键本身就是坏的

更要命的是这些键会直接毁掉查询：构词分解产出的是 -able， 而表里存的是 able, -ible, -ble，永远查不到。P2 的构词提示会整片失效。

导入时改成按逗号拆成多条、去掉连字符和编号，611 条源数据展开成 1068 行 （前缀 118 · 后缀 98 · 词根 852）；同一个词缀合并释义而不是相互覆盖。 另外 affix_gloss() 现在必须区分前后缀——al 既是同化的 ad-（朝、向）又是形容词后缀 -al，答错一个就是在读者面前放一句明显错误的解释。

由此得到的一条使用建议

思考型模型（名字里带 thinking / R1 / qwen3 这类）跑这些机械任务时， 把每次调用的条数调小：实测 25 条会让中转站 504 超时，10 条 23 秒稳定通过。 批量大小现在是任务参数，控制台上可填。这类任务本来也不需要推理能力—— 真正需要好模型的只有义项集。

跑起来才暴露的两个 bug

限流。模型太快，并发 3 一分钟能发九十次请求，中转站的额度是 20，于是大批 429。 加了「每分钟最多调用次数」的前置限流（先排队再发，而不是被拒后回退）， 并且改成听服务端的 retryAfterSeconds——自己猜一个更短的等待时间， 只会再浪费一次调用。设成 18 次/分钟后失败归零。

诊断脚本会把正在跑的任务标成暂停。recover_interrupted() 挂在模块启动钩子上，而任何脚本只要 import 了应用就会触发它—— 它假设自己是唯一的进程，于是一边跑长任务一边查状态时，查询把任务写成了 paused。 改成只重置五分钟没动过的行：任务每处理一项就更新一次，动着的行不会被误判。

粗筛漏掉了熟词僻义，这是设计层面的错

第一轮跑完发现 present、spring、bear、 run、set 都没有义项集——它们只带中考/高考标签， 而目标词集合当时限定在 cet4/cet6/考研。

这正好把系统要教的东西筛掉了。认识 bear 是「熊」， 不等于认识「忍受」「支撑」「结出」；熟词僻义是 CET 阅读考得最狠的地方， 主文档 §C 就是这么写的。而设计文档里用来讲合并规则的例子 present， 居然不在集合里。

「零失败」是个假象，已经修掉

第一轮任务报告 368/368 失败 0，同时有四百多个词一条义项都没有。 原因是判据太松：一批八个词，存下至少一个就算这批成功。而模型每批稳定漏答一两个， 实测完整返回的批次只有 79%，平均每批回 6.6 个词——最差的一批八个词只回了一个。

所以那四轮补漏不是谨慎，是第一轮实际只完成了八成。改法两条： 返回不全就判失败，让它重试而不是记成功；重试时只问还缺的词—— 一批八个只缺一个时，重问整批有七八成是白花的钱。

造一个「只答一半」的回复验证过：现在会拦下来，报「这一批 2 个词只返回了 1 个，缺 [...]」。
