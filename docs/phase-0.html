八项技术定案

已充分讨论
议题结论
语言与框架 Python + FastAPI。决定因素是词形还原的精度，附带白送 OpenAPI 契约文档。硬件（4GB / 1TB SSD）让 Python 的劣势全部不成立
词典数据源 ECDICT——唯一同时提供大纲标签、词频、中文释义、词形变化的开源数据集
词形还原 spaCy + lemminflect，带词性消歧；ECDICT exchange 字段交叉验证。只在文章入库时跑一次，运行时不碰 NLP
数据库 SQLite，三个独立文件：dictionary.db（只读可重建）/ learning.db（要备份的全部学习数据）/ logs.db（可丢弃）
API 约定 /v1/client/… 与 /v1/admin/… 完全分离；单向数据流；错误响应带 trace_id；只增不减的兼容规则
项目结构 模块自包含，core/ 提供框架能力，modules/ 放功能。git + GitHub 私有仓库，数据文件不进版本控制
运行方式 开发直接跑 Python，部署用 Docker 多架构镜像。数据库文件挂载宿主机
日志 技术日志 / 决策日志分离；固定事件名 + trace_id；ERROR 时回溯转储 DEBUG；Bark 通知
§2

要建的东西

10 项

前五项是框架能力——它们的存在意义就是让后面每一个 Phase 加功能时不必重复造轮子。

B1 配置系统

所有参数（目标生词率、每日新词上限、生成时间、日志保留天数、代理地址、Bark 链接）集中管理，可从环境变量与配置文件读取，可在管理控制台修改。

为什么在 P0：后面每个 Phase 都会引入新参数，没有统一入口就会散落成硬编码。

B2 日志系统

结构化日志，五个级别，固定事件名，trace_id 贯穿。技术日志入 logs.db 按天轮转保留 30 天；决策日志入 learning.db 长期保存。DEBUG 平时只在内存滚动，遇 ERROR 自动落盘该 trace 的详细记录。

为什么在 P0：后补日志意味着回头改所有代码；而且它是此后每个 Phase 的调试依赖。

B3 事件总线

系统在关键节点发出事件，新功能通过订阅接入，不修改原有流程代码。P0 只建机制并跑通一个示例，具体事件由各 Phase 自己定义。

为什么在 P0：大部分新功能本质上是「在某件事发生时顺便做点什么」，这个机制把接入成本压到最低。

B4 模块注册机制

一个功能模块自带数据表、API 路由、管理页面、后台任务、配置项。在一处登记后自动挂载，无需修改路由表、菜单、任务列表。

B5 数据库迁移机制

版本化迁移脚本按顺序自动应用，升级前自动备份 learning.db。

为什么在 P0：learning.db 里是不可再生的真实学习记录，而后面每个 Phase 都要改表结构。没有迁移机制就是每次手动改表，一旦出错数据就没了。

B6 三个数据库与初始表结构

建立三个库，以及 P0 阶段确实需要的表：词条、义项、词族、迁移版本、日志。

注意边界：义项表和词族表只建结构，不填数据——数据要靠 LLM 批量生成，那是 P1 的事。

B7 词典数据导入

下载 ECDICT，清洗后导入 dictionary.db：拼写、音标、词频排名（BNC / 当代语料）、大纲标签、中文释义、词形变化。建好索引。脚本可重复执行。

B8 词形还原能力

接入 spaCy + lemminflect，输入一段英文，输出每个词的位置、表面形式、词性、词条，并标出专有名词。ECDICT exchange 字段用于交叉验证与兜底。

这是 P0 完成定义的核心，也是 P1 文章校验的前置依赖。

B9 API 骨架

/v1/client/… 与 /v1/admin/… 分离；设备令牌与管理密钥两套认证；统一错误响应（错误码 + 中文说明 + trace_id）；OpenAPI 契约自动生成并可访问。

P0 只有健康检查和词汇查询两个真实接口，其余是骨架。

B10 管理控制台骨架

服务端渲染，零构建链。P0 阶段包含四页：登录、系统状态、日志查询与导出、数据库备份下载与上传。另含 Bark 配置与测试发送。

为什么在 P0：它是此后所有 Phase 的诊断通道和备份入口，越早有越省事。

新增一个功能就是在 modules/ 下加一个目录并登记，其余全不动。这条是 P0 验收项之一，要现场演示。

§4

P0 明确不做

防止跨 Phase

下列每一项都属于后续 Phase。P0 阶段即使「顺手就能做」也不做。

×文章生成与校验——整条生成管线属于 P1，包括调用 LLM。
×义项与词族的数据生成——P0 只建表结构。批量生成要调 LLM，属于 P1。
×任何学习逻辑——水平估计、选文、复习调度、难度计算，都归后面的学习类 Phase。
×阅读界面——点词查词、标记生词属于 P2。
×今日包与事件上报的业务实现——P0 只定接口形状与认证骨架，实际内容属于 P2。
×结构化数据导出——P0 只做整库文件的下载与上传。JSON 导出没有排期（主文档 §M）。
×真题语料——获取、清洗、义项统计属于 P1。
×iOS 客户端——属于将来的原生端。

09 错误可追溯故意触发一个错误，响应中带 trace_id，用它能在日志里查到完整链路，且 DEBUG 详情被自动保留。
§6

留到后面的问题

P1词性标注误差的实际影响——Turn left at the corner 中的 left 被标注为动词，因而归到 leave。属小语言模型固有精度，非消歧逻辑问题。待 P1 用真实生成语料统计发生率，再决定是否值得换更大的模型（代价是体积与 ARM 上的速度）
P1义项集的粒度标准如何落成可执行的生成提示——中等粒度、按英文概念边界，需要实际跑几批验证一致性
P1真题语料的获取与清洗途径，尚无现成资源
P1英文释义所用的受限词汇表如何随水平提升重新生成
P2今日包的具体字段与事件类型清单
P3初始词汇量测试的题量与词频分段
以后结构化导出的格式与跨版本兼容策略
