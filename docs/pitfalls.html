零、四条元教训

底下 27 条里反复出现的其实就这四个形状。新坑八成还是它们。

  1. 已知答案的样本一直在手边，却没去对。 同一个 tags 字段栽了四次（§5）。 labor / labour 对一下就当场露馅，而它安静地过了整整一个阶段。
  2. 让模型「找错」是生成任务，它会编造；让它判断具体对象是封闭任务，它很准。（§1） 开放式提问有产出压力，模型总能挤出点什么。
  3. 一个测试在已知好的样本上报零，不等于它有效——还得看它在已知坏的样本上报不报。（§4） 阴性对照 + 阳性对照，缺一个都得不出结论。
  4. 注释、方案、字段名说了什么，不等于代码做了什么。（§7、§6） 一段解释性的注释会让人以为对应的代码在那儿，读代码时就跳过它了。

一、改提示词前

§1.4 保留的是 2026-09-09 的实验原始记录。词组清单已在 P11 重建，不能把旧 P2 §18 的覆盖数字当现状；现行判据见 P11 §2、§9。

1.1 模型对提示词里的数量约束基本无感

症状：「不要超过五六处」无效（反而更高）、「至少用一两处」无效、义项集那次「合并成 3-5 项」也无效（给了 7 项）。 原因：数量是模型算不出来的东西，它只能大概比划。 正确做法：说清楚「什么时候该用」。被动语态就是靠给条件 + 写完自查，从 30.8 降到 15.5 的。 2026-09-16 第四个实例，也是最值钱的一个：用词上限写成「限制在最常见的约 4000 个英语单词以内」， gemini-3.8-flash-high 十个种子零合格、超纲中位 5.82%。 换成它认得的类别——「四级大纲以内，六级／考研／雅思托福 GRE 才学的词一个都不要用」—— 同样十个种子 7/10、0.56%，与 gpt-5.5 持平，命中率还升了。 它不是不守规矩，是感觉不到 mechanism、municipal、rigorous 难，直到你说这些词属于哪一级。 配套还有两段各自有效、合起来更有效的：给一张越界词对照表（16 个词各配一个替代说法）、 要它写完逐词自查。三段单独是 2.12 / 3.28 / 3.67，合起来 0.88。互补，不是同一句话说三遍。 顺带一条反向的教训：压住抽象词之后，剩下的越界词全变成 storehouse、smokestack 这类具体名词， 而「必须写具体的事」是另一条硬要求——所以那一段必须给出口而不是下禁令， 否则模型会靠把文章写空来守规矩。 守卫：无。改提示词时只能靠这条。数据在 phase-4.html §4 末节。

1.2 一个错误的度量比没有度量更危险

症状：「形式主语几乎为零」，为此改了三轮提示词。 原因：校验器在数 there be——spaCy 只把 there is/are 标成 expl，It is clear that… 里的 It 是普通 nsubj。 改对之后真实值 8.91、基线 5.6，一直是偏多而不是为零。 正确做法：改代码前先验证指标本身在数什么。 守卫：无。见 §4.2 的通用做法。

1.3 绝不让模型「找错」，只让它逐句做封闭判断

症状：问 deepseek-v4-flash「找出这篇文章里不地道的搭配」，它给考试委员会审定的真题判出均值 5.1 个「问题」 （exerting influence on 要改成 having influence on、gap remains yawning 要改成 wide）。 原因：开放式找错是生成任务，模型有产出压力。 正确做法：换成逐句的封闭判断——「这句话里的搭配，母语者会这么说吗？」 种下已知错误（真题句里 make a decision → do a decision）的对照测试里 8/8 全中、零误报。 守卫：无。这条是 B3「过量生成择优」的方法基础，写在主文档 §B3。

1.4 同一条的第二个实例，比第一个更干净（2026-09-09）

症状：让 deepseek-v4-flash 通读一篇六级真题、「指出文章中所有的词组」，同一篇跑三次： 提出 37/28/34 个，并集 50、交集 19，稳定率 38%；只有 21/50（42%） 在 318,207 条词典里查得到； 23 个在原文里根本找不到那个字符串（a you-and-me-against-the-world principle、strategic calculations、the cries of）； 而且连现有流水线已知的 13 个都漏了 3 个。 对照：同一篇上，放宽后的结构筛提出 28 个、全部在词典里、零编造，其中 16 个是现有筛子漏的。 正确做法：把候选锚在词典上——词典里没有的组合它一个都提不出来，没有编造的余地。 守卫：无。数据在 docs/phase-2.html §18。

二、调模型 / 换模型前

2.1 长文生成必须开流式

症状：写一篇 450 词的文章每次 524，而模型其实还在写。 原因：网关掐的是沉默，不是长度。gpt-5.5 要先思考约 109 秒才吐第一个可见 token，中转站在 120 秒掐断空闲连接。 正确做法：llm_stream 默认开（2026-09-09 加）。开了之后同一个请求 60 秒完成（453 词、超纲 0.85%、目标词 24/25）。 关掉它长文生成直接不可用。 顺带：中转站上非流式只有 minimax-m2.5 能写完整篇，但它目标词只命中 10/25、均句长 12.4； 其余模型把 2500 个输出 token 全烧在思维链上，正文 0 字。能写完和守约束是两回事。

2.2 思考型模型会「成功地」返回空正文——流式也救不了（2026-09-10）

症状：deepseek-v4.1-flash 写文章四篇全空。流是通的、finish_reason 也有，就是没正文。 原因：reasoning_tokens: 4000 / completion_tokens: 4000，delta 里只有 reasoning_content，content 一次都没出现。 正确做法：三条解法——预算提到 16000（12.9s）、enable_thinking: false（9.9s，最快）、thinking: {"type":"disabled"}（13.1s）。 排查手法记住：模型「返回成功但没内容」时，先把流里 delta 的字段名和 usage 打出来——reasoning_tokens 会直接告诉你预算去哪了。

2.3 别拿 star 数当权威依据

症状：fsrs4anki 有 4.1k star、py-fsrs 只有 481，差点据此选错。 原因：前者是给 Anki 用的 JS 调度脚本 + notebook（而且 FSRS 已内置进 Anki 23.10+，那个仓库对新版用户已无必要）， 后者才是能嵌进 Python 后端的库。star 差的是用户群大小，不是权威性。 正确做法：真正的权威证据是「FSRS 被 Anki 官方吸收成默认调度器」，外加公开的 SRS benchmark 和十几种语言的独立实现。 顺带：许可要逐个核对。py-fsrs 是 MIT；Anki 本身是 AGPL，绝对不能抄它的代码； 同一个组织（open-spaced-repetition）下的仓库许可不一，有 AGPL 也有 CC0、BSD。

2.4 别把「写文章」和「造例句」的横评结论搞混

症状：两次横评结论相反，容易记岔。 原因：任务大小不同——写 350 词整篇文章 vs 写一句话带一个指定的词。 结论：写文章 gpt-5.5 完胜（同一套提示词，超纲率 0.32% 对 deepseek-v4-flash 的 3.64%）； 造例句不适用这条（2026-09-09 横评 23 个模型）：合格率 92–100%，deepseek-v4-flash-0731 96% 反而高于 gpt-5.5 94%。 顺带：deepseek-v4-flash 那次横评 20 个模型的结论是数据整理要的是不思考的模型—— 思考型模型把输出预算烧在思维链上，强模型反而在中转站的 180 秒网关超时里跑不完。

三、写管理页 JS 前

3.1 hidden 在管理页里不一定隐藏得了

症状：设了 el.hidden = true，按钮失效了但没消失——「看得见却点不动」，代码全对而屏幕在骗人。 原因：base.html 给 button 设了 display: inline-block，优先级高过浏览器自带的 [hidden] { display: none }。 正确做法：已在 base.html 加 [hidden] { display: none !important; }。 这类最难查，因为没有任何东西出错。 守卫：verify_phase0.py 4.10。

3.2 管理页继承 base.html 的全局作用域，别用它已有的名字

症状：页面加载正常、之后每次点击都 404，症状看着还是「按钮点不动」。 原因：复习页定义了同名的 api() 走 /v1/client，被 base 那个走 /v1/admin 的覆盖。 已被占用的名字：api / toast / humanBytes。P2 的阅读页把 helper 叫 client() 所以没事。 正确做法：页面脚本一律包进 IIFE。 守卫：verify_phase0.py 4.9 会扫描并报出撞车。

3.3 Web 页的调试办法：抽出 <script>，在 node 里重放点击序列

症状：P3 人工验收时「按钮点不动」，猜了两轮都没找到。 正确做法：把 <script> 抽出来，配假 DOM 和假服务端，在 node 里重放点击序列。重放一次就看清了—— 包括「答案面板没打开时点『对了』照样会提交」这种眼睛看不出来的。 顺带：开发期的页面要 Cache-Control: no-store——缓存的旧 JS 看起来和「没修好」一模一样。

四、加验收项或新指标前

4.1 验收脚本不许依赖「今天碰巧有数据」

症状：verify_phase3 起初走当天真实的到期队列，于是复习做完之后再跑就一片红。 原因：只在某些日子能过的验收脚本等于没有。 正确做法：自己种探针、用完删掉，前后各清一次——中断的上一轮也不会污染下一轮。 2026-09-21 又一次，栽在「清理清单按形状列，而形状漏了一半」：fixture_events.py 的 FIXTURE_SHAPES 收着 v2-ph-mark-% / v2-ph-unmark-%，注释还写着「verify_phase2 词组那一节」， 而同一节里 v2-ph-seed-% / v2-ph-unseed-% 这一对从来没进过清单—— 于是那一节每跑一次就往 events.db 里留一条 come 的 study_states， 安静地待了一年，直到 P10 的 A13「学习记录已清空」把它照出来。 清理是按形状匹配的，所以漏一个形状就是永久漏，而漏掉的那部分不会报错。 加清理形状时去种探针的那处逐个数一遍，别照着已有的清单补。

4.2 任何新指标上线前，先拿一个已知答案的样本验证它数得对

症状：难度画像里的「超纲率」量出来四级真题比考研还难。 正确做法：真题的三个等级就是现成的已知答案，任何难度类指标都该先在它上面跑一遍，看单调性对不对。 （这次是在写进代码之前跑数才发现的；§1.2 那次是改了三轮提示词之后。）

4.3b 拿模型的输出做对比实验，先量噪音底数（2026-09-21）

症状：同一篇文章、同样两个批次配置，跑两遍，结论方向相反 （第一次「只有小批次作答 8 个」，第二次「只有大批次作答 8 个」）。 而我已经拿这种单次对比调了大半天批次，还把「批次越大越准」写进了 CLAUDE.md。 原因：标注调用 temperature=0.1，不是 0。模型输出本身带随机性， 而我从来没量过那个随机性有多大。 实测：同一篇、同一个配置跑两遍——一致率 99.3%，单边作答 5 对 1； 而跨配置（35 vs 100）是一致 97.5%、单边 1 对 8。 两者同一个量级，所以配置差异淹没在噪音里。 正确做法：任何拿模型输出做的 A/B，都要先跑 A/A。 那一趟给出噪音底数，没有它，A/B 的差值读不出意义。 工具在 scripts/compare_annotation.py，它的模块注释写着这条。 这是 §4.3 的同一个形状，第三次：前两次是「分不出对和瞎选」， 这次是「分不出配置差异和随机波动」——一个分不出两种情况的测量等于没有测量。 顺带：温度不为零时，「跑一次看看」永远不是证据，哪怕数字很好看。

4.3c 盲判的答案键写反过一次，而反常的数字早就在提示了（2026-09-22）

症状：P10 的 B3 新旧标注盲判，第一版结论是「旧的更好，48 对 19」。 原因：取样时 A/B 顺序随机，flip 为真时 A 装的是旧释义， 而答案键写成了 new="A"——整份结论反了。阳性对照那一半的键恰好是对的， 所以「判法分得出对错」那个结论不受影响，错的只有新旧归属。 怎么抓到的：不是复查代码，是交叉核对——reserve 的「（野生生物）保护区」、 approach 的「探讨；处理；对待」在新义项集里逐字存在，而我却把它们当成「旧标注」在报， 五个词五次逐字撞上。 本来早该露头：同一份脚本算出的长度基线说「新标注是更短的那个」（17%）， 而柯林斯的中文明明更长——我当时写了句「方向和我猜的相反」就放过去了。 正确做法：盲判类实验，答案键要用一个独立事实验一遍 （比如「被判为旧的那条，在新词典里存在吗」），别只靠读代码确认。 以及：反常的数字要当场追，不要记一句就走。 那句「方向和我猜的相反」 如果当场追下去，能省掉后面一整轮分析和一次错误的结论。

4.3d 对照逮得到抽样逮不到的东西（2026-09-22，P11）

症状：词组清单的 B 档（「柯林斯某一块的加粗串正好等于这个词组」）抽样 14 条全对， 于是当成干净的直接收了。后来种 30 条阳性对照去验判定模型，它把其中 6 条判成「不是」—— 查下去模型六条全对，错的是我的对照：as far as ＋ is concerned 是一个词组被分段加粗 （as far as 只是半个）、beside yourself with／beside the point 是两个词组挤在一块 而那块的中文只描述前者。两种都会让读者点开看到不是这个词组的中文。 原因：抽样只能告诉你「抽到的这些对」，而它抽不到你没想到的那一类。 对照不一样——它拿已知答案去问，答案不符就暴露出「我以为的已知答案其实不成立」。 正确做法：凡是「这一档我抽样看过，是干净的」这种判断，都要再种一次对照。 代价极小（这次 60 次调用），而它换来的是一个抽样永远给不出的结论。 顺带：对照不过关时，先别急着调阈值——先看是哪几条，很可能是对照本身错了。

4.3 阴性对照 + 阳性对照，缺一个都得不出结论

症状：搭配检查改好提示词之后真题和生成文都判成 ~0，看着像「文章没问题」。 原因：分不清是「没问题」还是「裁判瞎了」。 正确做法：补上阳性对照——拿真题句子把 make a decision 改成 do a decision 种个已知错误。 补上之后才知道模型是好的、问法是坏的。

4.4 验收脚本会往真实告警通道里灌假警报（2026-09-11）

症状：用户刚打开 Bark，当天就收到两条失败推送——任务失败：验收探针·失败、任务 probe.p4 的周期设置看不懂。 原因：verify_phase4 有两项故意制造错误来验行为（任务抛异常、周期写坏）， verify_phase0 也每次报一条 verify.failure 验追溯链路。这些都是 ERROR， 而告警处理器挂在 logging 上，于是原样推给用户。 为什么比噪音更糟：notifications.py 的设计第一句就是「一个狼来了的告警通道会被忽略」。 验收每跑一次推两条假警报，就是在亲手训练用户忽略它——而它是夜间任务失败的唯一出口。 正确做法：notifications.muted()，验收脚本整段包进去。两处刻意设计： ① 是进程内变量，不是配置项——用「跑前关掉、跑完打开」实现的话，脚本崩在中途就会 把告警永久关掉，而比误报更糟的失败模式是手机永远安静； ② 只静音推送，不静音日志，ERROR 照旧全量落盘，查得到。 守卫：无。验的时候要用阴性+阳性对照（§4.3）——只看「没推」分不清是静音生效还是推送链路本来就坏了。

4.4b 验收脚本会绊在自己刚制造出来的东西上（2026-09-12）

症状：verify_phase2 7.9「候选已逐处判断过」报「待判 5」。跑完之后再查，是 0。 原因：这个脚本自己会入库一篇文章，入库时结构预筛提出新的词组候选，而判词组是异步任务—— 脚本在自己刚制造出来的候选还没判完时就去数了。 正确做法：等，带上限。改成轮询到 0 或者两分钟超时，超时了把「等了两分钟还没判完」写进说明—— 那时它指向的是模型那条路断了，而不是代码坏了。 这一条和 §4.6 是一家：一个是脚本触发了真任务然后把它掐死，一个是脚本没等自己触发的任务。 共同点是「脚本自己动了手，又假装只是在观察」。

4.4c 「待人工」的项数变多，可能只是今天没数据（2026-09-12）

症状：verify_phase4 从「38 通过、2 待人工」变成「34 通过、4 待人工」，看着像回归。 原因：C3.1 离线补报与 C4.1 幂等要「当天有未完成的复习条目」才跑得动， 而我刚用命令行客户端把当天的复习做完了。脚本自己说了「当天没有未完成的复习条目，跑不了这一项」。 正确做法：这两项该自己种探针、用完删掉（§4.1）。在那之前，看到项数变化先读那一行的说明， 它通常已经告诉你原因了——别急着当成回归去查代码。

4.5 算法要用仿真验，单元检查查不出标定错

症状：FSRS 接线有两个错（把「一次过」当 Easy、没关掉自带 learning steps），在 1.1–1.6 全过的时候一直存在。 原因：它们不让任何东西报错，只让间隔排得不对——8→66→180 天，而正确的是 2→11→46→163→180。 正确做法：让仿真里的学习者按 FSRS 自己的曲线遗忘，消掉模型分歧，剩下的只有接线—— 实测到期可提取性 0.901 对目标 0.900，偏离 0.0005。 再换一个不同形状的遗忘模型，一次过率掉到 0.28——那不是 bug，正是 optimizer 存在的理由。

4.6 验收脚本会触发真实的定时任务，然后把它掐死在半路（2026-09-12）

症状：跑完一轮验收，verify_phase4 的 B5.1、B5.2 红了——「1 篇停在半路」「12 处待判词组」。 看着像刚改的代码碰坏了什么。 原因：验收脚本会 create_app()，于是定时任务循环跟着起来，夜间备稿正好到点触发， 真的生成了 3 篇、真的排了标注任务。然后脚本跑完退出，线程池关掉—— 任务当场 RuntimeError: cannot schedule new futures after interpreter shutdown， 判词组那个则永远挂在 running。花了钱，留下一篇打不开的文章，而验收把它报成自己的失败。 怎么认出来：先看 llm_jobs 的 error 列——这一条的指纹就是 after interpreter shutdown。 是环境不是代码，形状同 §1.2：别拿着它去改根本没错的东西。 收拾办法（也是正常的运维动作）：重启服务让 recover_interrupted() 把僵住的 running 收成 paused——但它有个 5 分钟的陈旧窗口，刚死的任务收不到，等一会儿再重启； 然后控制台重启任务，查 llm_jobs 等它跑完（有超时上限）。 没有守卫。真正的解法是让验收脚本别把真任务跑起来，但那是要改验收框架的事。 在那之前：跑验收之前先看一眼离 04:00 还有多久，以及跑完检查一遍 llm_jobs 有没有留下 running。

五、查词典 / 判大纲前

**这个字段栽了四次。**四次的共同点是：已知答案的样本一直在手边，却没去对。

5.1 第四次，也是最贵的一次（2026-09-09）

症状：阅读页把 quickly 标成超纲词，还说「不用学会」。 原因：「这个词在不在大纲里」有三个调用方——生成校验器算超纲率、入库打 beyond 标记、难度画像算超纲词比例。 三方各写了一遍，只有生成校验器是对的。它做了四件事，另外两方只做了第一件：

  1. 词条自己的标签（并英美变体）
  2. 表面形的标签（datum 无标签，页面上是 data）
  3. 词典自带的变形表（teeth / phenomena / curricula 还原失败，但 ECDICT 的 exchange 认得）
  4. A 级派生的词根，且要顺链走到底（nationality → national → nation，一步不够）

实测：453 篇里 8,401 处超纲标记，3,005 处（35.8%）的词根就在纲内——quickly 30 处、fully 28 处、cultural 27 处。修完降到 4,158 处。 正确做法：vocabulary/syllabus.py 一个函数，三方都调它，且返回布尔不返回标签集合—— 返回集合就意味着每个调用方自己写比较，而它们正是各自停在了不同的地方。 B 级派生单独回答（light_root），它不算超纲但算三分之一个目标词，两个答案要能分开数。 重算走 reading/recompute.py（POST /v1/admin/reading/recompute），只重写词典派生出来的值， 绝不碰 token 的身份、位置、义项标注——那些是遇见记录，标记指着它们；前后各数一次行数，对不上就回滚。 这次比前三次多学到一条：坏规则不只是让数字难看，它会让你选错。 P3 的模型横评先用坏规则算，排出 gpt-5.5 92% > deepseek-v4-flash 88%；换成对的规则重算变成 96% 对 94%，名次反了——差一点就把活派给了贵四倍、慢四倍的模型。 守卫：verify_phase2.py 3.6（quickly / teeth / nationality 不许判超纲）与 3.7（读源码断言三方调的是同一个函数）。 2026-09-18（P9）后果升级了一档：大纲判定的结果现在随文章下发到设备， 而设备照着它画记号、决定哪些词能标。判错一次不再只是这边数字难看， 是那个错误跟着今日包去了手机上，而那台手机离线时连改都改不了—— 只能等下一次下发。所以「三方调同一个函数」这条比以前更硬，不是更松。

5.2 第三次：tags 在英式／美式拼写之间随机分配（2026-09-08）

症状：labor 被判成超纲——实测 21 个词条、125 处，labor 一个词 41 处。 原因：ECDICT 的 tags 不是各存一份：labour 带 zk gk cet4 cet6，而 labor 只带 ky； judgement 是四级词，judgment 一个标签都没有。 正确做法：vocabulary/spelling.py 和 tags_of() 就是为这件事写的，模块开头第一段写的正是这个问题——调它。 （当时判超纲的两处 ingest._is_beyond、difficulty.syllabus_tags 没有调，安静地过了整整一个阶段。） 守卫：verify_phase2.py 3.5。

5.3 第二次：tags 是分级清单，不是累积的（2026-09-07）

症状：超纲率 58%，四级真题量出来比考研还难。 原因：the 只带 zk gk（中考、高考），并不带 cet4；make、people 同理。 正确做法：「四级水平之内」= 带 zk / gk / cet4 任意一个。改对之后超纲率 58% → 10%，三个等级也变成正确的单调上升。

5.2b 英美拼写的第二个现场：义项集（2026-09-24，P12 真机）

症状：catalog 点开标不了。 原因：柯林斯每个词只挂在一种拼写下、而且不固定是哪边（catalogue/behaviour 英式、 organization/realize 美式）；senses_of() 只按原拼写查。生产库 274 处 / 26 个词标成了「无义项集」。 §5.2 修的是大纲标签那个现场，spelling.py 早就在，义项集这个现场没人去调它。 正确做法：senses_of() 自己没有义项时退到 spelling.variants()——改在那一个函数里。 改完要重标注（reannotate_all.py --stale-zero），不然查法对了、库里的 0 还是 0。 守卫：verify_phase10.py C1–C3（C2 是阴性对照 sise/membre，C3 守「标成 0 的现在确实查不到」）。

5.2c 「在纲」这个名单本身漏了 195 个词（2026-09-25）

症状：dollar、colour、percent、mile 没有义项——柯林斯里明明有完整词条。 原因两层：① P10 导入名单取自旧义项集，而不是 targets.target_headwords()， 于是把 P1b 粗筛的判断原样继承了；② targets 里 frq > 0，注释说筛掉的「绝大多数是缩写和专名」， 没人数过——frq 是 COCA（美国）词频，英式拼写和一批普通词在那儿是 0。 更要紧的一条：守卫 A4 写的是「缺的 ≤ 320」，而名单漏掉的词根本不算缺—— 一个按错名单算的上限，守住的正是这个 bug。 正确做法：frq > 0 OR bnc > 0；导入名单＝在纲词 ∪ 已有；缺的每一个要缺得有理由。 守卫：verify_phase10.py A4（带阳性对照 dollar/percent）。

5.4 词形还原式和原样式各查一次

症状：漏义项报告里排第一的词是 accord，追下去是 84 处 according to 一处都没识别出来。 原因：spaCy 把 according 还原成 accord，而 accord to 在词典里没有条目。 正确做法：查词典时两种形式各查一次。 顺带：报告本身就是诊断工具——它排第一的那个词指的不是缺一条义项，而是识别少了一整类。

六、写数据库代码 / 解析别处写的数据前

§6.6 的 -Xswiftc 交叉编译示例属于当年的 CI 环境。Xcode 27 本地须使用顶层 --triple 加 --sdk，见 开发参考。§6.8 的 Documents 路径是当时场地，不是当前 checkout。

6.1 凡是解析别处写的数据，先看一眼它长什么样

症状：文章照样能读，读完什么都不记。不报错。 原因：generation_drafts.target_words 存的是 JSON 数组，按逗号空格切会切出 ["assignment" 这种永远匹配不上的东西。 正确做法：别照着字段名想当然，先打印一条真实数据出来看。

6.2 sqlite3.IntegrityError 被捕获后必须回滚

症状：几步之后一个毫不相干的请求报「database is locked」。 原因：失败的 INSERT 会把隐式事务挂着不放写锁。 正确做法：吞掉数据库异常的地方都要问一句事务归谁收。

6.3 ISO 时间戳和 SQLite 的 datetime() 不能直接比（2026-09-11）

症状：recover_interrupted() 只恢复得了昨天以前中断的批次任务。当天崩溃的永远停在 running， 于是那篇文章的标注永远续不上，文章永远停在 annotating、点开是空的，全程零日志。 原因：存的是 '2026-09-11T13:14:15+00:00'（ISO，T 分隔），比的是 datetime('now','-5 minutes') 即 '2026-09-11 13:09:15'（空格分隔）。'T' 的码位 0x54 大于空格 0x20，日期段相同时后面一位就把结果定死—— 同一天的比较永远为假，跨天才碰巧正确。 正确做法：截止时间在 Python 里按同一种格式算出来再比，别让两种格式在 SQL 里碰面。 顺带：这条最毒的地方是「跨天能用」——所以它能在测试里蒙混过去，只在当天重启时发作。

6.4 「下次运行时间为空」＝这个任务永远不再跑（2026-09-11）

症状：夜间备稿任务二十七分钟一次没跑，runs 一直是 0，没有任何日志说它为什么不跑。 原因：task_runs.next_due_at 是 NULL，而判定是 due <= now——None 永远不满足。 播种逻辑又只在行不存在时才写，行在、值为空就原样返回。 这个状态真实可达：任务收尾时如果周期解析失败（在控制台把周期写错过一次）， next_due_at 就被写成 NULL，从此永远不跑，把周期改回正确的也救不回来。 正确做法：值为空要重排并记 WARNING，而不是当作「已排好」。 重排到下一次而不是「立刻」——修复动作不该顺手多跑一次生成。 顺带：这类「空值＝永远不满足条件」的判定，都要问一句空是怎么来的、谁负责补上。 守卫：verify_phase4.py A3.3。

6.6 CI 的一步「成功」了也可能什么都没做（2026-09-12）

症状：L1「Core 能为 iOS 编译」这个 job 绿了，37 秒，一行都没编译。 原因：写成 xcodebuild … | xcbeautify || xcodebuild …，而管道的退出码是最后一个命令的—— xcodebuild 报错退出，xcbeautify 把输出消化完返回 0，于是这一步成功，|| 的兜底也没触发。 底下真正的错是 Supported platforms … is empty：xcodebuild -scheme 要从 SwiftPM 包里推导 scheme 支持哪些平台，推导出来是空的。 正确做法：① set -euo pipefail；② 别用 || 兜底，它会把失败变成沉默； ③ 编完断言产物真的存在——没有这一步，哪天又变成空跑，job 还是会绿。 绿着的空跑比没有这个 job 更糟，因为它还给人信心。 顺带：改用显式的 target triple 加 SDK（swift build -Xswiftc -target …），不让工具去推导。

6.8 macOS 的定时任务读不了 ~/Documents，而它不会说（2026-09-21）

症状：装了一个 LaunchAgent 跑标注脚本，launchctl list 里有、退出码 0， 看上去完全正常。真触发时什么都没发生，日志一个字没有。 原因：StandardErrorPath 里写着 /bin/zsh: can't open input file: …/scripts/resume_annotation.sh—— **macOS 的隐私保护（TCC）**不让 launchd 起的后台任务读 ~/Documents， 而这个项目和它的数据库都在那底下。同一个脚本手动跑完全正常（终端有权限）， 所以「我试过了，能跑」这句话在这里是假的。 正确做法：两条路—— ① 给 /bin/zsh 完全磁盘访问权限（系统设置 → 隐私与安全性 → 完全磁盘访问权限 → ＋ → Cmd+Shift+G 输入 /bin/zsh），代价是任何 zsh 脚本都能读全盘； ② 把项目挪出 ~/Documents（比如 ~/code/），不需要任何授权，更干净， 但路径写死在 CLAUDE.md 和几个脚本里，要一次改齐。 这条同时是 §6.6 的又一个实例：launchctl list 报的是「任务登记成功」， 不是「任务能干活」。只有真触发一次、看到日志里出现预期的那句话，才算验过。 顺带：launchd 给的环境极其干净，PATH 里几乎什么都没有—— 调 uv、python3 一律写绝对路径，或者在 plist 里补 EnvironmentVariables。

6.7 一个分不出两种情况的断言，等于没有断言（2026-09-12）

症状：为了防 6.6，我加了「确认产物是 arm64」的断言——它照样会在「iOS 目标被忽略、 实际编成了 macOS」时通过，因为两个平台的产物都是 arm64。 而且构建目录名写着 arm64-apple-macosx（SwiftPM 按宿主命名），看上去更像是编错了。 正确做法：读 Mach-O 的 load command——otool -l x.o | grep -A5 LC_BUILD_VERSION， platform 2 才是 iOS。读不出来要报红，不能默默放过：一个说不清自己验了什么的检查， 比没有更糟。 这条和 §4.3 是同一个形状：不是「有没有报错」，是「它区分得开吗」。

6.9 一个永远不等于任何东西的名字，不会报错（2026-09-22，P11）

症状：词组扫描抓出了 at - home、talked about . 这种跨逗号跨破折号的匹配， 而代码里明明写着「遇到标点就断开」。 原因：那一行是 BREAKING_KINDS = frozenset({"punct"})， 而这个项目里标点的 kind 叫 nonword（ingest._classify 定的，只有 content / function / proper / nonword 四种）。于是那个判断永远不成立， 静默失效——没有报错，没有日志，只有数据里多出一批看着像对的东西。 正确做法：正面列举允许的值，别列举要排除的值（改成 PHRASE_KINDS = {"content","function","proper"}）。前者写错了当场什么都匹配不上、 一眼看得见；后者写错了是「全部放行」，跟正常运行长得一模一样。 这条和 §6.7 是一家：不是「有没有报错」，是「它区分得开吗」。

6.5 任务「成功」了也可能什么都没做（2026-09-11）

症状：标注任务显示 6/6 全部完成、耗时 0.03 秒、零错误，而 275 个实词一个都没标注。 原因：任务规划时把 token id 存进了 payload，之后文章被重新分析过一次，token 被删了重建、id 全变。 每一批都按旧 id 去查，查出来是空的，于是「没有需要处理的内容」——报成功。 正确做法：按业务对象自愈，不要按任务自愈。要问的不是「任务跑完没有」而是 「文章现在能不能打开」——把所有「备好但没就绪」的文章按当下真实缺的 token 重新排上。 守卫：verify_phase4.py B5.1（不许有备好却打不开的文章）。 2026-09-18（P9）这个坑的后果变了，而且变得看不见了：token 被删了重建、id 全变， 以前只伤服务端自己（文章打不开，一眼看得出来）。记录搬到设备之后，标记指着的正是这些 id—— id 一变就是别人手机上的标记静默失效，而这边一切正常。 所以「内容 id 不可变」从实现细节升成了架构铁律 5：重新分析必须是加一个新版本，不是原地重建。

七、读代码时、等后台任务时

§7.2 所说的后台四条规则见根文件「模型与批量任务」，也保存在 开发参考。不要再按「上面」去找原根文件的位置。

7.1 一段解释性的注释会让人以为对应的代码在那儿

症状：404 带着 trace_id 发给用户、什么也不写；用户把 trace 贴过来，查出来是空的。 而「贴 trace 就能定位」正是把 trace_id 放进响应的全部理由。 原因：core/errors.py 的 404 处理器上写着「保持 INFO 级：拼错地址不算事故」，下面没有任何一行 log 调用。 正确做法：读代码时不要把注释当成实现的描述——它描述的是意图，实现可能从来没跟上。 守卫：verify_phase0.py 9.4。

7.3 查残留进程要查「自己丢到后台的那些」，不只是服务（2026-09-12）

症状：P5 全部做完、收尾查过好几遍「没有残留进程」之后，用户看到后台还有一个 shell 在跑。 是一条 find / -name "Package.swift" -path "*swift-openapi-generator*"—— Git Bash 里的 / 会扫遍 C: 和 D:（D: 上 516 GB），跑了三个半小时、烧掉 13000 秒 CPU。 原因有两层：① 那条命令本身就不该写，我几秒后就用别的办法查到了答案，扫描却没停； ② 收尾时我每次只查 python|swift|uvicorn 和端口占用，从没查过自己超时丢到后台的一次性命令。 正确做法：别在 Windows 上写 find /，要找第三方包就去它该在的目录找。 收尾那一查要按 CPU 排，不要按进程名过滤——名字是猜的，CPU 不是： Get-Process | Where-Object { $_.CPU -gt 60 }。 这条最扎眼的地方：CLAUDE.md 早就写着「收尾时顺手查一次，不要留给用户去发现」， 而这次正好是用户发现的。

2026-09-20 又一次，同一条，而且又是用户发现的（挂了 4 小时 51 分）。 这次多出一层，值得单记：|| 后面的兜底分支是没人审的代码。 当时那条命令是 ssh aliyun 'ls /opt/appdata/english-reader/data/ || find / -name "content.db" …'—— 路径猜错了（真实路径是 /opt/appdata/English reader/data，带空格和大写）， 于是 ls 失败、兜底的 find / 在阿里云上扫了全盘。 写的时候我眼睛只看了前半句，「万一找不到就全盘搜一下」这半句是顺手加的， 而它才是真正会跑起来的那一半。 两条都要守：① 兜底分支要和主分支同等对待，问一句「它什么时候触发、触发了干什么」； ② find / 在哪台机器上都不要写，远程执行时更甚——本地看到的只是一个不返回的 ssh， 跑飞的是别人的机器。 怎么认出来：本地那条 ssh 一直不退出，而 ps 里它的 CPU 时间几乎是 0 （活干在远端，本地只是在等）。所以按 CPU 查这次查不出来，要按 ELAPSED 查。

7.7 「我修好了一个真的缺陷」不等于「我修好了他报的那个问题」（2026-09-19）

症状：用户报「切选项卡很卡，还在转圈」。我从日志里挖出四个缺陷， 每一个都确凿（服务端 trace 里的 422、成对出现的日志行、存档里的越界值）， 每一个都修了、都配了回归测试——推了三版（11／13／14）， 而用户那边症状一次都没变。 原因：我一直在回答「日志里有什么不对」，而他问的是「屏幕为什么在转」。 那是两个问题。事后的日志能证明某个请求失败了，证明不了某一帧为什么没画出来—— 主线程花了多少毫秒、切屏时重建了哪些视图、.task 被取消了几次，日志里一个字都没有。 正确做法：症状类的报告，先想清楚「我要看的那个东西，现在的手段看得见吗」。 看不见就先解决看得见的问题（这次的答案是换场地到 Mac）， 而不是拿看得见的那部分连猜三轮——每一轮都消耗一次用户的真机验收， 而那是这个项目最贵的资源（P6 §13 就是为它欠了三个 Phase 的账）。 顺带一条：修掉的东西要如实说成「修了一个真的缺陷」，不能说成「应该好了」。 我三次都说成了后者。 守卫：无，这类守不住。phase-9.html §17 把这次的账算清了。

7.5 @MainActor 不防重入，而「每一行日志都是双份」是认出它的办法（2026-09-18）

症状：手机「一直转圈而且非常卡」。日志里 adopted=399 出现两次、 progress.pool.reported 出现两次、pending 从 0 跳到 798（正好 399×2）。 原因：AppModel 是 @MainActor，我据此以为 drain() 不会并发—— 而 MainActor 只保证「都在主线程上跑」，不保证不重入：await 一让出去， 第二个调用就从头跑起来。启动时 .task 和 scenePhase == .active 几乎同时到。 两趟 pull() 各自在开头取一份「已知幂等键」快照，于是同一批事件进日志两遍， 而两边的游标写入互相覆盖。 正确做法：要互斥就自己写互斥（一个 in-flight Task，并发进来的等它 而不是丢掉——await drain() 的含义是「一趟同步完成了」）。 怎么认出来：日志里每一行都是双份。这比任何推理都快， 而且它在 09-16 的日志里就已经是双份了——那时不致命，所以没人看它。 守卫：无。回归测试在 SyncTests（分片那条）与 EventLogTests（幂等那条）。

7.6 同一个方法、同一个形状、隔两天栽两次（2026-09-18）

症状：2026-09-16 真机上「越用越慢」，答得越多越卡。 原因：refreshPendingCount() 里塞了 outbox.pending()，而那个方法会 读取并解码发件箱里的每一个文件；record() 每记一条事件就调一次它。 2026-09-18 我在同一个方法里塞了 events.load()（为了显示「日志一共多少条」）， 形状一模一样，原因完全不同。 正确做法：贵的计数按需算（refreshEventCount() / refreshDamagedCount()）， 而禁令写在那个方法的注释里，不只记在这份坑里—— 第二次栽的时候我正在读这份文件的别处，而注释就在我手指下面。 守卫：无。

7.4 pkill -f <模式> 会杀掉你自己那条命令（2026-09-15，一小时里栽了三次）

症状：通过 ssh 在远端跑 pkill -f "docker compose --env-file"，命令没有任何输出就结束了， 后面的步骤一步都没执行。看起来像 ssh 断了，其实是它把自己杀了。 原因：pkill -f 匹配的是进程的完整命令行，而我那条 ssh 命令的命令行里就含着那个模式串—— ssh host 'pkill -f "X"' 的远端 shell 命令行里有 X，于是它匹配到自己。 写成脚本也救不了：只要 ssh 命令行里出现过那个字面量（比如用 heredoc 把脚本内容传过去）， 远端那条 bash -c 的命令行里就有它。第三次是在 pgrep -f "bake" 上栽的， 当时我以为换成 pgrep 就没事了。 正确做法：先用一次调用取 PID，再用下一次调用按 PID 杀。 非要在一条命令里做，就让模式串在命令行里长得不一样：pgrep -f bak"e"—— pgrep 收到的是 bake，而我的命令行里是 bak"e"，匹配不上。 怎么认出来：远端命令静默地少执行了后半截，而且没有任何错误。 和 §6.6 是一家——失败被变成了沉默。 守卫：无。

7.2 等待条件不要依赖一个后来又被自己改变的东西

症状：循环永远不退出，shell 一直空转，控制台一直显示「还有任务在跑」，让人以为有事没做完。 原因：犯过两次同一类错误——第一次是等一个永远凑不满的输出行数（自己用 tail 截掉了前几行）， 第二次是等一个日志文件里的完成标记（自己在收尾时 rm 掉了那个文件）。 正确做法：见上面「后台任务与等待」那四条规则（查数据库不轮询日志、循环必须有超时、清理放最后、收尾查残留进程）。

2026-09-15 第三次，形状又变了一点：等的是一个已经死掉的进程的输出。 两个 until grep -q ...; do sleep; done 分别在等两个探针脚本写出结果， 而那两个脚本一个被 timeout 杀了、一个 import 失败当场退出—— 它们的输出永远不会出现，于是循环永远不退。 最后是机器内存不足把它们杀掉才结束的（当时在 r5s 上，3.6G 还跑着九个容器）。 「循环必须有超时上限」这条就是为这个写的，而我没照做—— 等待条件不只要防「自己后来改掉它」，还要防「产生它的那个进程已经不在了」。 顺带：别并行跑验收脚本，每个都要加载 spaCy（134 MB）加一整个后端—— 在小内存机器上这会直接被 OOM 杀掉（r5s 上栽过），Mac 上不至于，但一样是白烧。
